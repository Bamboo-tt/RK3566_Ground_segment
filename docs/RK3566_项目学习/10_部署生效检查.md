# 10 部署生效检查：把交付资料与正在运行的系统对应起来

前面各章已经说明屏幕、触摸、电源和风扇的工作原理。现在需要回答一个更具体的问题：那些源码和包内配置，是否真的被手中这块板采用了？如果运行的仍是另一个内核或另一份设备树，在新文件里分析得再正确，也不能直接解释眼前现象。

本章沿“实物与交付身份 → 构建和启动选择 → 最终设备树 → 驱动绑定 → 标准接口 → 物理行为”逐层检查。所有 Linux 命令都是**目标板已有系统上的后续只读示例，本轮没有执行**，也没有预填实测输出。工具不存在、路径不同或权限不足时，应记录证据缺口，不能把空输出直接当成硬件故障。整个检查不要求安装、刷机、重启或改写配置。

## 10.1 先明确每一层的“生效”证明了什么

| 证据层 | 当前可以回答的问题 | 还不能单独证明的事 |
| --- | --- | --- |
| 原始资料与交付包 | 准备分析或部署的内容是什么 | 板上已安装并启动这些内容 |
| 包管理与构建结果 | 哪个包已配置，哪个内核的 DTBO 已生成 | 引导过程实际选择了它们 |
| 运行内核和最终设备树 | 本次启动的内核发行号、内核可见的硬件描述 | 驱动理解所有属性且外设通信成功 |
| 设备绑定和标准接口 | 哪个 driver 接管设备，注册了什么能力 | 像素、坐标、物理量和恢复过程一定正确 |
| 物理行为和上层消费 | 明确输入条件下是否得到正确、可重复结果 | 未覆盖条件下的长期、环境和业务可靠性 |

这个顺序来自依赖关系，而不是为了多做检查。包不对应时先解决版本身份；最终树不对应时先解决选择与组合；原始 input 事件已正确时，才转向桌面坐标映射。每到一层都应保留前一层的对象信息，否则后续日志可能来自完全不同的配置。

第 2 章解释的是产物如何形成，本章检查的是这些产物是否参与了当前系统；第 11 章再把本章取得的证据用于具体故障判断。三者分别承担构建原理、生效确认和症状定位，不能把历史安装步骤直接当成本次检查结果。

## 10.2 先固定实物与软件身份

### 10.2.1 原理图、屏幕和交付包必须属于同一组对象

从核心板型号、底板丝印及修订、屏幕型号、装配器件开始记录，再选择相应原理图。2025-10-21 的地面站底板与 2025-11-21 的相机底板存在 GPIO 用途差异，文件日期更近不能证明它对应实物。6 英寸与 7 英寸屏幕资料也需要先分开，不以“都是 MIPI 屏”推定配置通用。

软件一侧至少记录原始 `.deb` 哈希、内核发行号、基础 DTB 来源、准备启用的产品 DTBO 名称。两份 overlay 包都标为 `radxa-overlays-dkms 0.2.4`，因此版本号相同不能区分普通与 PWM 变体。已核对原包的路径、哈希和关键成员统一见[第 13 章](13_关键资料阅读索引.md)。

原包哈希只识别交付文件。系统中的文件可能在安装后被重建或替换，DTBO 也可能来自另外一次构建，因此还要沿安装位置、启动选择和最终树继续核对。不要把一个包的哈希扩大成整套运行状态的身份凭据。

### 10.2.2 分别检查“已安装”和“正在运行”

在目标板 Linux shell 的任意目录，先读当前内核和发行版，再读包管理记录：

```sh
# 查看这次启动的内核、系统发行版和已有安装记录。
uname -r
cat /etc/os-release
dpkg-query -W -f='${Package}\t${Version}\t${Architecture}\t${Status}\n' 'linux-image-*' radxa-overlays-dkms
```

`uname -r` 给出当前运行内核的发行号；`dpkg-query` 可以列出多个已安装版本。`install ok installed` 只说明包管理状态正常，不意味着该内核已经启动。现有交付包对应的发行号为 `6.1.84-12-rk2410-nocsf`，它是待比较对象，不是本轮命令的实际输出。

如果已装版本与运行版本不一致，应先追踪引导选择，而不是立即重装。即便发行号相同，也不能据此证明二进制和源码完全相同，因为不同构建可以保留同一发行号。若系统发行版与历史记录不同，也先记录平台差异，避免把另一套发行版的启动路径和工具习惯直接套用。

## 10.3 DTBO 已生成之后，还要证明启动过程选择了它

### 10.3.1 从 DKMS 状态找到当前内核对应的产物

overlay 包交付的是源码和构建规则，安装并不等于已经得到当前运行内核可用的全部 DTBO。只有目标板已经具备 DKMS 时，才在其 shell 中执行以下读取：

```sh
# 查询构建安装状态，并查看当前内核的 overlay 目录和候选产物。
dkms status
readlink -f "/usr/lib/linux-image-$(uname -r)/rockchip/overlays"
find -L "/usr/lib/linux-image-$(uname -r)/rockchip/overlays" -maxdepth 1 -type f -name 'aircas-compact-GCS*.dtbo'
```

先核对 DKMS 条目对应的内核和架构，再看目录链接最终指向哪里，最后确认产物文件存在。某个旧内核显示构建成功，不足以证明当前内核的目录有文件；普通和 PWM 变体同时存在，也不意味着它们同时被启用。

包内 `dkms.post_install` 会检查目标内核的 vendor 目录，并在某些目录布局不符合条件时跳过链接处理；已有非链接的 overlays 目录也有单独处理分支。它还只在可找到 `rsetup` 时调用 `rsetup rebuild_overlays`。这些是包内脚本事实，解释了“源码已经安装”和“启动侧能找到产物”之间为何还存在一步。

没有产物时，下一步应读对应 DKMS 构建日志和 hook 条件，区分未构建、构建失败、内核目标不符、链接未建立。目录或工具不存在则先记录环境差异，本章不补装工具，也不为了检查而重新执行构建脚本。有产物时，才继续寻找启动选择。

### 10.3.2 配置文件里的选择意图仍需与运行结果对应

现有材料没有给出足够完整的实际引导工程，正式启动配置入口仍待确认。下面只读取几种常见候选文件，不能把任意候选写成本板唯一启动方式：

```sh
# 在确实存在的候选文件中寻找基础设备树和 overlay 的选择记录。
for boot_cfg in /boot/extlinux/extlinux.conf /boot/uEnv.txt /boot/config.txt; do
    if [ -f "$boot_cfg" ]; then
        grep -HnEi 'fdt|overlay' "$boot_cfg"
    fi
done
```

有匹配项时，记录所指文件、所在启动项及其来源，再与上一节产物位置对应。候选全部没有匹配项，只能说明这次查找没有发现入口，还应根据实际引导配置、rsetup 生成结果和启动日志追查；不能直接判断 overlay 未应用。

即使配置中出现了产品名称，它也只是启动意图：可能另一个启动项生效，也可能产物路径已变或组合失败。要判断此次内核实际得到什么，必须进入最终设备树层。

## 10.4 读取内核可见的最终设备树

### 10.4.1 先识别平台，再定位具体设备

Linux 通常通过 `/sys/firmware/devicetree/base` 暴露运行设备树。字符串属性含 NUL 终止符，整数属性是二进制大端数据，不能把所有属性都用 `cat` 当普通文字解释。这是接口通用原理，不是本轮获得的板端目录快照。

例如源码的 `max-x = <1280>` 是一个 32 位整数单元，按编码规则对应字节 `00 00 05 00`；它不是文本字符 `1`、`2`、`8`、`0`。这个由源码换算的例子说明了为什么直接打印可能看到空白或不可读字符，不能把这种显示当成属性为空。下一节用 `dtc` 读取的目的，就是让工具按设备树编码还原这些值和引用关系。

在目标板 shell 中，先检查身份字符串，再按本项目地址寻找候选节点：

```sh
# 读取平台身份，并定位触摸与电量计的设备树候选节点。
tr '\0' '\n' < /sys/firmware/devicetree/base/model
tr '\0' '\n' < /sys/firmware/devicetree/base/compatible
find /sys/firmware/devicetree/base -type d \( -name '*@14' -o -name '*@62' \)
```

`model` 和 `compatible` 说明内核得到的身份描述，但产品 overlay 未必改写它们，不能仅凭平台名称确认全部产品属性。找到 `@14` 或 `@62` 后，还要用父节点、`compatible` 和 `reg` 区分同地址设备，不直接假设它就是目标 GT9XX 或 CW2015。

节点及父总线都要检查状态。没有 `status` 通常不等于禁用；反过来，子节点写了 `okay`，父控制器不可用也不能形成正常通信链。Linux I2C 总线编号还可能受 aliases 等因素影响，不能把文件中的 `i2c1` 标签机械替换成板端固定总线号。

### 10.4.2 比较最终属性，而不只比较节点名称

若系统已提供 `dtc`，可以把运行树转换为可读文本，在目标板 shell 中查看：

```sh
# 反向呈现运行树；只读，不安装或修改设备树。
dtc -I fs -O dts /sys/firmware/devicetree/base | less
```

这有助于读取整型值、跟踪 phandle 及检查合并结果。反向呈现的标签不一定保留源码写法，看到数字引用时应沿节点关系查找，不能因为标签名不同就认定来源不同。结构警告也应结合实际 binding 分析，警告总数不是故障数量。没有 `dtc` 时保留原始属性供主机离线解析，不在本任务安装它。

| 最终树中的重点 | 为什么检查 | 什么结果会改变下一步 |
| --- | --- | --- |
| I2C1 触摸地址、GPIO、供电、尺寸属性 | 确认产品节点和驱动契约 | 属性仍属另一驱动分支时，先解决版本对应，不先调坐标 |
| I2C3 下 `0x62`、profile 和采样设置 | 确认外置电量计配置 | 节点缺失时先查组合；存在时再查 CW2015 绑定和采样 |
| VP0 → DSI0 路由、endpoint、panel 参数 | 确认像素链描述 | 路由不符时先查基础树与 overlay，不直接改初始化表 |
| PWM5 亮度表长度及默认索引 | 区分当前有效配置 | 197 项表要按索引 0～196 分析，不能默认范围是 255 |
| SDMMC0 状态与 GPIO1_D5 用途 | 检查屏幕电源脚的复用条件 | SDMMC0 也启用时继续核对 pinctrl，不能因 DTBO 合并成功排除冲突 |
| 风扇 PWM0、trip 和 cooling map | 确认温控关系是否完整 | 缺失绑定时先修正身份判断，不从两个阈值猜风扇开关 |

最终树正确只说明描述到了内核。以两套 GT9XX 为例，相同 compatible 仍可能对应不同属性解析，因此下一步必须查实际设备和 driver，而不能在“节点存在”处停止。

## 10.5 从设备对象走到真正绑定的驱动

### 10.5.1 I2C 设备：用地址筛候选，用来源确定身份

I2C 设备目录名通常含总线号和四位地址。以下命令在目标板读取地址候选的名称、设备树来源和已绑定驱动，不假设固定总线号：

```sh
# 区分设备存在、来自哪个节点，以及是否已与 driver 绑定。
for i2c_dev in /sys/bus/i2c/devices/*-0014 /sys/bus/i2c/devices/*-0062; do
    [ -e "$i2c_dev" ] || continue
    printf '%s\n' "$i2c_dev"
    [ ! -r "$i2c_dev/name" ] || cat "$i2c_dev/name"
    [ ! -e "$i2c_dev/of_node" ] || readlink -f "$i2c_dev/of_node"
    [ ! -L "$i2c_dev/driver" ] || readlink -f "$i2c_dev/driver"
done
```

没有候选设备目录时，优先回看父控制器、最终节点和总线枚举。目录存在但没有 `driver` 链接时，继续查驱动配置、匹配、probe 错误和延迟探测。driver 链接存在时，再查它注册的 input 或 power_supply 对象，不能把所有后续成功都包含在“已绑定”三个字中。

`lsmod` 没有 GT9XX 不是充分的故障证据。现有内核包的 `CONFIG_TOUCHSCREEN_GT9XX=y`，表示内建；内建驱动不以普通已加载模块形式出现在 `lsmod` 中。包还包含另一项 `CONFIG_TOUCHSCREEN_GOODIX=m`，这不能替代对实际设备绑定的确认，更不能凭名称相近认作同一实现。

### 10.5.2 风扇：代码加载和设备绑定仍是两件事

现有包的 `CONFIG_SENSORS_PWM_FAN=m`，并包含对应发行号的 `pwm-fan.ko.xz`。因此看不到目标 cooling device 时，先确认模块和 platform 设备关系，再讨论 governor 是否选择了合适档位。

在目标板 shell 中只读模块列表及驱动目录：

```sh
# 查看 pwm-fan 代码是否加载，以及 platform 驱动下是否有设备链接。
lsmod | grep -E '^pwm_fan[[:space:]]'
ls -l /sys/bus/platform/drivers/pwm-fan
```

模块在列表中只说明代码加载了；驱动目录存在但没有相应设备链接，也不等于绑定完成。应从实际设备链接回溯 `of_node`，确认对应的是目标风扇，再进入 cooling device、PWM 和物理转动检查。目录不存在时先区分当前内核、模块位置及装载状态，本章不执行 `modprobe` 来改变现场。

显示也应遵循相同原则，但 panel 是 DSI 链的一部分，不能拿 I2C 地址检查套用它。通过 DRM 接口及设备父子关系确认其实际来源，再结合 DSI/panel 日志定位，详见[显示与背光](06_显示与背光.md)。

### 10.5.3 错误日志要按依赖关系回溯

在目标板具有日志权限时，读取本次启动的内核消息：

```sh
# 搜索相关错误的上下文；这只是入口，不以最后一条日志直接定因。
journalctl -k -b --no-pager | grep -Ei 'goodix|gt9|cw2015|charger|panel|dsi|backlight|pwm|thermal|defer|regulator|pinctrl'
```

没有 journal 时可以读取已有 `dmesg`，权限不足则记录限制。过滤结果用于定位时间点，仍应保留相邻的未过滤上下文。例如后面的 I2C 错误可能来自先前的 regulator 失败，GPIO 申请失败可能来自 pinmux 冲突；先修正对前置依赖的判断，才有依据解释后续报错。

日志沉默不证明成功。部分源码会记录错误后继续，也可能根本没有到达目标分支。下一层必须给出明确输入，观察标准接口是否产生对应结果。

## 10.6 标准接口提供的是哪一种证据

### 10.6.1 显示和背光分别观察

在目标板读取 DRM connector 公布的状态和模式，再独立读取 backlight 属性：

```sh
# 查看显示连接状态、软件使能状态和公布的模式。
for drm_conn in /sys/class/drm/card*-*; do
    [ -r "$drm_conn/status" ] || continue
    printf '%s\n' "$drm_conn"
    cat "$drm_conn/status"
    [ ! -r "$drm_conn/enabled" ] || cat "$drm_conn/enabled"
    [ ! -r "$drm_conn/modes" ] || cat "$drm_conn/modes"
done

# 分别读取请求亮度、报告亮度、最大索引和背光电源状态。
for bl_dev in /sys/class/backlight/*; do
    [ -d "$bl_dev" ] || continue
    for bl_attr in brightness actual_brightness max_brightness bl_power; do
        [ ! -r "$bl_dev/$bl_attr" ] || grep -H . "$bl_dev/$bl_attr"
    done
done
```

**connector** 是 DRM 对一个显示输出连接的表示；它不是面板通信是否成功的万能状态。三个文件应放在一起理解：

| 属性及可能读到的内容 | 当前能说明什么 | 下一步判断 |
| --- | --- | --- |
| `status` 为 `connected`、`disconnected` 或 `unknown` | 驱动报告的连接判断 | 固定面板未必具有能检查排线的热插拔检测，不能把 connected 当成物理通信通过 |
| `modes` 列出一个或多个模式名 | 该输出公布的可用模式 | 它是候选列表，不等于当前正在按第一项扫描；为空时回看模式获取、拓扑与 panel 路径 |
| `enabled` 为 enabled 或 disabled | 输出在软件显示管线中的关联状态 | disabled 时先查输出选择和提交；enabled 时仍需核对实际呈现及物理链路 |

[上游 v6.1 的 DRM sysfs 实现](https://raw.githubusercontent.com/torvalds/linux/v6.1/drivers/gpu/drm/drm_sysfs.c)中，`enabled` 依据 connector 是否关联 encoder 判断，`modes` 则遍历模式列表。这解释了上述证据边界，不代表目标 BSP 的所有细节已经核对。有模式但无图像时，还要区分上层是否提交了非黑的内容、面板是否准备完成以及物理传输是否可靠；软件提交全黑画面与链路故障在肉眼上可能相似。

背光的 `brightness` 是请求值，`actual_brightness` 是驱动报告值，都不是光学测量。某个可选属性未提供不表示整个接口失败。`max_brightness` 若为 196，与 197 项表的索引范围相符，但仍要结合最终树确认来源，不能把它当作包身份的唯一指纹。

背光有光而画面为空，下一步应沿 panel/DSI 链调查；逻辑亮度非零却没有光，则继续核对使能、PWM 和电路。这样才能避免在错误通道中反复修改参数。

### 10.6.2 触摸先看原始事件，再看桌面消费

先读取 `/proc/bus/input/devices`，用 Name、物理路径及 Handlers 确认目标 input 设备和实际 `eventN`；再使用系统已有的 `evtest /dev/input/eventN`。`eventN` 是需要替换的设备编号，不能跨启动固定假定。命令和事件含义见[第 7 章](07_触摸与input.md)。

这里的“原始事件”是相对于桌面而言：`evtest` 读取 evdev，看到的是触摸驱动解析、交换或翻转后提交给 input 的值，不是 I2C 原始字节。它可以帮助区分“内核输入结果”和“桌面消费”这两段；若还要区分控制器 CFG 与驱动内部变换，需要匹配源码以及位于解析前后的诊断记录，当前标准接口不能单独给出答案。具体观察位置见[第 11 章 11.4.2 节](11_故障排查与验证.md)。

能力声明可以帮助区分 slot、tracking ID 等上报方式，但不能只凭一个设备名确认驱动版本。用单指按下、移动、抬起，再用多指重复，检查事件帧是否完整、释放是否出现、坐标范围和四角方向是否合理。

原始事件正确而桌面点击位置错误时，调查显示方向、桌面坐标变换和消费者选择；原始事件已经错误时，留在控制器配置、驱动转换和数据有效性层。没有事件时再查 IRQ、I2C 和驱动状态，不先把问题归到坐标交换。

### 10.6.3 电源读数先确认对象和单位

在目标板枚举实际注册的 power_supply 对象：

```sh
# 将对象名称和属性一起读取，避免把不同电源设备的状态混为一谈。
for ps_dev in /sys/class/power_supply/*; do
    [ -r "$ps_dev/uevent" ] || continue
    printf '%s\n' "$ps_dev"
    cat "$ps_dev/uevent"
done
```

先区分 CW2015 电量计、外部输入检测，以及系统可能同时存在的其他电池驱动。标准电压字段通常使用 µV；容量百分比、充电状态和在线状态又是不同含义。解释具体字段时必须结合实际绑定驱动，不能把两个对象里相近的名字直接互换。

外部输入 `ONLINE=1` 说明该检测链认为电源在线，不能证明电池正在接受充电电流。电压数值存在也只说明软件提供了值，还需与独立测量核对单位、单双节条件和量程。profile 的来源与电芯匹配则是另一项验证，不能用“电压看起来合理”替代，详见[第 8 章](08_电量与外部供电.md)。

### 10.6.4 温度、策略、冷却档位需要成组读取

在目标板分别读取 thermal zone 和 cooling device，再将实际对象关联起来：

```sh
# 确认温区身份、当前温度和当前采用的策略。
for thermal_zone in /sys/class/thermal/thermal_zone*; do
    [ -d "$thermal_zone" ] || continue
    for thermal_attr in type temp policy; do
        [ ! -r "$thermal_zone/$thermal_attr" ] || grep -H . "$thermal_zone/$thermal_attr"
    done
    for trip_attr in "$thermal_zone"/trip_point_*; do
        [ ! -r "$trip_attr" ] || grep -H . "$trip_attr"
    done
    for thermal_binding in "$thermal_zone"/cdev[0-9]*; do
        [ -L "$thermal_binding" ] || continue
        printf '%s -> %s\n' "$thermal_binding" "$(readlink -f "$thermal_binding")"
        [ ! -r "${thermal_binding}_trip_point" ] || grep -H . "${thermal_binding}_trip_point"
    done
done

# 确认冷却设备身份、当前档位和最大档位。
for cooling_dev in /sys/class/thermal/cooling_device*; do
    [ -d "$cooling_dev" ] || continue
    for cooling_attr in type cur_state max_state; do
        [ ! -r "$cooling_dev/$cooling_attr" ] || grep -H . "$cooling_dev/$cooling_attr"
    done
done
```

thermal 温度通常以 m°C 表示，`cur_state` 是离散冷却状态，不是占空比百分比或实测 RPM。上面的第一组读取还沿 `cdev*` 符号链接定位全局 cooling device，并读取它在该温区对应的 trip 编号。温区内的 `cdev0` 不一定指向全局 `cooling_device0`，不能仅凭末尾数字把两者配对。

例如某条绑定若指向已经确认的 pwm-fan，且其 `_trip_point` 为 `N`，就应继续对应同一温区的 `trip_point_N_type/temp/hyst`；这是一种结果判读方式，不是本轮输出。风扇对象存在却找不到目标温区到它的绑定时，应先定位绑定关系；绑定存在时再讨论该 trip 与策略如何触发冷却请求。[thermal sysfs 文档](https://www.kernel.org/doc/html/v6.1/driver-api/thermal/sysfs-api.html)说明了这些接口之间的关系。

编译配置中的默认 governor 不能代替运行时 `policy`；策略名称相同，也还需确认它与这个冷却设备的能力相容。如果温度跨过 trip 但档位未变，下一步检查 governor 和 cooling map；档位已变但风扇不动，则继续看 PWM 和电路。不能仅根据 60 ℃、85 ℃ 两个阈值推导简单开关逻辑，具体机制见[第 9 章](09_温控与风扇.md)。

## 10.7 把软件状态与可重复的物理结果连接起来

软件接口给出的是某一时刻的观察窗口。要形成可以复核的验证记录，还需要说明实物、软件组合、时间、输入条件、原始输出、物理观察和剩余问题。写“某内核和设备树下，目标 input 节点在四角操作时产生对应原始事件”，比只写“触摸 OK”更能支持后续判断。

以下均是待执行步骤，没有预填 PASS；本轮没有实际操作硬件或改变设备状态。

| 后续验证步骤 | 能够证明什么 | 仍不能证明什么 |
| --- | --- | --- |
| 对应内核、包、最终树和绑定对象 | 测试对象与资料形成可追踪关系 | 外设已经产生正确物理行为 |
| 显示固定图样，核对方向、边缘和连续刷新 | 当前配置及当前条件下图像链可用 | 所有供电、温度和恢复条件下可靠 |
| 单指/多指按下、移动、释放，对照原始事件和桌面 | 输入协议、坐标和消费者的基本关系 | 长时间抗干扰及全部手势场景 |
| 对照独立电压测量和外部输入变化 | 当前读数单位、量程及在线检测极性 | 实际充电控制、profile 适用性和 SOC 精度 |
| 核实电芯型号，并逐字节对应 profile 来源 | 模型数据与声称的电池对象匹配 | 实际使用条件下的 SOC 估算准确性 |
| 对照温度、policy、cooling state、PWM 和实际转动 | 选定条件下温控链是否接通 | 极端负载散热能力和风扇寿命 |

需要测量时，应记录仪器、测点、负载及供电条件。一次软重启成功不能代替冷启动；一次风扇转动不能证明高负载温控；状态位恢复也不能证明总线通信恢复。验证边界写清楚，才能让下一次检查沿已有证据前进，而不是重新猜测。

本章完成的是“当前系统采用了什么、哪些层已有证据”的确认。接下来[第 11 章](11_故障排查与验证.md)从黑屏、触摸错位、电量异常和风扇不响应等现象出发，决定优先沿哪条链继续收敛。

## 10.8 自查：能否判断下一条证据应来自哪里

### 10.8.1 问题

1. `dpkg-query` 显示正确版本后，为什么还要查 `uname -r`，并继续核对实际文件？
2. DTBO 文件存在、启动配置出现其名字，是否已经证明 overlay 生效？
3. 为什么运行树中有 GT9XX 节点，甚至出现 driver 链接，触摸仍可能没有事件？
4. 日志没有报错，而 `actual_brightness` 和 `cur_state` 都有数值，下一步应验证什么？
5. 某组检查没有输出时，为什么不应立即重装或换包？

### 10.8.2 回答要点

1. 已安装状态和本次启动选择不同；相同发行号也不保证二进制完全相同。应把原包、实际文件、运行版本和最终树建立对应关系。
2. 它们分别证明产物存在和选择意图；仍需确认本次有效启动项、最终树属性及驱动消费，不能跨层推断。
3. 节点可能未正确枚举，属性可能不匹配，probe 可能忽略某些错误；绑定后 IRQ、I2C、触点校验及上报也可能失败。应依次定位缺失环节。
4. 这些是软件报告值。背光要与实际光照及 PWM/使能对应，风扇要与温区绑定、PWM 和物理转动对应，同时保留当时条件。
5. 先区分路径、工具、权限、设备身份和版本问题，再判断缺失在哪一层。重装会改变现场，却不一定触及原因，也无法代替原始证据。
