# 10 部署生效检查

```text
包内源码/产物 -> 包配置与 hooks
    +-- 内核、模块、基础 DTB -> 系统安装位置 --+
    +-- DKMS -> DTBO -> 内核 overlay 链接 ----+-> 启动项选用
RootFS：启动配置、hooks、用户程序 -------------+       |
                                                    v
运行内核 + 最终设备树 -> 设备绑定 -> 标准接口 -> 外设行为与上层消费
```

核心依据是[内核包](../../debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb)的 `control/postinst`、[overlay 包](../../debs/radxa-overlays-dkms_0.2.4_all.deb)的 `dkms.post_install`，以及[构建记录](<../../RADXA CM3地面站编译.docx>)中的 rsetup 选择步骤。第 02 章解释文件如何产生，本章把一个文件追到一次启动及其设备接口。

下面命令用于目标板 Linux shell，使用系统已有工具，以读取状态为主。先选定实物底板与屏幕，再记录包哈希、内核发行号、基础 DTB 和产品插件；后续每个结果都沿同一个设备对象解释。

## 10.1 将安装版本与运行内核对应

地面站底板和相机底板使用部分相同 GPIO，却连接不同负载；6 英寸与 7 英寸屏也有独立初始化参数。先按丝印、接口与装配选择原理图，再用[资料索引](13_关键资料阅读索引.md)确定交付文件。两个 overlay 包均为 0.2.4，应使用完整哈希区分。

```sh
# 查看这次启动的内核、系统发行版和已有安装记录。
uname -r
cat /etc/os-release
dpkg-query -W -f='${Package}\t${Version}\t${Architecture}\t${Status}\n' 'linux-image-*' radxa-overlays-dkms
```

`dpkg-query` 可以列出多个已安装内核，`uname -r` 只返回当前运行内核。两者不同，就先找启动项指向哪一个映像；相同则继续比较实际文件来源与最终设备树。版本号可以被不同构建复用，包管理记录也不会跟踪用户后来手工替换的每个文件。

本项目包对应 `6.1.84-12-rk2410-nocsf`。其模块目录在 `/lib/modules/<release>/`，基础 DTB 在 `/usr/lib/linux-image-<release>/rockchip/`；内核 `postinst` 把发行号和映像路径交给 `/etc/kernel/postinst.d` 中的系统 hooks。若安装记录正常但启动仍旧，检查从 hook 输出到启动项的交接，而不是先重装所有包。

## 10.2 从 DTBO 构建目录追到启动选择

### 10.2.1 找到当前内核的产物与符号链接

```sh
# 查询构建安装状态，并查看当前内核的 overlay 目录和候选产物。
dkms status
readlink -f "/usr/lib/linux-image-$(uname -r)/rockchip/overlays"
find -L "/usr/lib/linux-image-$(uname -r)/rockchip/overlays" -maxdepth 1 -type f -name 'aircas-compact-GCS*.dtbo'
```

按内核发行号和架构比较 DKMS 条目，再看链接目标与 `aircas-compact-GCS*.dtbo`。旧内核的构建成功不会自动提供新内核的产物；普通和 PWM 插件同时存在，也还要选择所需变体。

`dkms.post_build` 保存 DTBO，`dkms.post_install` 建立 vendor/overlays 链接。后者在目标内核缺少 vendor 目录，或该位置已有非链接的 overlays 目录时会跳过；只有存在 rsetup 才调用 `rebuild_overlays <kernelver>`。包内另有占位 `radxa-overlays.ko`，它只打印日志，不负责合并树。

若找不到 DTBO，先读该 kernel release 的 DKMS 构建日志：没有构建记录就查包配置入口，编译出错就查对应 headers 与目标，文件已生成而安装位置缺失就查上述链接条件。这三个结果指向不同环节。

### 10.2.2 找实际生效启动项，再看合并结果

本仓库没有保存最终 RootFS 中的启动配置及 rsetup 生成内容，因而需要从目标系统确定选择入口。下面仅在存在的候选文件中查找 DTB/overlay 字段：

```sh
# 在确实存在的候选文件中寻找基础设备树和 overlay 的选择记录。
for boot_cfg in /boot/extlinux/extlinux.conf /boot/uEnv.txt /boot/config.txt; do
    if [ -f "$boot_cfg" ]; then
        grep -HnEi 'fdt|overlay' "$boot_cfg"
    fi
done
```

有结果时沿当前启动项解析基础树和插件路径，并与上一节真实链接对应。没有结果时继续查实际引导程序使用的配置位置及启动日志；候选列表并不覆盖所有系统布局。

配置中的路径表达选择意图，最终树表达这次内核收到的组合。若启动项名字正确但属性仍旧，应比较有效启动项、文件内容、读取位置与 overlay 应用日志。将复制、生成、选用和应用分开，就能定位“装了包却没变化”停在哪一步。

## 10.3 在最终树中确认资源和属性

### 10.3.1 二进制属性按自身编码读取

`/sys/firmware/devicetree/base` 暴露内核当前的设备树。字符串包含 NUL，整数单元采用大端编码。例如 `<1280>` 对应 `00 00 05 00`，直接 `cat` 看到空白字符时，不应按文本空值解释。

```sh
# 读取平台身份，并定位触摸与电量计的设备树候选节点。
tr '\0' '\n' < /sys/firmware/devicetree/base/model
tr '\0' '\n' < /sys/firmware/devicetree/base/compatible
find /sys/firmware/devicetree/base -type d \( -name '*@14' -o -name '*@62' \)
```

按父总线、`compatible` 与 `reg` 共同识别 `@14` 和 `@62`，再核对父控制器的状态。`status` 缺省通常允许设备，父控制器 disabled 则会阻断子设备创建。DTS 标签 `i2c1` 也不能直接当作 Linux 的固定总线编号，应沿实际 `of_node` 追溯。

系统有 dtc 时可完整查看树：

```sh
# 反向呈现运行树；只读，不安装或修改设备树。
dtc -I fs -O dts /sys/firmware/devicetree/base | less
```

反向呈现会显示数字 phandle，源码标签不一定保留原名；沿 phandle 指向的节点理解依赖。结构警告也要落实到具体属性与 binding。

### 10.3.2 比较会改变行为的属性

| 对象 | 对照内容 | 结果如何决定下一步 |
| --- | --- | --- |
| GT9XX | 父 I2C、0x14、GPIO、supply、尺寸属性 | 缺节点查选择/组合；属性属另一分支查驱动契约 |
| CW2015 | I2C3、0x62、profile、双节与周期配置 | 组合正确后进入初始化、缓存和采样 |
| 显示 | VP0、DSI0 route、endpoint、panel 命令与时序 | 先定位路由还是面板状态，再查像素输出 |
| 背光 | 表长、默认索引、PWM5、极性与使能 | 按当前表解释亮度值，不固定假定 0～255 |
| 屏幕供电 | GPIO1_D5 与 SDMMC0 状态 | 同时占用时继续检查 pinctrl 的实际请求 |
| 风扇 | PWM0、cooling-levels、trip 与 map | 描述完整后比较 governor 和设备能力 |

## 10.4 从设备对象确定实际驱动

### 10.4.1 地址、of_node 和 driver 形成身份链

```sh
# 区分设备存在、来自哪个节点，以及是否已与 driver 绑定。
for i2c_dev in /sys/bus/i2c/devices/*-0014 /sys/bus/i2c/devices/*-0062; do
    [ -e "$i2c_dev" ] || continue
    printf '%s\n' "$i2c_dev"
    [ ! -r "$i2c_dev/name" ] || cat "$i2c_dev/name"
    [ ! -e "$i2c_dev/of_node" ] || readlink -f "$i2c_dev/of_node"
    [ ! -L "$i2c_dev/driver" ] || readlink -f "$i2c_dev/driver"
done
```

没有 I2C 设备目录，回查控制器与子节点枚举；有目录而无 driver 链接，查匹配、代码是否可用及 probe 返回；已经绑定，再找它注册的 input 或 power_supply 对象。

GT9XX 内建配置为 `y`，因此不应靠 `lsmod` 找它。另一项 `CONFIG_TOUCHSCREEN_GOODIX=m` 也不能替代对实际 driver 的识别。两套代码均能声明 Goodix 身份，但读取的属性和初始化路径不同。

### 10.4.2 模块风扇还包含加载与绑定环节

```sh
# 查看 pwm-fan 代码是否加载，以及 platform 驱动下是否有设备链接。
lsmod | grep -E '^pwm_fan[[:space:]]'
ls -l /sys/bus/platform/drivers/pwm-fan
```

pwm-fan 在当前包中为模块。列表中有 `pwm_fan` 表示代码已加载；platform driver 下的设备链接才把代码与具体节点连接。沿链接查看 `of_node`，再找它对应的 cooling device。代码已加载而没有设备，先查节点匹配与 probe；已绑定而无策略请求，则进入温区关联检查。

显示通过 platform、DSI 与 DRM 等对象衔接，panel 不使用 I2C 地址检查法。其父子关系和子系统接口在[第 06 章](06_显示与背光.md)展开。

### 10.4.3 日志要回到最早失败的资源

```sh
# 搜索相关错误的上下文；这只是入口，不以最后一条日志直接定因。
journalctl -k -b --no-pager | grep -Ei 'goodix|gt9|cw2015|charger|panel|dsi|backlight|pwm|thermal|defer|regulator|pinctrl'
```

过滤结果用于找时间点，随后读该时间点前后的完整消息。后续 I2C 失败可能来自先前的电源错误，GPIO 申请失败可能来自另一个设备的 pinmux 占用。驱动也可能记录错误后继续，因此无报错和 probe 返回都要与后续接口结果一起解释。系统没有 journal 时使用已有内核日志入口。

## 10.5 按接口的数据含义观察运行结果

### 10.5.1 显示输出状态与亮度各自读取

```sh
# 查看显示连接状态、软件使能状态和公布的模式。
for drm_conn in /sys/class/drm/card*-*; do
    [ -r "$drm_conn/status" ] || continue
    printf '%s\n' "$drm_conn"
    cat "$drm_conn/status"
    [ ! -r "$drm_conn/enabled" ] || cat "$drm_conn/enabled"
    [ ! -r "$drm_conn/modes" ] || cat "$drm_conn/modes"
done

# 分别读取请求亮度、报告亮度、最大索引和背光电源状态。
for bl_dev in /sys/class/backlight/*; do
    [ -d "$bl_dev" ] || continue
    for bl_attr in brightness actual_brightness max_brightness bl_power; do
        [ ! -r "$bl_dev/$bl_attr" ] || grep -H . "$bl_dev/$bl_attr"
    done
done
```

| 属性 | 含义 | 对排查的作用 |
| --- | --- | --- |
| connector `status` | 驱动报告的连接状态 | 固定面板可能没有物理热插拔检测；结合拓扑解释 |
| `modes` | 输出公布的候选模式 | 为空时查模式获取和 panel；有列表后再查实际提交 |
| `enabled` | 软件输出关联状态 | disabled 时先查输出选择；enabled 后检查实际内容 |
| `brightness` / `actual_brightness` | 请求索引与驱动报告值 | 与表值、blank 状态和 PWM 对应 |
| `max_brightness` | 最大逻辑索引 | 197 项表对应 196，256 项表对应 255 |

DRM 的 connector 是显示输出对象，候选模式列表与正在扫描的模式是两个信息。`enabled` 的通用实现检查 encoder 关联，详见 [v6.1 DRM sysfs](https://raw.githubusercontent.com/torvalds/linux/v6.1/drivers/gpu/drm/drm_sysfs.c)。若提交的内容本来全黑，肉眼现象也可能类似像素链故障，所以显示检查要使用已知非黑图样和目标输出。

背光软件值描述请求或报告值，光强取决于 PWM、使能、电源与 LED 电路。亮度范围已正确且请求非零却无光时，继续查执行链；有光无图时进入 panel 与像素链。

### 10.5.2 input 帧先于桌面映射

先读 `/proc/bus/input/devices`，按名称、物理路径和 Handlers 找到目标 `eventN`，再用已有的 `evtest /dev/input/eventN` 观察单指按下、移动、抬起和多指切换。

evtest 位于驱动解析与变换之后、桌面映射之前。记录 ABS 范围、是否有 slot、tracking ID、同步边界及释放事件；四角测试比单测中心更能区分轴交换、翻转和缩放。input 结果正确而桌面错位，继续查用户态方向与设备选择；input 已错则返回 CFG、数据解析与驱动变换。原始 I2C 坐标要从解析前诊断取得，不能从 evtest 直接还原。

### 10.5.3 电量属性带着来源、单位和采样时间

```sh
# 将对象名称和属性一起读取，避免把不同电源设备的状态混为一谈。
for ps_dev in /sys/class/power_supply/*; do
    [ -r "$ps_dev/uevent" ] || continue
    printf '%s\n' "$ps_dev"
    cat "$ps_dev/uevent"
done
```

系统可能同时有 CW2015、RK817 和 gpio-charger，对象名称、driver 与 `of_node` 要一起确认。标准电压字段使用 µV，CAPACITY 是百分比，ONLINE 是外部输入逻辑状态，STATUS 则是驱动组合条件后的状态。

[第 08 章](08_电量与外部供电.md)所用公开基线以周期任务更新 CW2015 缓存，属性读取返回最近保存值。因此连续读 sysfs 不会强制立即采样；电压不变时应连同采样周期、I2C 错误与真实负载变化分析。ONLINE 变化而没有充电电流，应转查硬件充电通路。

### 10.5.4 将温区、策略和风扇绑定读成一组

```sh
# 确认温区身份、当前温度和当前采用的策略。
for thermal_zone in /sys/class/thermal/thermal_zone*; do
    [ -d "$thermal_zone" ] || continue
    for thermal_attr in type temp policy; do
        [ ! -r "$thermal_zone/$thermal_attr" ] || grep -H . "$thermal_zone/$thermal_attr"
    done
    for trip_attr in "$thermal_zone"/trip_point_*; do
        [ ! -r "$trip_attr" ] || grep -H . "$trip_attr"
    done
    for thermal_binding in "$thermal_zone"/cdev[0-9]*; do
        [ -L "$thermal_binding" ] || continue
        printf '%s -> %s\n' "$thermal_binding" "$(readlink -f "$thermal_binding")"
        [ ! -r "${thermal_binding}_trip_point" ] || grep -H . "${thermal_binding}_trip_point"
    done
done

# 确认冷却设备身份、当前档位和最大档位。
for cooling_dev in /sys/class/thermal/cooling_device*; do
    [ -d "$cooling_dev" ] || continue
    for cooling_attr in type cur_state max_state; do
        [ ! -r "$cooling_dev/$cooling_attr" ] || grep -H . "$cooling_dev/$cooling_attr"
    done
done
```

thermal 温度以 m°C 表示，`cur_state` 是冷却档位。温区内 `cdev0` 可能指向任意全局 `cooling_deviceN`，要沿符号链接配对；`${thermal_binding}_trip_point` 再把该关系接到同一温区的 trip 编号。[thermal sysfs 接口](https://www.kernel.org/doc/html/v6.1/driver-api/thermal/sysfs-api.html)说明这些文件的对应关系。

例如绑定指向 pwm-fan 且 trip 编号为 N，就继续看 `trip_point_N_type/temp/hyst` 及 `policy`。没有绑定先查 map；有绑定但档位不变查策略与能力；档位变化后继续查 PWM 和物理响应。公开基线的 power_allocator 跳过不具备 power actor 回调的普通 pwm-fan，所以不能仅凭 map 和阈值推断调速，具体条件见第 09 章。

## 10.6 用同一组输入连接软件与物理行为

记录一次结果时保存硬件、软件组合、时间、输入及输出：例如四角触摸的物理位置、input 坐标和桌面命中位置对应成组，或把温度、policy、cur_state、PWM 和实际转动对应成组。这样前后两次比较才使用相同对象。

| 链路 | 有区分力的输入与观察 | 能继续定位的方向 |
| --- | --- | --- |
| 显示 | 已知图样、目标输出、方向、边缘与连续刷新 | 内容提交、模式、panel 和传输 |
| 触摸 | 单指/多指、按下/移动/释放、四角 | 完整帧、生命周期、坐标变换 |
| 电量 | 相同测点电压、负载、更新时间与在线状态 | 单位、分压、缓存、模型和充电电路 |
| 风扇 | 同一温区策略、档位、波形及转动 | 控制请求、PWM、驱动级和负载 |

恢复问题要比较挂起前后同一链路；冷启动问题要保留上电时序。一个场景通过后再扩展环境与负载，能避免在条件不断变化时失去原因。

## 10.7 核心工程问题与深度理解

### 10.7.1 安装包正确、DTBO 也存在，修改为什么仍可能没有生效

产物还要进入当前启动项及最终树。先核对 kernel release 和链接，再找有效启动项及其文件路径，最后比较内核可见属性。这样能区分旧内核、旧产物、错误选择和组合失败。

### 10.7.2 已绑定驱动却没有事件，应继续查哪里

进入设备的运行路径。GT9XX 要区分 IRQ/轮询是否触发、I2C 是否取得完整帧、状态是否允许上报以及 input 是否形成同步帧。绑定只确定由谁处理设备，运行中的通知和采集仍有自己的失败分支。

### 10.7.3 为什么温区 cdev0 不能直接配 cooling_device0

前者是该温区内的绑定序号，后者是全局冷却设备编号。必须沿链接找到对象，并用 trip_point 属性确定控制点；配错设备会把 CPU 降频状态与风扇状态混在一起。

继续阅读：[第 11 章故障排查与验证](11_故障排查与验证.md)。
