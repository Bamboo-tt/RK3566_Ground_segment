# 10 部署生效检查：确认系统实际采用了哪一套配置

前面各章解释了外设应怎样工作。本章把这些机制落实到一个判断：手中的资料，是否真的对应正在运行的那块板和那套系统？检查从身份开始，逐层走到接口与物理效果，避免在错误版本上反复修改参数。

本章所有 Linux 命令均是**目标板已有系统上的后续检查示例，本次没有执行** 。每组命令只读取现有状态；工具不存在或权限不足时记录这一限制，不以空输出推断硬件失败。这里不执行安装、刷机、重启或配置写入。

## 先理解“生效”的五个不同含义

| 证据层 | 它能回答的问题 | 它不能单独证明的事 |
| --- | --- | --- |
| 原始包和源码 | 准备部署的是什么内容？ | 板上是否安装、是否启动它 |
| 包管理与构建状态 | 包是否解包配置？DKMS是否生成相应对象？ | 引导路径是否选择这些结果 |
| 运行内核与最终设备树 | 这次启动执行哪个内核、看到了哪些硬件描述？ | 外设通信与驱动初始化是否成功 |
| 设备绑定与标准接口 | 哪个驱动接管设备、向系统注册了什么能力？ | 物理量、像素或坐标一定正确 |
| 连续物理行为与上层消费 | 对明确输入是否产生正确、可重复结果？ | 超出检查条件的长期、环境或全业务可靠性 |

这个次序来自依赖关系：如果实际运行的还是旧内核，分析新包中的函数没有直接解释力；如果设备树没应用，驱动尚未拿到预期参数；如果原始 input 坐标已正确，就应继续查桌面变换，而不是再改 CFG。

## 第一步：把实物和材料配成一组

记录核心板型号、底板丝印/修订、屏幕型号和实际装配器件，再选择对应原理图。目录中 2025-10-21 的地面站底板与 2025-11-21 的相机底板存在 GPIO 用途差异；文件日期较新不等于本次实物使用它。

软件一侧保留原始 `.deb` 的哈希、基础 DTB 身份、准备启用的 DTBO 名称和来源。两份 overlay 包都称 `radxa-overlays-dkms 0.2.4`，只看包管理记录无法区分它们。当前已读取包的完整哈希在[阅读索引](13_关键资料阅读索引.md)。

**通用原理。** 已安装文件也可能被后续重建或替换；对原始包的哈希只能识别交付文件。还应将实际启用配置与有效设备树对应起来，不能用一个文件的哈希代替全部运行状态。

## 第二步：区分已安装版本与运行版本

在目标板 Linux shell 的任意目录执行：

```sh
# 查看这次启动的内核和发行版，再查看包管理器记录。
uname -r
cat /etc/os-release
dpkg-query -W -f='${Package}\t${Version}\t${Architecture}\t${Status}\n' 'linux-image-*' radxa-overlays-dkms
```

`uname -r` 回答当前内核发行号。`dpkg-query` 回答系统记录的安装包，可以同时列出多个版本；`install ok installed` 表示包管理状态正常，不表示对应内核已被启动。本目录包的预期发行号是 `6.1.84-12-rk2410-nocsf`，这只是比较对象，不是命令应输出的伪造结果。

如果两者不一致，下一步检查实际引导选择，而不是立即重装。若 `/etc/os-release` 与历史记录不同，也应先记录当前平台，避免把 Debian 11 和 Debian 12 的配置路径混用。

## 第三步：确认 overlay 构建结果和选择关系

在目标板 Linux shell 中，仅当已有 DKMS 工具时：

```sh
# 查询各内核的构建安装状态，并查看本次内核的 overlay 安装目标。
dkms status
readlink -f "/usr/lib/linux-image-$(uname -r)/rockchip/overlays"
find -L "/usr/lib/linux-image-$(uname -r)/rockchip/overlays" -maxdepth 1 -type f -name 'aircas-compact-GCS*.dtbo'
```

应核对条目属于哪个内核与架构，并确认实际链接和文件存在。当前包的 `dkms.post_install` 会跳过某些目标目录，故“源码已安装”与“目标内核可找到 DTBO”之间仍可能有缺口。没有文件时先定位 DKMS 对应构建日志及 hook 行为；有文件时进入选择关系检查。

启动配置位置在当前材料中**待确认** 。以下只读取几种常见候选，不能将其中任意一个写成该板唯一正式入口：

```sh
# 在确实存在的候选文件中寻找基础设备树和 overlay 的选择记录。
for boot_cfg in /boot/extlinux/extlinux.conf /boot/uEnv.txt /boot/config.txt; do
    if [ -f "$boot_cfg" ]; then
        grep -HnEi 'fdt|overlay' "$boot_cfg"
    fi
done
```

没有匹配项，只能说明这些候选没给出答案；还需依据实际引导配置、rsetup 生成文件和启动日志查找来源。看到某个插件名，也只是启动意图；下一步必须核对内核实际得到的树。

## 第四步：读取最终设备树，而不只阅读源码

**通用原理。** 运行设备树一般可通过 `/sys/firmware/devicetree/base` 查看。字符串属性常含 NUL 终止符，整数属性是二进制大端数据，不能都当普通文本 `cat` 后凭显示判断。节点没有 `status` 通常不等于禁用，还要检查其父总线与其他依赖。

在目标板 Linux shell 中：

```sh
# 确认内核看到的平台身份，定位触摸和电量计节点。
tr '\0' '\n' < /sys/firmware/devicetree/base/model
tr '\0' '\n' < /sys/firmware/devicetree/base/compatible
find /sys/firmware/devicetree/base -type d \( -name '*@14' -o -name '*@62' \)
```

节点路径取自实际输出，不假定 Linux I2C 总线编号与 DTS 标签编号相同。对找到的节点，核对 `compatible`、`reg`、`status`，并向父节点确认控制器已启用。还要读 supply、GPIO 与尺寸属性，不能只停在“节点找到了”。

若系统已经提供 `dtc`，可以用设备树编译器反向呈现整棵运行树：

```sh
# 只把运行树转换成可阅读文本；不会安装或修改设备树。
dtc -I fs -O dts /sys/firmware/devicetree/base | less
```

这能帮助解析 phandle 引用与最终属性。反编译后的标签不一定与原始源码一致，结构警告也要结合绑定判断，不能把警告总数直接当成故障数量。若系统没有 `dtc`，保留属性原始值或交给主机离线解析，不在此任务补装。

本项目重点看：I2C1 下触摸地址 `0x14`；I2C3 下 CW2015 地址 `0x62`；DSI0 与 VP0 路由；PWM5 背光表长度和默认值；SDMMC0 与 GPIO1_D5；风扇 PWM0、trip 和 cooling map。它们应与所选硬件组合一致。

最终树正确只证明内核看到了描述，不证明每个消费者都理解了属性。两套 GT9XX 恰好展示了相同 compatible 下的属性差异，必须继续检查绑定。

## 第五步：找到真正绑定的设备和驱动

I2C 设备目录名通常包含总线编号和四位地址。这里根据地址筛选候选，再看 `of_node` 与 `driver`，避免把其他总线上的同地址器件认成目标。

```sh
# 在目标板读取候选设备身份、设备树来源与已绑定驱动。
for i2c_dev in /sys/bus/i2c/devices/*-0014 /sys/bus/i2c/devices/*-0062; do
    [ -e "$i2c_dev" ] || continue
    printf '%s\n' "$i2c_dev"
    [ ! -r "$i2c_dev/name" ] || cat "$i2c_dev/name"
    [ ! -e "$i2c_dev/of_node" ] || readlink -f "$i2c_dev/of_node"
    [ ! -L "$i2c_dev/driver" ] || readlink -f "$i2c_dev/driver"
done
```

设备目录存在但没有 `driver` 链接时，优先检查匹配、配置、probe 错误和延迟探测。已有驱动链接时，继续核对它注册的子系统设备。`lsmod` 没有 GT9XX 并不反常：现有包该配置为 `y`，内建驱动不会作为普通已加载模块列在其中。

风扇需要另查模块与 platform 设备。**包内事实。** `CONFIG_SENSORS_PWM_FAN=m`，包中有与内核发行号配套的 `pwm-fan.ko.xz`。若没有对应 cooling device，先确认代码是否加载并绑定，再检查 governor，不能越过模块环节。

```sh
# 在目标板只读模块列表与pwm-fan的platform驱动目录；目录可能尚不存在。
lsmod | grep -E '^pwm_fan[[:space:]]'
ls -l /sys/bus/platform/drivers/pwm-fan
```

模块出现在列表中，只证明代码已加载；驱动目录存在但没有设备链接，也不等于完成绑定。用其中的设备链接回溯 `of_node`，确认它确实对应目标风扇，再进入 cooling device 和 PWM 检查。

在目标板具有日志读取权限时：

```sh
# 只读本次启动的内核消息，寻找初始化和恢复错误的上下文。
journalctl -k -b --no-pager | grep -Ei 'goodix|gt9|cw2015|charger|panel|dsi|backlight|pwm|thermal|defer|regulator|pinctrl'
```

没有 journal 时可读取已有 `dmesg`；没有权限时记录权限问题。不要只截最后一个错误码：例如 GPIO 申请失败可能由前面的 pinmux 冲突引起，regulator 错误可能阻断后面的 I2C 通信。日志中没有错误，也不能代替事件与物理结果。

## 第六步：按子系统检查接口，再检查效果

### 显示和背光分别观察

在目标板 Linux shell 中：

```sh
# 读取 DRM connector 状态和公布的显示模式。
for drm_conn in /sys/class/drm/card*-*; do
    [ -r "$drm_conn/status" ] || continue
    printf '%s\n' "$drm_conn"
    cat "$drm_conn/status"
    [ ! -r "$drm_conn/enabled" ] || cat "$drm_conn/enabled"
    [ ! -r "$drm_conn/modes" ] || cat "$drm_conn/modes"
done

# 分别读取请求亮度、报告亮度、范围与背光电源状态。
for bl_dev in /sys/class/backlight/*; do
    [ -d "$bl_dev" ] || continue
    grep -H . "$bl_dev"/brightness "$bl_dev"/actual_brightness "$bl_dev"/max_brightness "$bl_dev"/bl_power
done
```

某个可选属性不存在不等于整条链路失败。connector/mode 信息支持判断软件显示路径；它不证明排线上有正确波形，也不证明液晶已显示内容。`actual_brightness` 是驱动报告值，不能当作光学测量。亮度范围若为 0～196，应结合 PWM 变体的 197 项表分析，不能默认上层总能写 255。

### 触摸先看原始事件，再看桌面

读取 `/proc/bus/input/devices`，用 Name、物理路径和 Handlers 找到相应 `eventN`，再用系统已有的 `evtest /dev/input/eventN` 观察。`eventN` 是需要替换的实际编号，不能跨启动固定假设。完整命令和事件含义见[触摸章](07_触摸与input.md)。

确认能力是否含 slot、tracking ID，观察按下、移动、抬起与同步帧。原始事件正确而桌面位置错误时，转向显示旋转、桌面变换与消费者选择。原始事件已错误时，留在 CFG、驱动变换和数据完整性层。

### 电源与温控读数需要带单位和关系

在目标板 Linux shell 中：

```sh
# 查看实际注册的供电对象及各自暴露的属性。
for ps_dev in /sys/class/power_supply/*; do
    [ -r "$ps_dev/uevent" ] || continue
    printf '%s\n' "$ps_dev"
    cat "$ps_dev/uevent"
done

# 查看各温区的身份、当前温度与实际策略。
for thermal_zone in /sys/class/thermal/thermal_zone*; do
    [ -d "$thermal_zone" ] || continue
    grep -H . "$thermal_zone"/type "$thermal_zone"/temp "$thermal_zone"/policy
done

# 查看冷却设备的身份和当前档位。
for cooling_dev in /sys/class/thermal/cooling_device*; do
    [ -d "$cooling_dev" ] || continue
    grep -H . "$cooling_dev"/type "$cooling_dev"/cur_state "$cooling_dev"/max_state
done
```

供电对象必须先用身份区分 CW2015、外部输入与其他电池驱动。标准电压字段通常以 µV 表达，thermal 温度通常为 m°C，档位则是离散状态；实际字段应结合绑定驱动和接口文档解释。不能把外部输入 `ONLINE=1` 等同于电池正在接受充电电流，也不能把 `cur_state=2` 直接解释为某个实测 RPM。

温控还需要读取对应 `trip_point_*` 属性和 `cdev*` 绑定，确认所看的风扇确实连接到该 zone。编译默认 governor 不代替当前 `policy`；即使当前策略名称一致，也还要确认它能操作这个冷却设备。详见[温控与风扇](09_温控与风扇.md)。

## 把检查结果写成可以复核的证据

建议每次记录包含：硬件对象、软件组合、检查时间、输入条件、原始输出、判断和剩余问题。例：“某内核、某设备树下，指定 input 节点在四角操作时产生对应事件”，比“触摸 OK”更可复用。

| 后续验证 | 能证明 | 仍不能证明 |
| --- | --- | --- |
| 检查内核、包、最终设备树和驱动绑定 | 测试对象与资料的对应关系 | 每个外设物理工作正确 |
| 显示固定图样并确认方向、边缘及连续刷新 | 当前模式下图像链路可用 | 所有面板温度与供电条件下可靠 |
| 单指/多指按下移动释放，核对原始事件与桌面 | 输入协议、坐标和消费者的基本关系 | 长时间抗干扰与全部手势场景 |
| 对照独立电压测量及外部输入状态 | 当前读数单位/量程和在线检测极性 | profile适用性、SOC精度及充电控制策略 |
| 核实实际电芯型号并逐字节比对profile来源 | 模型数据与所声称电池对象的对应关系 | 实际使用条件下的SOC准确性 |
| 对照温度、policy、cooling state、PWM与风扇响应 | 选定条件下冷却链是否实际接通 | 极端负载散热能力与寿命 |

这些是待执行步骤，没有预填 PASS。需要物理测量的地方应记录仪器、测点和负载条件；仅仅读取软件接口不能替代电路结果。

## 自查与回答要点

1. **`dpkg-query` 显示正确版本，为什么还查 `uname -r`？** 包管理记录与本次启动选择不是同一状态。
2. **为什么直接查看运行设备树比仅比较源码更接近实情？** 它包含这次启动实际交给内核的组合结果；但属性是否被驱动消费仍需进一步确认。
3. **设备绑定成功为什么还可能不工作？** probe 的错误处理可能不完整；运行时供电、协议、恢复和消费者还可能失败。
4. **日志无报错，怎样继续判断？** 给出明确的物理输入，观察标准接口和实际效果是否对应；日志沉默不是成功判据。
5. **检查没有结果时是否立即重装？** 先确认路径、权限、工具和版本，再定位缺失层级；盲目重装会破坏原始状态且不一定触及原因。
