# 11 故障排查与验证

```text
带版本与触发条件的现象
    -> 选择涉及的正常链路
    -> 找到最早缺失的结果
    -> 一项能区分原因的观察
       +-- 前一级没有交付 -> 查前置资源、输入与错误返回
       +-- 前一级已交付   -> 查本级处理及下一级消费
    -> 在相同条件下复查原因与结果
```

定位入口：[产品 overlay](../../设备树包/aircas-compact-GCS_overlay.dts)、[IO DTS](../../src/rk3566-radxa-cm3-io.dts)、两套 GT9XX 的采集与上报函数，以及第 06～09 章定位的公开 BSP 实现。第 10 章提供运行对象与只读命令，本章用具体症状决定该取哪项信息。

## 11.1 先让现象带上条件

“屏幕不好用”应拆成背光不亮、背光亮却无图、颜色异常或恢复后黑屏；“触摸不准”应拆成固定翻转、四角偏移、多指错报或抬起残留。不同现象落在不同的处理环节，检查对象随之改变。

先固定底板、屏幕、运行内核、最终设备树与驱动分支，再说明冷启动、持续运行还是挂起恢复触发了现象。已有 input 正常帧，就从坐标映射继续；连设备对象都没有，就从树与总线枚举返回。无需每次从最底层重查，也不要用另一套驱动的风险直接解释当前设备。

每项观察都要能改变判断：结果 A 出现时转向一段，结果 B 出现时转向另一段。这样一次只查有区分力的位置，避免“看日志、改配置、重启”循环。

## 11.2 背光亮但无图像

### 11.2.1 先区分照明、内容提交与面板状态

背光已经发光，说明照明支路有输出。面板供电、复位、初始化命令与像素输出仍是独立路径。若完全不发光，则先按第 10 章找 backlight 对象、亮度请求和 blank 状态，再查 PWM5、GPIO4_B3 与背光电源。

对有背光的黑屏，先读取目标 connector 的 `status`、`enabled`、`modes`。输出 disabled 时查桌面输出选择与显示提交；有模式且输出已用时，再用已知非黑图样区分“提交的内容就是黑色”与“内容没有到达面板”。固定面板可能始终报告 connected，这个状态不检查每根排线。

| 观察位置 | 结果一及下一步 | 结果二及下一步 |
| --- | --- | --- |
| 软件输出关联与图样提交 | 输出未使用或图样到另一输出：查用户态输出选择 | 目标输出已有正确提交：查面板及像素通道 |
| 面板供电与复位 | 电压或物理时序错误：沿 regulator、GPIO 与电路查 | 工作条件成立：查初始化命令和 DSI |
| 最终 route、endpoint、VP 选择 | 链路不对应：查基础树与 overlay 组合 | 描述一致：查模式、命令返回及传输 |
| panel 命令与 DSI 日志 | 写入报错：定位电源、reset、Host/PHY 与器件 | 命令发送完成：继续比较等待和像素参数 |

### 11.2.2 用资源竞争和命令顺序解释具体分支

当前本地 IO DTS 启用 SDMMC0，其 bus4 pinctrl 使用 GPIO1_D5；产品 overlay 又用 GPIO1_D5 控制面板供电。包内基础 DTB 禁用 SDMMC0。若采用本地重新构建的基础树并叠加此屏幕配置，就要检查最终树与 pinctrl 申请是否发生占用冲突；采用包内禁用状态时则沿其他条件继续。

[7 英寸厂商表](../../阿美林-1000nit-7inch/初始化序列/BOE_7WX_ILI9881C_V04_20210507.txt)要求 `0x11` 退出睡眠后等 120 ms，再发 `0x29`。当前 overlay 末段却是 `15 00 02 11 00`、`15 78 02 29 00`。[公开配套基线的 panel-simple.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/panel/panel-simple.c)在发送当前记录后执行延时，因此这组记录把等待放在 `0x29` 后。

这为黑屏或启动不稳定提供了一个具体候选：退出睡眠到开显示之间缺少厂商要求的间隔。要把它与当前现象对应，确认运行树使用这一序列，并比较实际命令和电源时序。生命周期另一阶段的 `enable-delay-ms=120` 不会移进两条命令之间。该解析路径对命令发送错误还可能只记日志继续，因此 panel 的后续状态要与发送返回一起读。

已有图像而出现颜色或边缘错误时，优先比较 RGB888、lane 数、像素时钟和行场参数；本 7 英寸配置的 854×1314 总周期、67.3 MHz 对应约 59.974 Hz。偶发花屏再结合供电与传输质量。只在恢复后失败时，则比较挂起前后的电源、reset 和初始化命令，保留冷启动正常这个区分条件。

## 11.3 亮度范围或变化方向异常

先把三个量分开：上层写索引，驱动查表得到控制值，PWM 与电路决定照明。相邻索引输出不变，可能是表值重复；表值变化而灯不变，则继续查 PWM 和负载电路。

[普通包](../../debs/radxa-overlays-dkms_0.2.4_all.deb)包含 256 项表，[PWM 包](../../debs/radxa-overlays-dkms_pwm.deb)的 `usr/src/radxa-overlays-0.2.4/arch/arm64/boot/dts/rockchip/overlays/aircas-compact-GCS-pwm.dts` 使用 `[0,60…255]` 共 197 项。默认索引都为 200，而变体最大索引是 196。公开配套 `pwm_bl.c` 警告后钳到 196，查表得到 255，随后请求最大 PWM 有效时间。按[第 06 章](06_显示与背光.md)的反相 PWM、U5 和 SY7201 接法，这一末档可使 EN 长时间为低，表现为暗屏。范围错误已被钳制，后续现象要沿实际波形与电路解释。

先读最终表和 `max_brightness` 区分有效范围，再检查启动默认值、blank 状态和使能。若请求正常但亮度方向相反，沿以下位置比较同一组低/高请求：

```text
索引 -> 表值 -> PWM 有效时间 -> SoC 引脚的高/低电平比例
     -> 光耦及后级控制端 -> LED 电流 -> 可见亮度
```

PWM 极性、GPIO 有效极性和外部反相电路分别作用于不同位置。有表值变化却没有引脚波形变化，查 PWM/pinctrl；波形变化而后级不变，查光耦与使能；后级方向相反，再看电路怎样响应控制端。`actual_brightness` 是软件报告，不是光强传感器。

## 11.4 触摸没有事件、中断异常或坐标残留

### 11.4.1 设备存在后再区分通知与采集

按第 10 章先找 I2C client、`of_node`、driver 和 input 设备。client 缺失查父控制器与子节点；driver 缺失查匹配与 probe；input 已有才进入事件路径。GT9XX 的 INT 在复位时还用于地址选择，RST/INT 时序不正确可能让器件实际地址与软件 `0x14` 不同。

| 现象 | 最有区分力的观察 | 下一步 |
| --- | --- | --- |
| 无事件，IRQ 计数不变 | 确认当前走 IRQ 还是轮询，再看 INT 与屏蔽状态 | 轮询就查 timer/work；IRQ 则查线、触发类型、禁用状态 |
| IRQ 增长却无 input 帧 | 对应采集函数的 I2C 返回、ready 位、触点数和工作标志 | 读失败查通信；读成功查校验、门控和上报 |
| IRQ 持续触发 | INT 是否一直有效，状态确认写是否成功，IRQ 类型是否匹配 | 区分未清器件状态、触发配置错误与线路干扰 |
| evdev 有完整帧，桌面不响应 | 当前会话使用的输入设备与映射 | 转向用户态消费者 |

操作前后比较 `/proc/interrupts` 中实际登记的中断，不固定 IRQ 编号。计数表示 CPU 收到通知，坐标仍要由 I2C 取得。共享 IRQ 还需要确定通知来源。

旧 V2.2 的 IRQ 回调屏蔽本设备 IRQ 后投递 `goodix_wq`，正常尾部确认器件状态再恢复 IRQ；V2.8.7 直接在 IRQ 线程采集，确认时机和错误出口不同。故障应沿当前分支检查，不能把“禁用—读取—确认—使能”当成两套代码共有的一段理想伪代码。完整顺序见[第 07 章](07_触摸与input.md)。

### 11.4.2 用同一个触点比较三个坐标位置

| 位置 | 观察方式 | 分辨的问题 |
| --- | --- | --- |
| I2C 帧坐标字段 | 解析前诊断记录或可归属的总线采集 | CFG 与控制器实际输出 |
| input 坐标及 ABS 范围 | evtest | 驱动解析、交换、翻转后的结果 |
| 桌面命中位置 | 同次操作与用户态变换配置 | 输出方向、缩放及映射 |

先按 input 声明范围确定预期原点，比较中心和四角。中心在多种翻转下仍不变，四角才能把交换、反向和缩放区别开。不同量程先比较归一化相对位置，不直接把触摸数值当作显示像素。

input 正确、桌面错误就查用户态；input 已错再回到 CFG 和驱动。旧版 probe 虽读 `max-x/max-y`，将它们赋给 `abs_x_max/abs_y_max` 的代码却被注释，因此改属性不一定改变 input 范围。范围的实际来源要沿 `gtp_init_panel()`、`gtp_get_info()` 与输入注册继续追踪。

### 11.4.3 多指和抬起异常先查完整帧与状态保存

旧版 `gtp_i2c_read()` 的完整成功是返回 2 条消息，不是 2 字节；重试耗尽后可返回短传输值，而部分调用者只判断负数。多点续读还存在未检查返回值便复制数据的路径。若只在多指时出现异常，先对照续读是否完整，再查解析偏移和触点 ID。

随后区分 Type A 与 Type B。Type A 依靠逐点同步及帧边界组织接触，Type B 保存各 slot 的生命周期并释放消失 ID。旧分支由 `CONFIG_CHROME_PLATFORMS` 控制路径；V2.8.7 使用自己的配置。读取失败时原有 input 状态可能保留到下一次有效帧，恢复函数清标志也不会自动补出所有释放事件。

V2.8.7 把采样点存入 `points[ID]`，其 Type A 报告函数却按连续位置读取且没有检查相应 status。单点 ID 非零时，就要沿真实布局比较它报告的是哪一项。这个问题与旧版 slot 循环对记录顺序的假设属于不同分支，详见第 07 章的具体例子。

### 11.4.4 卡顿与恢复按执行上下文检查

旧路径在 IRQ 后还有一次 workqueue 排队，I2C 重试与复位也会延长处理；V2.8.7 IRQ 线程直接采集。其无 IRQ 路径从普通 hrtimer 回调直接进入含可睡眠 I2C 和分配操作的函数，只有运行这条分支时才属于当前候选原因。

只在恢复后卡住时，比较工作标志、INT 地址选择、I2C 应答和首个有效 input 帧。V2.8.7 恢复失败后仍可重新放行 work，因此应以通信及完整事件恢复定位，而非停在标志已清除处。

## 11.5 电量不更新或外部电源状态错误

### 11.5.1 先定位对象、单位和缓存年龄

CW2015、RK817 与 gpio-charger 可以同时存在。用 driver 和 `of_node` 确认属性来源，再比较电压 µV、SOC 百分比和 ONLINE。电量计对象缺失先查 I2C3、0x62 与 probe；对象存在但电压约差一倍，先查分压与 `dual-cell`，不要立即改设计容量。

公开基线中 CW2015 的工作任务更新缓存，当前 overlay 指定每轮结束后 5000 ms 再排队。读取 `voltage_now` 不触发新采样。MODE 读失败会跳过本轮；单字段读取失败则保留该字段旧值。因此应把电压停住与对应时间的 I2C 日志、负载变化一起看，区分正常缓慢变化、周期任务失败和旧缓存。

单独电压变化不置 `battery_changed`，上层只等通知时可能刷新较慢；SOC、连接状态或推导 STATUS 变化才触发这份驱动的通知。缩短用户态读取间隔和修复后台采样是不同措施。

### 11.5.2 电压合理但 SOC 异常时追模型和参数用途

当前 64 字节 profile 对应构建记录的远东 FEB 6 Ah 数据，设计容量为 6000000 µAh。profile 在初始化时写入芯片 BATINFO，SOC 由芯片报告再经驱动抖动抑制；设计容量参与 `charge_now`、估算 `current_now` 等派生量。只改容量不会重新校准 SOC，也不会改变硬件充电电流。

先核对实装电芯、模型写入和芯片状态，再看 SOC 异常恢复日志。`cellwise,dual-cell` 由 bool API 按存在性读取，`<0>` 仍然为真。`charge_counter` 在此基线中实际记录插电次数，若上层按 µAh 解释，应先修正对接口语义的判断。完整换算在[第 08 章](08_电量与外部供电.md)。

### 11.5.3 ONLINE、STATUS 和充电电流分别判断

若插拔时 ONLINE 方向错误，先核对当前底板 GPIO3_B4 的用途，再沿光耦、物理电平与 GPIO 有效极性检查。物理检测端不变查电路，端电平正确而 ONLINE 错误查属性与 GPIO 对象。

gpio-charger 的 IRQ 可立即通知输入变化，CW2015 则等自己的周期任务查询供电关系，短暂出现 ONLINE=1、STATUS 仍为 Discharging 有明确调度原因。超过正常更新周期仍不同步，再查 `power-supplies` 引用、MODE 读取及采样工作。

ONLINE 和 Charging 均正常却没有充电电流时，转查 TP5100 与实际取电、充电通路。该 CW2015 状态由 ONLINE 和 SOC 推导，当前节点没有接入硬件 CHRG#/STDBY#，软件 Charging 不承担电流测量。

## 11.6 风扇档位或物理响应不符合预期

### 11.6.1 对象齐全后检查策略能力

无 SoC 温区先查 TSADC；温区正常而无风扇 cooling device，查 `pwm_fan` 模块、PWM 资源与 probe。两端都存在时，沿温区 `cdev*` 链接找到同一个风扇，再读 trip 编号和实际 policy。

包内默认 `power_allocator`，而公开基线的普通 pwm-fan 只有状态回调，没有功率模型所需的 power actor 回调。策略分配时会跳过它；在已有非 power actor 绑定上绑定该策略还可能返回 `-EINVAL`。所以温度跨过 60℃而档位不变，应先看策略到设备接口，而非反复调阈值。风扇持续高速还可能来自 probe 的最大初值。

若实际 policy 是 step_wise，状态还与趋势及前次状态有关；此实现的调档判断不读取 hysteresis，不能按“60 开、58 关”预期。第 09 章按同一组阈值演算升降温过程。

### 11.6.2 档位变化后顺着控制输出检查

| 已有结果 | 下一观察 | 判断方向 |
| --- | --- | --- |
| cur_state 变化 | hwmon `pwm1`、`pwm1_enable` 和 PWM 请求 | 区分状态请求与输出被关闭 |
| PWM 请求变化 | GPIO0_C7 的 PWM0_M1 波形 | 无变化查 pinmux、资源与驱动错误 |
| 栅极波形变化 | 风扇端电压及起转 | 电压不足查功率级；电压正常查负载和启动条件 |
| 风扇确实转动 | 相近负载的温度趋势 | 查散热接触、气流与总散热能力 |

状态 2 查表得到 128，10000 ns 周期下驱动请求 5020 ns 有效时间，约 50.2%；这不是已测半速。当前节点没有测速 IRQ，接口不提供由该配置建立的 RPM 反馈。

旧底板第 8 页把 AO3400 N-MOS 放在 +5 V 与二线风扇正端之间，栅极由 PWM 驱动。若按图装配且只有约 3.3 V 栅极高电平，源极上升会压低 VGS，无法形成理想的 5 V 高侧导通。这时提高档位不会补出足够栅极电压，应同时比较栅极、源极和器件连接，不能只看到 PWM 就认定风扇供电完整。

## 11.7 包已安装但修改没生效

从现象反向选择最短检查链：

```text
uname -r 与目标不符 -> 启动项选择
内核正确、最终属性仍旧 -> DTB/DTBO 文件、链接、有效启动项和合并
属性正确、驱动行为仍旧 -> 属性消费者、编译分支及实际绑定实现
接口结果已改变、上层未改变 -> 消费者、缓存与映射
```

两包同名同版本时比较哈希和具体插件名；DTBO 按旧内核构建时比较 DKMS 的 release；已有真实 overlays 目录时检查安装脚本跳过条件。原包、系统文件和本次启动分别是可比较对象，顺着同一文件追踪才能把部署问题与器件问题分开。

取得候选原因后，保留相同硬件与输入条件，比较引发差异的那一个配置或状态。一次同时更换驱动、插件和屏幕，即使现象消失也难以确定原因。

## 11.8 核心工程问题与深度理解

### 11.8.1 背光亮、connector 有模式，下一项最有价值的检查是什么

先确认目标输出被实际使用并提交了已知非黑内容，再比较面板电源、复位、命令与像素通路。模式列表给出候选能力，照明给出另一条链的结果，两者之间仍有内容提交和面板状态。

### 11.8.2 电池属性可读而停住，先改轮询周期是否合适

应先确认最近更新为何没有提交。I2C 或 MODE 失败会保留旧缓存，缩短周期只会更频繁失败；若采样正常而上层只等通知，则需读通知条件。先定位采集、缓存还是消费，才能选择修改位置。

### 11.8.3 温度升高、风扇高速转，怎样判断策略是否真的在调速

同时比较 policy、绑定、温度趋势与 cur_state 的变化。风扇可能一直保持 probe 初值；当前 power_allocator 与普通 pwm-fan 的接口也不配套。只有策略请求确实改变并经过 PWM 与负载产生响应，才形成完整控制链。
