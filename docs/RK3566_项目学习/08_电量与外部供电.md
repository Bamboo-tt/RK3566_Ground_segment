# 08 电量与外部供电：从电池测量到上层状态

```text
运行时的数据流
电池总电压 -> R44/R37 分压 -> CW2015 的 VCELL / SOC / RRT 寄存器
  |
  v  I2C3，地址 0x62
cw_bat_work 周期任务：读取寄存器并转换数值
  |
  +-- 查询上游 ONLINE <--- gpio-charger <--- GPIO3_B4 <--- 光耦 <--- 外部 9 V
  |
  v
电池缓存：SOC、电压、供电连接状态、推导的充电状态
  |
  +-- 属性读取 -> power_supply / sysfs -> 系统电源服务或应用
  |
  +-- SOC / 供电连接 / 状态发生变化 -> power_supply_changed -> 变化通知

gpio-charger 自身的检测 IRQ -> power_supply_changed -> 外部供电变化通知

实际充电的能量流：9 V 输入 -> TP5100 及外围电路 -> 电池
CH224K 经 CC 请求输入电压，设置取电条件。
```

核心位置：[产品 overlay](../../设备树包/aircas-compact-GCS_overlay.dts) 的 `battery`、`mains_charger`、`i2c3/cw2015@62`；[2025-10-21 底板图](../../原理图/SCH_RK3566底板V2_2025-10-21.pdf) 第 4 页；[构建记录](../../RADXA%20CM3地面站编译.docx) 的电池建模与内核版本段落。驱动分析采用该记录指定、公开 `6.1.84-12` 发布版使用的 [Radxa 基线 `3bbac32`](https://github.com/radxa/kernel/tree/3bbac32c942f4d98fc87bde3852f185dce56ff56)：主要文件为 [cw2015_battery.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/power/supply/cw2015_battery.c) 和 [gpio-charger.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/power/supply/gpio-charger.c)。构建记录随后还有本地适配，以下逐函数解释对应这份公开基线。

显示与触摸让人能够操作设备，电源信息则回答“还剩多少电、是否接入外部电源”。这两个答案来自不同的硬件和驱动。先分清测量、估算、检测与充电通路，才能解释为什么电池图标变化与真实充电电流并不总是同步。

## 8.1 电池检测支路先把总电压送到电量计

旧底板第 4 页的 U8 是 CW2015。R44 从 `VCC_PB+` 接到 CELL，R37 从 CELL 接地，两者均为 200 kΩ。忽略芯片输入负载时：

```text
VCELL = V电池 × R37 / (R44 + R37) = V电池 / 2
示例：两节串联电池总电压 7.6 V -> CELL 检测端约 3.8 V
```

分压解决的是检测量程。芯片本身另由 `VCC3.3CW` 经 R45 供电；SDA/SCL 经串联电阻接 GPIO1_A0/A1，并上拉到 `VCC3.3CW`。所以 VDD 正常、CELL 比例正确和 I2C 应答分别对应供电、测量、通信三个条件。分压电阻装错时，I2C 仍可能读写正常，只是电压和电量估计的输入已经失真。

CW2015 的 SOC 是 State of Charge，即剩余电量百分比。它结合电池模型和自身测量估计 SOC，Linux 驱动读取这一结果，再做少量抑制抖动与异常恢复；驱动没有用“当前电压除以满电电压”生成百分比。两节串联使总电压相加，同一支路的 Ah 容量不因此翻倍。

图中的 `ALRT#` 接 GPIO3_A1，但产品节点没有配置这条中断。当前软件采集入口是周期任务，不能把这根已有硬件线接进运行拓扑冒充采样 IRQ。

## 8.2 设备树把器件、模型与上游电源交给 probe

### 8.2.1 三种描述分别交给不同消费者

[overlay](../../设备树包/aircas-compact-GCS_overlay.dts) 的以下摘录保留了电池与供电关系，64 字节模型仅在此处省略：

```dts
battery: battery {
    compatible = "simple-battery";
    charge-full-design-microamp-hours = <6000000>; // 设计容量，单位 µAh
};

mains_charger: dc-charger {
    compatible = "gpio-charger";
    charger-type = "mains";                       // power_supply 的供电类别
    gpios = <&gpio3 RK_PB4 GPIO_ACTIVE_HIGH>;      // 检测输入，高电平为在线
    pinctrl-names = "default";
    pinctrl-0 = <&dc_det_pin>;
};

&i2c3 {
    status = "okay";
    pinctrl-0 = <&i2c3m0_xfer>;                   // SDA/SCL 复用到 M0 引脚组
    #address-cells = <1>;
    #size-cells = <0>;
    cw2015: cw2015@62 {
        status = "okay";
        compatible = "cellwise,cw2015";
        reg = <0x62>;                            // I2C 从地址
        // 此处省略原文件的 64 字节 cellwise,battery-profile
        cellwise,dual-cell = <1>;                // 此驱动按“属性存在”读取
        cellwise,monitor-interval-ms = <5000>;   // 周期任务重新排队的延时
        monitored-battery = <&battery>;         // 静态电池参数
        power-supplies = <&mains_charger>;       // 查询上游 ONLINE 的关系
    };
};
```

`simple-battery` 是静态数据，不是采样器。CW2015 注册自己的 `power_supply` 后，调用 `power_supply_get_battery_info()`，由框架沿 `monitored-battery` 取出 `charge_full_design_uah`。另一条 `power-supplies` 引用让 `power_supply_am_i_supplied()` 找到 `dc-charger` 并读取它的 ONLINE。这两条 phandle 的目的不同，交换或漏掉任何一条都会影响不同的结果。

64 字节 profile 交给 `cw2015_parse_properties()`。长度不是 64 时返回 `-EINVAL`；没有该属性时保留芯片原有配置。构建记录中同时保存了两套模型：2S 4000 mAh 以 `15 7E 9E 47 26 14` 开头，远东 FEB 6AH 以 `15 7E 90 3A 19 15` 开头。当前 overlay 的全部 64 字节与后者一致，和 6000000 µAh 的设计容量属于同一组记录。profile 要随实际电芯选择，不能仅靠修改容量字段适配另一种电池。

`cellwise,dual-cell` 在这份实现中由 `device_property_read_bool()` 读取。它检查属性是否存在，因此写成 `<0>` 仍会启用双节换算；要关闭此分支，应让最终设备树没有该属性。监测间隔由 `device_property_read_u32()` 读取，缺省为 8000 ms，当前配置覆盖为 5000 ms。该函数没有拒绝零值，而后面的恢复计数会除以这个间隔，因此它必须大于零。

### 8.2.2 初始化先配芯片，再建立持续采样

I2C3 控制器建立后，内核根据子节点创建 `i2c_client`，`cellwise,cw2015` 匹配 `cw2015_of_match`，进入 `cw_bat_probe()`。正常顺序是：分配状态结构并令初始 SOC 为 1；解析上述属性；建立 8 位地址、8 位数值的 I2C regmap；调用 `cw_init()` 配置芯片；注册 `cw2015-battery`；取得静态电池信息；创建名为 `rk_battery` 的单线程工作队列，首次延迟约 10 ms 排队采样。

`cw_init()` 将芯片置于正常模式并读取 CONFIG。如果配置更新标志未设置，就上传 profile；标志已设置时，读回 BATINFO 的 64 字节，与 DTS 中的模型逐字节比较，有差异再替换。`cw_update_profile()` 从 `0x10` 写入模型、设置更新标志、通过 MODE 触发重启，等待 20 ms 后清除重启位，随后轮询 SOC，等待它进入 0～100 的有效范围，超时返回错误。profile 在这里参与芯片初始化，不是每轮采样都下载一遍。

[交付内核包](../../debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb) 的 `boot/config-6.1.84-12-rk2410-nocsf` 配置 `CONFIG_BATTERY_CW2015=y`、`CONFIG_CHARGER_GPIO=y`；其基础 DTB 中 I2C3 为 disabled。驱动内建解决代码是否进入内核，overlay 开启总线并声明器件解决设备从哪里来。接口缺失时，应先检查最终树、I2C client 与 probe，设计容量不参与这几步。

## 8.3 周期任务怎样更新电压、SOC 与状态

### 8.3.1 三次寄存器读数变成整包电压

`cw_read_word()` 从寄存器连续读两字节，并用 `be16_to_cpu()` 按高字节在前还原数值。`cw_get_voltage()` 连续读三次 VCELL，求整数平均，再把 ADC 码换成 mV。下面是该函数核心的等价整理，省略调试打印：

```c
u32 avg = 0;
for (i = 0; i < 3; i++) {
    ret = cw_read_word(cw_bat, CW2015_REG_VCELL, &reg_val);
    if (ret)
        return ret;                 // 任一次失败，本轮不提交新的电压
    avg += reg_val;
}
avg /= 3;                           // 先在 ADC 码的单位下求均值
voltage_mv = avg * 312 / 1024;        // 每码约 0.305 mV，整数换算
if (cw_bat->dual_cell)
    voltage_mv *= 2;                 // 对应本板 1:2 分压，还原整包电压
return voltage_mv;
```

例如三次均值为 12472，整数运算得到 `12472 × 312 / 1024 = 3800 mV`，双节分支得到 7600 mV。对外读取 `voltage_now` 时再乘 1000，得到 7600000 µV。这是沿同一份数据的换算，误差来源包括电阻比例、ADC 和整数近似。提高采样频率只能缩短刷新等待，不能修复比例错误。

### 8.3.2 单线程采样保存结果，属性读取使用缓存

I2C 访问可能等待或睡眠，因此采集放在工作队列上下文。`cw_bat_work()` 每轮先读 MODE，检查芯片是否意外进入睡眠；随后按下图更新，最后才安排下一轮：

```text
读取 MODE 成功
    -> 必要时尝试唤醒/重置，最多 5 次
    -> cw_update_soc
    -> cw_update_voltage
    -> cw_update_charge_status：查询上游 ONLINE
    -> cw_update_status：用 ONLINE 与 SOC 推导状态
    -> cw_update_time_to_empty
    -> 必要时 power_supply_changed
    -> 本轮结束后延迟 5000 ms 再排队
```

所以 5000 ms 是“本轮完成到下轮具备调度条件”的间隔，实际开始间隔还包括传输、重试和调度时间。`cw_battery_get_property()` 不直接发 I2C 请求，它返回状态结构中最近保存的值。连续 `cat voltage_now` 不会加速采样，多个属性也没有一个锁保护的整帧快照，跨文件读取可能落在同一轮更新的不同位置。

SOC 读取失败时 `cw_update_soc()` 记录错误并保留旧值；电压和剩余时间也分别保留自己的上一次成功结果。MODE 读取失败则跳过这一轮全部更新，但仍重新排队。于是一次读取 sysfs 成功可以同时伴随后台通信失败。例如 0 秒成功、5 秒电压读取失败，6 秒读出的电压仍可能来自 0 秒；缓存没有暴露采样时间戳，需要结合日志与受控变化判断时效。

`battery_changed` 由 SOC 变化、外部供电连接变化或推导 STATUS 变化置位。只有这些变化会触发本驱动的 `power_supply_changed()`；单独电压或剩余时间变化不置位。框架通知用户空间“属性可能变化”，上层随后读取；这和按固定频率主动读取属性是两种更新方式。

### 8.3.3 电量抖动抑制与恢复也有明确条件

`cw_get_soc()` 读取 SOC 整数部分。充电时，较上次下降 1～2 个百分点的结果被保留为旧值；放电时，上升 1～2 个百分点也被抑制。达到 3 个百分点时不再被这条判断拦住。这样能减小负载引起的显示抖动，也会暂时隐藏小幅反向变化。

SOC 大于 100 进入无效数据计数；当前 5 秒配置下，计数超过 `40000 / 5000 = 8`，即第 9 次连续无效报告，尝试复位电量计。状态为 CHARGING 且 SOC 长期完全相同时，超过 `1800000 / 5000 = 360` 次才尝试恢复。这是按采样次数估计时长，并非独立的精确秒表。普通 I2C 读失败直接返回错误，不计入这个“数值大于 100”的计数器。

复位函数依次写睡眠、等待 20 ms、写正常模式，再重新执行 `cw_init()`。这份实现有具体的恢复限制：SOC 异常路径忽略复位返回值并清零计数，工作函数在 5 次唤醒均失败后也继续尝试采样。因此看到“尝试恢复”的日志，还要对应下一笔成功读数；反复复位无法修好断线或错误模型。

挂起时 `cancel_delayed_work_sync()` 等待在途采样退出，恢复时立即重新排队。设备托管的 delayed-work 清理负责取消工作，但这份基线没有释放 `create_singlethread_workqueue()` 创建的私有队列，也没有处理 `devm_delayed_work_autocancel()` 的失败返回；反复解绑及资源紧张下的清理不完整。这个问题属于工作队列寿命，不改变正常轮询与属性缓存的关系。

## 8.4 设计容量怎样进入标准属性

同一个 `power_supply` 目录中混合了测量、估算和派生量。根据 `cw_battery_get_property()`，应这样读它们：

| 属性 | 单位或类型 | 此版本的数据来源 |
| --- | --- | --- |
| `capacity` | % | 芯片 SOC，经驱动抖动抑制后的缓存 |
| `voltage_now` | µV | 三次 VCELL 平均、换算、双节补偿后的缓存 |
| `status` | Discharging / Charging / Full | 上游 ONLINE 与 SOC 共同推导 |
| `present` | 0 / 1 | 缓存电压是否非零，没有独立电池在位检测 |
| `charge_full_design`、`charge_full` | µAh | 都返回 `charge_full_design_uah`，后者没有学习老化容量 |
| `charge_now` | µAh | 设计容量 × SOC / 100 |
| `time_to_empty_now` | s | RRT_ALERT 低 13 位的分钟数 × 60；仅放电且数值有效时输出 |
| `current_now` | µA | 设计容量、SOC 与剩余分钟数估算，非电流传感器读数 |

沿用 6000000 µAh、SOC 为 60% 的示例，`charge_now = 3600000 µAh`。若芯片报告剩余 120 分钟，驱动估算 `current_now = 60 × 3600000 / 120 = 1800000 µA`，即 1.8 A。修改设计容量会改变这些派生量，但不会改写芯片已报告的 SOC，也不会改变 TP5100 的充电电流。

当前 `simple-battery` 没有满电电压属性。这份 CW2015 驱动也没有使用 `voltage_max_design_uv` 或 `constant_charge_voltage_max_uv` 做 SOC 比例换算或设置充电终止电压。充电电压由硬件充电电路与电池方案决定；芯片的估算特性则由 profile 表达。

还有一个接口语义缺陷需要单独识别：该驱动把检测到的插电次数 `charge_count` 放进 `CHARGE_COUNTER`。标准 `charge_counter` 应表达以 µAh 为单位的电荷量，这里返回的却是事件次数。消费这一属性的程序若按电荷量解释会得到错误含义；它也不是电池的充放电循环寿命计数。[power_supply 单位约定](https://www.kernel.org/doc/html/v6.1/power/power_supply_class.html)

## 8.5 外部电源检测怎样与电池状态会合

底板第 4 页中，9 V 经 R52 驱动 U23 光耦的 LED，低压侧集电极接 `VCC3.3CW`，发射极经 R79 下拉并通过 R57 接 GPIO3_B4。输入存在时检测端趋向高电平，符合 `GPIO_ACTIVE_HIGH`。SoC 接收的是低压侧逻辑信号，9 V 不直接进入 GPIO。

`gpio_charger_probe()` 申请输入 GPIO，注册 `dc-charger`，并尝试申请上升、下降两个边沿 IRQ。IRQ 回调只调用 `power_supply_changed()`；读取 ONLINE 时，`gpio_charger_get_property()` 执行 `gpiod_get_value_cansleep()`，返回当时的 GPIO 逻辑值。即使 IRQ 申请失败，probe 仍可成功并保留按需读取 ONLINE 的能力，只是变化通知路径缺失。这个实现没有另加软件防抖定时器。

产品节点没有 `charge-status-gpios` 或充电限流 GPIO，因此它只提供 ONLINE。TP5100 的 CHRG#/STDBY# 接到板上指示电路，当前节点没有把它们交给 Linux。实际充电、充满与输入接入由不同位置表达，不能只从节点名 `dc-charger` 推出所有状态。

插入外部电源后，GPIO 对象可以立即发出变化通知；CW2015 的描述符没有 `external_power_changed` 回调，仍等自己的下轮工作调用 `power_supply_am_i_supplied()`。其状态规则明确是：未接入则 DISCHARGING；接入且 SOC 小于 100 则 CHARGING；接入且 SOC 达到 100 则 FULL。这里的 Charging 是软件推导，没有测量充电电流。由于 SOC 更新排在 ONLINE 查询之前，刚插拔时 SOC 抑制还可能使用上一轮的连接状态，然后本轮才更新 STATUS。

因此上层可以短暂读到 `dc-charger/online=1`，同时电池仍为 Discharging。正常情况下下一轮会合；如果长期不一致，优先检查供电引用、MODE/I2C 错误与周期任务，而不是把 GPIO 检测状态当成电量计已经更新。

## 8.6 从读数选择下一处观察点

目标 Linux 系统可先枚举对象，不固定假设名称或编号：

```sh
# uevent 将对象身份、单位约定下的属性与当前缓存一起列出。
for supply in /sys/class/power_supply/*; do
    [ -r "$supply/uevent" ] || continue
    printf '\n%s\n' "$supply"
    cat "$supply/uevent"
done
```

接口缺失时，沿最终设备树的 I2C3、0x62、驱动绑定与 probe 错误回查。接口存在而电压约差一倍时，先核单位、R44/R37 和 `dual-cell`；电压合理而 SOC 明显不合实际使用变化时，再核电池身份、完整 profile 与恢复日志。只有电压变化但没有通知时，前面的 `battery_changed` 条件已提供代码解释。

外部状态错误则沿另一条链缩小范围：检测线电平未随输入改变，检查光耦与供电；电平改变而 ONLINE 错误，检查最终 GPIO 与有效极性；ONLINE 正确而电池 STATUS 长期不变，检查电量计采样及供电关联。详细故障流程见[第 11 章](11_故障排查与验证.md)。

## 8.7 核心工程问题与深度理解

### 8.7.1 把设计容量改成两倍，能否修正双节电池电压少一半

不能。电压倍率由分压电路、VCELL 换算和 `dual-cell` 分支决定；设计容量参与 `charge_now`、`current_now` 等派生量。改容量会使这些派生量失真，却不会修复电压。

### 8.7.2 为什么读取电池属性很快，却可能拿到几秒前甚至更早的数据

属性函数读取内存缓存，I2C 发生在另一个周期任务中。正常时数据有一个轮询周期左右的年龄；读取失败时各字段保留旧值，年龄继续增长。频繁读取接口不能替代后台采样，必须结合日志和有意义的输入变化判断。

### 8.7.3 ONLINE 和 Charging 都出现后，还能否直接计算真实充电功率

不能。这份实现用 ONLINE 与 SOC 推导 Charging，`current_now` 只在有效放电剩余时间条件下估算；两者都不是充电电流测量。真实充电功率需要电池端电压、电流及测量方向，或充电芯片相应遥测接口。
