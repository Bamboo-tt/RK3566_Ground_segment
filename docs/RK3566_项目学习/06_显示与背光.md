# 06 显示与背光：让像素、面板状态与照明配合

```text
运行时像素链
显示缓冲区 → DRM/KMS 提交与扫描配置 → VOP 的 VP0 → DSI0 Host/PHY
                                                     → 四条 DSI 数据 lane → 液晶像素

面板状态切换链
panel prepare → 电源开启 → 复位与等待 → 初始化命令 → 退出睡眠/开启显示
panel enable  → 等待首帧条件 → DRM panel 框架开启关联背光

运行时背光链
亮度请求 → backlight → brightness-levels 查表 → PWM5 → U5 → SY7201 → LED 光源
                          开关屏状态 ──────→ GPIO4_B3 → Q6/Q9 电源开关

液晶像素 + LED 光源 → 人眼看到的画面
```

本章主要使用 [AIRCAS overlay](../../设备树包/aircas-compact-GCS_overlay.dts)的 `dsi_panel/backlight/route_dsi0`、[BOE 初始化表](../../阿美林-1000nit-7inch/初始化序列/BOE_7WX_ILI9881C_V04_20210507.txt)、两份 [普通](../../debs/radxa-overlays-dkms_0.2.4_all.deb)/[PWM](../../debs/radxa-overlays-dkms_pwm.deb) overlay 包，以及 [8 页底板图](../../原理图/SCH_RK3566底板V2_2025-10-21.pdf)第 3 页。

驱动机制对照[历史构建记录](<../../RADXA CM3地面站编译.docx>)指定的 Radxa 内核提交 `3bbac32c942f4d98fc87bde3852f185dce56ff56`，它也是公开 `linux-rk2410-nocsf 6.1.84-12` 的源码基线。重点函数位于 [panel-simple.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/panel/panel-simple.c)、[pwm_bl.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/video/backlight/pwm_bl.c)和 [drm_panel.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/drm_panel.c)。历史记录另有 panel 复位修改，相关差异在 6.3 节说明。

前两章已经建立设备描述、驱动与资源的关系。显示在此基础上有三个任务：输出正确像素，让面板处于可接收图像的状态，让背光提供适量照明。三条链在屏幕上汇合，各自的控制对象和失败位置仍然不同。

## 6.1 显示缓冲区怎样成为连续像素流

### 6.1.1 内存中的图像交给显示控制器扫描

DRM/KMS 管理显示设备、模式和扫描输出。上层将图像保存在缓冲区中，通过图形栈提交要显示的内容和模式；显示控制器按扫描节拍读取像素。Rockchip 的 VOP 承担显示处理，VP 是其视频输出端口，DSI Host 将像素组织成串行传输，PHY 通过差分信号送到面板。

本章配置为视频模式。静止界面可以重复扫描同一份内容，应用更新图像的频率与显示硬件的扫描频率可以不同。更新画面通常改变缓冲区内容或选用的缓冲区，不需要每帧重新上电和发送初始化表。DSI 的 RGB888 规定线路上的每像素 24 bit 表达；用户态缓冲区还可能带其他格式、对齐和 stride，由显示管线进行相应处理。

上层的交接位置是 DRM 设备与图形栈，触摸则经 input 进入另一条链，见[第 7 章](07_触摸与input.md)。图像扫描、背光调节和触摸采集可以并行发生。

### 6.1.2 路由和端点共同闭合 VP0 到面板的通路

产品 overlay 开启 `dsi0_in_vp0`、禁用 `dsi0_in_vp1`，开启 `video_phy0`、禁用 `video_phy1`，并将 `route_dsi0.connect` 指向 `vp0_out_dsi0`。这组配置选择 VOP 的 VP0 向 DSI0 输出。仅开启 DSI 控制器，还没有选定像素来自哪个 VP。

DSI 输出与 panel 输入另有一对 endpoint。下面是原节点的关键摘录，位置分别在 `route_dsi0`、DSI `port@1` 和 panel `port@0`：

```dts
&route_dsi0 {
    status = "okay";
    connect = <&vp0_out_dsi0>;          /* 选择 VP0 → DSI0 路由 */
};

/* DSI0 的输出端口。 */
dsi_out_panel: endpoint {
    remote-endpoint = <&panel_in_dsi>;
};

/* panel 的输入端口，与 DSI 输出互相引用。 */
panel_in_dsi: endpoint {
    remote-endpoint = <&dsi_out_panel>;
};
```

endpoint/remote-endpoint 描述数据连接，`power-supply` 描述电源消费者关系，`backlight` 引用描述面板关联的照明设备。它们服务不同框架，数据端口闭合并不会自动给面板供电。

这里还要保留基础树差异：当前 IO DTS 的 `route_hdmi` 为 okay，交付基础 DTB 则为 disabled；产品 overlay 禁用 HDMI 控制器和其 VP0 输入，但未显式覆盖 `route_hdmi`。从不同基础树生成最终显示图时，应同时查看控制器、路由和端点，避免只看产品文件漏掉基础状态。

## 6.2 panel 驱动先取得资源，再把参数交给 DSI

`panel@0` 使用 `compatible = "simple-panel-dsi"`，虚拟通道 `reg=0`。公开基线中的 `panel_simple_dsi_probe()` 匹配该字符串后，调用 `panel_simple_dsi_of_get_desc_data()`：先读时序、延迟和命令表，再读 `dsi,flags/dsi,format/dsi,lanes`。

公共 `panel_simple_probe()` 获取名为 `power` 的 regulator、可选 enable/reset GPIO，读取面板方向，初始化 `drm_panel`，通过 `drm_panel_of_backlight()` 取得关联背光。资源获取错误会返回，背光提供者尚未注册时可以延迟探测。当前 panel 有 `reset-gpios`，但没有自己的 `enable-gpios`；背光的 GPIO4_B3 属于 backlight 设备，不能塞进 panel 的可选 enable GPIO 路径。

公共 probe 成功后，DSI probe 将参数写入 `dsi->mode_flags/format/lanes`，再 `mipi_dsi_attach()` 连接主机。当前已显式引用 PWM 背光，所以不会走“没有关联 backlight 时注册 DCS 亮度设备”的后备分支。资源就绪和 attach 完成后，显示框架才有了可调用的面板状态接口。

| 当前参数 | 进入哪一层 | 具体作用 |
| --- | --- | --- |
| `power-supply = <&vcc_lcd_mipi>` | regulator 消费者 | 开关面板逻辑电源 |
| GPIO3_C1、`GPIO_ACTIVE_LOW` | reset GPIO descriptor | 以低电平断言面板复位 |
| `backlight = <&backlight>` | DRM panel/backlight | 在面板开关流程中协调照明 |
| `dsi,lanes = <4>` | DSI Host/PHY | 使用四条数据 lane |
| `dsi,format = RGB888` | DSI 像素打包 | 每像素 24 bit |
| VIDEO、VIDEO_BURST | DSI 模式 | 选择视频扫描及 burst 传输方式 |
| LPM | DSI 消息传输 | 让命令消息请求低功耗发送 |

LPM 不会让整条视频像素链始终以低速发送。DSI 核心把设备模式中的 LPM 转成消息标志，主机的 `dw_mipi_message_config()` 再配置命令发送方式；视频模式的选择由另一组模式配置负责。

EOT 宏尤其需要连着头文件看。[headers 包](../../debs/linux-headers-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb)成员 `usr/src/linux-headers-6.1.84-12-rk2410-nocsf/include/dt-bindings/display/drm_mipi_dsi.h` 定义 `MIPI_DSI_MODE_NO_EOT_PACKET = 1 << 9`。[overlay 包](../../debs/radxa-overlays-dkms_0.2.4_all.deb)中的 `usr/src/radxa-overlays-0.2.4/arch/arm64/boot/dts/rockchip/overlays/dt-bindings/display/drm_mipi_dsi_overlay.h` 将旧名 `MIPI_DSI_MODE_EOT_PACKET` 映射到该新名。因此当前四项按位或后的值是 `0xA03`，其中 bit 9 的头文件语义是禁止 HS EOT。

还需看谁使用这个位：公开基线的 [Synopsys DSI 主机](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/bridge/synopsys/dw-mipi-dsi.c)在 `dw_mipi_dsi_packet_handler_config()` 固定写入 CRC、ECC、BTA 位，没有按 NO_EOT 分支切换 EOTP_TX_EN。可见旧宏名、展开值和主机寄存器处理是三个层次；迁移到另一主机实现时，需要重新检查最后一层。

## 6.3 面板准备与关闭按硬件阶段推进

### 6.3.1 电源、复位和命令在 prepare 中接力

公开基线的 `panel_simple_prepare()` 先检查 `prepared`，已准备的面板直接返回；否则使能 regulator，再操作可选 enable GPIO、等待、复位并发送命令。将当前 overlay 的值代入正常路径：

```text
regulator_enable(power)
  → 可选 enable GPIO 置有效（当前 panel 未配置此 GPIO）
  → prepare-delay：20 ms
  → reset 逻辑 1：GPIO3_C1 物理低，断言复位
  → reset-delay：5 ms
  → reset 逻辑 0：GPIO3_C1 物理高，释放复位
  → init-delay：5 ms
  → 发送 panel-init-sequence
  → prepared = true
```

这些操作位于允许等待的显示状态切换上下文。GPIO descriptor 的物理解释来自低有效属性；[第 3 章](03_硬件资源与供电.md)已经把它追到 FPC1 的复位脚。供电失败会直接返回错误，后面的复位和命令不执行。

下面摘录决定复位顺序的代码，省略前面的供电和后面的命令处理：

```c
/* p->reset_gpio 来自低有效 reset-gpios，逻辑 1 对应物理低。 */
gpiod_direction_output(p->reset_gpio, 1);
if (p->desc->delay.reset)
    panel_simple_msleep(p->desc->delay.reset); /* 当前为 5 ms */

gpiod_direction_output(p->reset_gpio, 0);     /* 释放复位，物理高 */
if (p->desc->delay.init)
    panel_simple_msleep(p->desc->delay.init);  /* 释放后再等待 5 ms */
```

`panel_simple_msleep()` 在此基线中调用 `usleep_range(ms*1000, ms*1000+100)`。它表达允许调度的等待范围，不提供硬实时截止保证；任务重新获得 CPU 仍受调度影响。

### 6.3.2 enable、disable 与断电各自改变哪些状态

`panel_simple_enable()` 等待 `enable-delay-ms=120`，设置 `enabled=true`，再通知关联设备。`drm_panel_enable()` 在该回调成功后调用 `backlight_enable()`，使照明与面板状态衔接。这里的 120 ms 位于完整 prepare 之后，不能代替初始化表内部两条命令之间的等待。

关闭时，`drm_panel_disable()` 先关闭背光，再进入 panel 的 disable 回调。后者发出预关闭通知，等待 `disable-delay-ms=50`，将 `enabled=false`。随后 unprepare 发送退出表：`0x28` 关显示、`0x10` 进入睡眠；再断言复位、撤销可选 enable、关闭 regulator，等待 `unprepare-delay-ms=120`，最后清除 `prepared`。退出表自身两条记录的延迟字段均为 0，断电后的 120 ms 与命令后、断电前的等待位置不同。

资源释放也沿这条关系进行：panel remove 先移出面板注册表，再调用 disable/unprepare，释放 DDC 引用；devm 资源随设备生命周期回收。关闭屏幕与卸载设备不是同一事件，前者通常保留对象，以便之后重新 prepare。

历史 Word 的“屏幕上电时序严格实现”另记录了 `reset_gpio` 逻辑值 `1→0→1`，并把注释写成“高→低→高”。若这段修改与当前低有效 `reset-gpios` 同时使用，实际电平会是“低→高→低”，末尾仍断言复位。该记录对应的修改版 panel 源码没有保存在仓库中；判断这项修改的效果，必须将当时极性配置与函数体成对使用。公开基线在发送命令前以逻辑 0 释放复位，不能将两个版本拼成同一时序。

## 6.4 初始化表怎样变成 DSI 消息

### 6.4.1 先建立寄存器页和记录布局

7 英寸 BOE/ILI9881C 原始表用 `REGISTER` 和 `Delay` 表达写寄存器与等待。`FF 98 81 03` 选择 page 3，后续同一个寄存器地址的含义受当前页影响。表中的 GIP 设置行扫描驱动时序与映射，电压/偏置设置液晶驱动工作点，Gamma 设置灰阶对应的驱动关系；这些配置与每帧图像、底板 PWM 亮度是不同对象。

云奥 [6 英寸初始化文本](<../../云奥-270nit-6inch/6.0-1MIPI CODE (1).txt>)则以 `HX8394D_HSD698` 结构和 `B9 FF 83 94` 开始，属于另一控制器方案，无法把记录形式相似当成可互换的寄存器表。

当前 Rockchip panel 扩展将命令编码成连续字节。源码中的头部为三个 `u8`：

```c
struct panel_cmd_header {
    u8 data_type;       /* DSI 消息类别，用于选择 generic/DCS 等发送路径 */
    u8 delay;           /* 这条命令发送后的等待，单位 ms */
    u8 payload_length;  /* 紧随头部的负载字节数，包含命令字节 */
} __packed;            /* 三字节连续布局，没有结构体填充 */
```

用两条实际记录拆开看：

| 记录 | 类型 | 后置延迟 | 长度 | 负载及用途 |
| --- | --- | --- | --- | --- |
| `39 00 04 FF 98 81 03` | `0x39`，DCS 长写类别 | 0 ms | 4 | 选择 page 3 |
| `15 78 02 29 00` | `0x15`，DCS 带参数短写类别 | `0x78=120` ms | 2 | page 0 的开启显示命令及参数 |
| `05 00 01 28` | `0x05`，DCS 无参数短写类别 | 0 ms | 1 | 关闭显示 |

`panel_simple_parse_cmd_seq()` 先复制原始数据，遍历时取 3 字节头，再检查剩余长度能否容纳 `payload_length`；不够或末尾残留字节返回 `-EINVAL`。计数完成后分配命令描述数组，各项保存头部和负载指针。当前 overlay 的初始化表为 194 条、978 字节，记录长度可变，因此不能按文本行宽或固定 5 字节跨到下一条。

### 6.4.2 发送类别、负载长度与错误返回共同决定行为

`panel_simple_xfer_dsi_cmd_seq()` 根据头部类别调用 DSI 接口。0x05/0x15/0x39 三类都进入 `mipi_dsi_dcs_write_buffer()`；该函数又根据实际负载长度选择无参数短写、带参数短写或长写。记录头选择发送家族，负载长度参与最终封包，两者应配套。[DSI 核心实现](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/drm_mipi_dsi.c)

下面摘录发送循环的 DCS 分支与循环末尾，其他消息类别省略：

```c
case MIPI_DSI_DCS_SHORT_WRITE:
case MIPI_DSI_DCS_SHORT_WRITE_PARAM:
case MIPI_DSI_DCS_LONG_WRITE:
    err = mipi_dsi_dcs_write_buffer(dsi, cmd->payload,
                                   cmd->header.payload_length);
    break;
/* 其他 switch 分支省略；未知类别返回 -EINVAL。 */

/* 发送错误只记录日志，当前循环继续处理后续命令。 */
if (err < 0)
    dev_err(dev, "failed to write dcs cmd: %d\n", err);
if (cmd->header.delay)
    panel_simple_msleep(cmd->header.delay); /* 明确发生在发送之后 */
```

这个版本在正常遍历结束后返回 0。DSI prepare 路径调用该发送函数时也没有检查其返回值，随后仍将 `prepared=true`。所以串行传输报错可能与面板软件状态“已准备”同时存在；此时应沿具体失败命令、Host 状态和面板供电复位定位，不能把 `prepared` 当作芯片读回确认。通用参数表能减少为每款屏幕复制驱动的工作，但这条路径没有读回校验和逐项失败回滚。

### 6.4.3 当前转换表把退出睡眠后的等待挪到了开显示之后

切回 page 0 后，BOE 原始表为 `0x11 → Delay 120 → 0x29 → 0x35`。当前 overlay 为：

```text
15 00 02 11 00   # 发退出睡眠；后置延迟为 0
15 78 02 29 00   # 随即发开启显示；之后等待 120 ms
15 00 02 35 00   # 再发送下一条控制命令
```

根据刚读到的发送函数，120 ms 确实位于 `0x29` 之后，原表要求的 `0x11` 与 `0x29` 之间间隔没有被编码。这会让开显示命令在面板退出睡眠尚未完成时到达，影响是否能正确接受命令以及冷启动、唤醒的稳定性。后面的 `enable-delay-ms=120` 同样在这两条命令之后，无法补回它们之间缺失的间隔。

[独立转换表](../../阿美林-1000nit-7inch/初始化序列/panel_init_sequence.txt)还比 overlay 多一条 `15 00 02 29 00`，共 195 条。重复开显示与错误等待位置是两个差异，比较供应商表时应按寄存器页与命令顺序逐项对齐。同名 `0x11` 在其他寄存器页里的写入，不应混入 page 0 的退出睡眠分析。

## 6.5 面板工作后，像素还要按完整时序传输

### 6.5.1 有效区域和消隐共同构成一帧

800×1280 只表示有效像素区。一行还包含水平同步和前后空白，一帧还包含垂直同步和空白行。当前 `display-timings` 的参数为水平同步/后沿/前沿各 18，垂直同步/后沿/前沿为 4/10/20，像素时钟 67.3 MHz。

```text
水平总周期 Htotal = 800 + 18 + 18 + 18 = 854 个像素节拍
垂直总周期 Vtotal = 1280 + 4 + 10 + 20 = 1314 行
60 Hz 所需像素时钟 = 854 × 1314 × 60 = 67,329,360 Hz
配置 67,300,000 Hz 对应刷新率 ≈ 59.974 Hz
```

同步极性也属于模式：当前 HS/VS/DE 为低有效、像素时钟配置为正沿相关属性。改分辨率或时钟时，需要连同同步、消隐和屏幕规格一起核对。模式不匹配可能导致不锁定、花屏或闪烁，即使初始化命令已经正确发送。

### 6.5.2 像素时钟与单 lane 速率不同

RGB888 每像素 24 bit，四条数据 lane 分担串行数据。用 `67.3 MHz × 24 / 4` 得到约 **403.8 Mbit/s/lane** 的数据量级；这还不是 PHY 的最终速率，Host 还要容纳包开销、burst 调度和时钟量化。

公开基线的 [dw-mipi-dsi-rockchip.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/gpu/drm/rockchip/dw-mipi-dsi-rockchip.c)在 `dw_mipi_dsi_calculate_lane_mpbs()` 中优先使用 `rockchip,lane-rate`。当前该属性被注释，走计算路径：先将像素时钟向上取整为 MHz，再计算 `mpclk × (bpp / lanes) × 10 / 9`，受最大速率限制。代入当前模式，整数计算为 `68 × 6 × 10 / 9 = 453 Mbit/s`，之后还需经过 PHY 配置或 PLL 参数选择。源码注释中的 480 因而不是当前固定输出值。

### 6.5.3 原生扫描方向与触摸坐标分别变换

panel 的原生模式是 800×1280，`rotation=90` 由 `of_drm_get_panel_orientation()` 读取，并通过 panel/connector 的方向信息交给显示栈。它本身不是每帧旋转图像的函数调用；实际输出方向由消费该信息的显示栈组织。

触摸节点中的 1280×800、供应商 CFG 中的 800×1280 处于另外的配置层。控制器原始坐标、驱动交换/翻转和桌面映射要各自对应。显示旋转不会自动修改 GT9XX 的坐标处理，重复交换轴也会造成二次变换。[第 7 章](07_触摸与input.md)沿同一触点继续解释范围和方向。

## 6.6 一次亮度请求怎样变成 PWM 状态

### 6.6.1 用户值先选表项，再按量程换算

backlight 节点使用 `pwm-backlight`，`pwms=<&pwm5 0 50000 PWM_POLARITY_INVERTED>` 指定 PWM5 的通道 0、周期 50000 ns 和反相极性。周期换算为 `1/(50000×10^-9)=20 kHz`，持续波形由 PWM 硬件产生。

用户写入的 `brightness` 是**表索引**。`pwm_backlight_parse_dt()` 从属性字节长度计算表项数量，把 `max_brightness` 设为项数减一；probe 遍历表取得最大表值 `scale`。更新时，`backlight_get_brightness()` 先考虑开关屏/挂起状态，再由 `compute_duty_cycle()` 查表换算。

| 对象及包内成员 | 表项与索引 | 默认值及查表结果 |
| --- | --- | --- |
| 工作区 overlay、普通包 `.../overlays/aircas-compact-GCS.dts` | 256 项；索引 0～255；开头 `0,20,20,21,21…`，最大表值 255 | 默认索引 200，表值 200 |
| PWM 包 `.../overlays/aircas-compact-GCS-pwm.dts` | 197 项：`0,60,61…255`；索引 0～196 | 默认仍写 200，超过最大索引 |

两个成员的完整前缀都是 `usr/src/radxa-overlays-0.2.4/arch/arm64/boot/dts/rockchip/`。重复表项会让相邻索引产生相同 PWM；非线性表则可调整每档变化，数组索引、数组值和人眼亮度不能当成一个数。

### 6.6.2 越界默认值会先警告，再钳制到末项

公开同版本基线的 `pwm_backlight_probe()` 在第一次更新前执行下列边界处理，属于源码摘录：

```c
if (data->dft_brightness > data->max_brightness) {
    dev_warn(&pdev->dev,
             "invalid default brightness level: %u, using %u\n",
             data->dft_brightness, data->max_brightness);
    /* 默认索引超界时选择最后一个有效索引，避免直接越界查表。 */
    data->dft_brightness = data->max_brightness;
}
```

因此 PWM 变体在这条实现下是 **200 → 196 → levels[196]=255**，默认 PWM 有效时间走到满量程。后面还会考虑 quiescent 参数、原有开关状态和 panel 的背光使能时机。这里的配置问题会改变默认输出，并非直接发生数组越界崩溃。对具体交付包，还需将它的私有驱动改动与这条公开路径对应；仓库中没有另一份 `pwm_bl.c` 修改记录。

### 6.6.3 计算有效时间，再处理开启和关闭

`compute_duty_cycle()` 的关系是：

```text
duty = levels[index] × (period − lth) / scale + lth
```

`lth` 是最低占空比偏移。当前 DT 路径清零平台数据且未设置该偏移，得到 lth=0；两张表最大值均为 255。普通默认索引 200 的计算为 `50000 × 200 / 255 = 39215 ns`，整数除法舍去小数，约 39.215 µs。PWM 控制器将这个纳秒目标进一步量化到硬件计数。

亮度大于 0 时，驱动先申请新的 duty，再在需要开启时使能电源/PWM，等待 `post-pwm-on-delay-ms=10`，最后将背光使能 GPIO 置有效。GPIO4_B3 为高有效，经 Q6/Q9 接通背光输入电源。亮度为 0 或开关屏状态要求关闭时，先撤销 GPIO，再等待 `pwm-off-delay-ms=10`，禁用 PWM、将 duty 置零，并释放电源使能请求。

这解释了为什么索引 0 要单独看：它进入关断路径，不能仅代入反相 PWM 公式推断“索引越低越亮，因此 0 最亮”。屏幕关闭后，panel 和 backlight 对象仍可存在，下一次开启再依据保存的亮度请求恢复输出。

该基线在 probe 时检查初始 PWM 配置错误；运行时 `update_status()` 却未向上返回每次 `pwm_apply_state()` 的错误，power-on 中 regulator 失败也只记录日志。接口写入返回成功时，如输出异常，应继续观察 PWM 状态、使能和电源响应，而非只读取保存的 `brightness`。

## 6.7 极性必须推到背光驱动输入端

反相 PWM 表示有效时间对应物理低电平。沿普通默认值算例，SoC 端每 50 µs 周期约低 39.215 µs、高 10.785 µs。示波器的“高电平占空比”约为 21.57%，而 Linux 请求的有效时间比例约为 78.43%，两种读数的定义不同。

再沿第 3 页电路看 U5。TLP2361 的 LED 阳极经 R84 接 `VCC3.3CW`，GPIO0_C4 经 R25 接阴极，阴极还有 R83 下拉。GPIO 拉低会增强 LED 电流；TLP2361 的真值表规定 LED 导通时输出低、关闭时输出高。因此在输入电流和电平满足器件阈值时，从 SoC GPIO 到 U5 输出的整体关系为低到低、高到高，不能因为器件标为反相光耦就再简单反转一次 GPIO 波形。[TLP2361 数据手册](https://toshiba.semicon-storage.com/info/TLP2361_datasheet_en_20260309.pdf?did=14229&prodName=TLP2361)

U5 输出经 R77 到 SY7201 的 EN/PWM。该芯片以高电平使能、低电平关闭，输入 PWM 调节 LED 电流；GPIO4_B3 控制的是另一条输入电源开关。在上述逻辑条件下，提高亮度表值会增加 SoC 低电平时间，减少 EN/PWM 的高电平时间，因而可以解释历史注释“非零档位越小越亮”的方向。若实际电路、器件或接法不同，则应从 U5 输入电流和输出波形重新推导。[SY7201 厂商数据手册，分销商镜像](https://datasheet.lcsc.com/datasheet/pdf/43c98b0e138641f6a7bfe084bff78457.pdf?productCode=C82173)

于是 PWM 变体默认被钳制到表值 255 后，反相波形趋于持续低电平；若对应上述电路，EN/PWM 也趋于低，背光可被关闭，即使电源使能 GPIO 仍有效。这是“最大软件索引可能对应最暗输出”的具体链路，不能将驱动的最大索引直接称为最大物理亮度。

SY7201 的 FB 引脚与 R27=1 Ω 构成恒流反馈，手册给出 `I=0.2 V/R`，对应约 0.2 A 的设定量级；PWM 改变调光条件，LED 电流来自升压电路。手册所列 1 MHz 是转换器内部开关频率，当前 20 kHz 是外部调光频率，二者不同。该早期规格对 PWM 推荐频率使用“高于 20 kHz”的表述，当前配置正处于边缘，调光频率与实际器件修订应配套检查。

## 6.8 沿三条链选择最有区分力的观察点

| 现象 | 第一项有区分力的观察 | 结果怎样改变判断 |
| --- | --- | --- |
| 完全无光 | 背光输入电源、GPIO4_B3 和 EN/PWM | 电源缺失回到 Q6/Q9；电源存在而 EN/PWM 无有效高电平，查表值、极性和 U5 |
| 背光亮但无图像 | 面板逻辑电源、RST、DRM 模式与 DSI 命令错误 | 电源复位失败先修工作条件；条件正常再检查退出睡眠间隔、端点路由和像素提交 |
| 有图但花屏或闪烁 | 完整模式、lane/格式与所用屏幕型号 | 固定配置不匹配时先比较参数；参数匹配后再定位排线和信号质量 |
| 冷启动异常，软重启正常 | 电源建立、复位释放与 0x11/0x29 间隔 | 区分残留状态掩盖的初始化缺口与持续扫描错误 |
| 非零档位方向反向 | PWM 的低/高时间、U5 输出及 EN/PWM | 区分软件索引定义与电路反相关系；相邻档位不变还要看重复表项 |
| 换 PWM 插件后默认黑屏 | max_brightness、默认钳制日志、最终表值 | 若为 196/255，继续核对反相后的持续低电平和使能状态 |

DRM 的设备与模式入口通常位于 `/dev/dri/`、`/sys/class/drm/`，背光位于 `/sys/class/backlight/`。`brightness` 保存请求，`actual_brightness` 的含义由驱动提供；此处没有光学传感器反馈，不能把它作为照度值。检查时将软件模式、实际波形和固定图样对应起来，完整排障组织见[第 11 章](11_故障排查与验证.md)。

## 6.9 核心工程问题与深度理解

### 6.9.1 为什么两处都是 120 ms，却不能互相替代

因为等待保护的是两个具体事件之间的间隔。当前命令表把 120 ms 放在 0x29 之后，enable 延迟又位于 prepare 完成之后；两者都没有拉开 0x11 与 0x29。只有在退出睡眠和开启显示之间加入所需等待，才表达了供应商原表的顺序。

### 6.9.2 PWM 插件默认 200 超界，为何可能黑屏却不发生越界崩溃

公开驱动先把 200 钳制到有效索引 196，查到表值 255，再算出满周期的有效时间。反相 PWM 将其变为持续低电平；按本图的 U5 接法，SY7201 的 EN/PWM 也趋于低。这条链解释了可能的暗屏后果，索引越界本身已被驱动边界处理挡住。

### 6.9.3 prepare 返回成功后为什么仍要看 DSI 错误

该版本的发送循环会记录单条命令错误并继续，prepare 也未检查 DSI 序列返回值，仍设置 `prepared`。软件状态表示流程走到哪里，未包含面板寄存器读回确认。若背光亮而无图，应把命令失败位置、面板电源复位与实际显示模式连起来判断。

### 6.9.4 面板已经横向显示，触摸为什么还可能偏转

显示方向信息、扫描模式和 GT9XX 坐标变换由不同对象处理。`rotation=90` 不会改写触摸驱动的交换/翻转标志。需要先确定 input 范围及四角坐标，再检查显示栈的映射，避免为已经转换过的触点再旋转一次。
