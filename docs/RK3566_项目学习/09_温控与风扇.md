# 09 温控与风扇：温度怎样变成一次冷却动作

```text
运行时的反馈关系
TSADC 温度码 -> rockchip_thermal_get_temp -> soc-thermal 当前温度
                                                |
                         trips / cooling-maps -> governor
                                                |
                       +------------------------+--------------------+
                       |                                             |
                       v                                             v
             CPU/GPU 冷却设备：限制发热                  风扇冷却设备：请求冷却状态
                                                                     |
                                                                     v
                                                   cooling-levels[state] -> PWM0
                                                                     |
                                                                     v
                                                     GPIO0_C7 / PWM0_M1
                                                                     |
                                                                     v
                                                      U31 供电电路 -> 风扇
                                                                     |
                                 后续温度 <------ 散热器与空气的热响应 --+

温度与状态可从 thermal / hwmon 读取；风扇支路能否被 governor 调用，
取决于策略要求的接口与冷却设备能力是否配套。
```

核心位置：[CM3 DTSI](../../src/rk3566-radxa-cm3.dtsi) 的 `tsadc`；[IO DTS](../../src/rk3566-radxa-cm3-io.dts) 的 `fan0`、`pwm0`、`soc_thermal`；[2025-10-21 底板图](../../原理图/SCH_RK3566底板V2_2025-10-21.pdf) 第 8 页。驱动采用[构建记录](../../RADXA%20CM3地面站编译.docx)指定的公开 Radxa `3bbac32` 基线，主要入口为 [rockchip_thermal.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/thermal/rockchip_thermal.c)、[thermal_core.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/thermal/thermal_core.c) 与 [pwm-fan.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/hwmon/pwm-fan.c)。其与本地适配包的关系沿用第 8 章的版本说明。

上一章把采样值交给上层读取，本章则要让一个测量值改变执行器。温度、控制策略、冷却状态、PWM 波形和实际风量各自有不同单位与完成条件。沿一次调速请求把它们连接起来，才能判断“温度超过 60°C，风扇却没有按预期变化”发生在哪一层。

## 9.1 温度输入与风扇输出分别建立资源

### 9.1.1 TSADC 把芯片温度交给 thermal zone

TSADC 是 SoC 内部温度检测控制器。CM3 DTSI 将它设为 `okay`，公开基线的 [rk356x.dtsi](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/arch/arm64/boot/dts/rockchip/rk356x.dtsi) 用 `thermal-sensors = <&tsadc 0>` 将通道 0 接到 `soc-thermal`。这里的 thermal zone 是一组温度、控制点和冷却关系的管理对象；它不是风扇的另一个名字。

`rockchip_thermal_probe()` 建立寄存器、时钟、复位、IRQ 等控制器资源，初始化传感器，再把各通道注册给 thermal。RK356x 使用 `rk3568_tsadc_data` 中的转换表；`rockchip_thermal_get_temp()` 调用芯片对应的 `get_temp`，将 ADC 码经表格和区间插值换成 m°C，并减去传感器校准偏移。因此 `60000` 表示 60°C，不能把 ADC 原码或摄氏整数直接交给后续 trip 比较。

更新有两种入口：thermal 的轮询工作，以及 TSADC 告警 IRQ 线程。告警线程先确认中断，再对传感器调用 `thermal_zone_device_update()`；框架读取温度、处理各 trip、执行策略并安排下次轮询。阈值与更新频率由此分工：阈值规定控制判断，轮询周期决定多久重新观察一次。

### 9.1.2 pwm-fan 先取得 PWM，再注册冷却接口

风扇是独立的 platform 设备。[IO DTS](../../src/rk3566-radxa-cm3-io.dts) 中的实际配置如下：

```dts
fan0: pwm-fan {
    compatible = "pwm-fan";
    #cooling-cells = <2>;                 // cooling map 传入状态下限和上限
    cooling-levels = <0 64 128 192 255>;  // 5 个状态分别对应的 PWM 控制值
    pwms = <&pwm0 0 10000 0>;             // 通道 0，周期 10000 ns，普通极性
};

&pwm0 {
    pinctrl-0 = <&pwm0m1_pins>;           // 输出到 GPIO0_C7 的 PWM0_M1 功能
    status = "okay";
};
```

`pwm_fan_probe()` 用 `devm_pwm_get()` 向已注册的 PWM 控制器申请通道，资源提供者尚未就绪时可延迟探测；随后取得可选 `fan-supply`。当前节点没有该供电引用，底板 +5 V 不由这里的 regulator 回调控制。驱动初始化 PWM 状态后，先请求控制值 255，使输出处于最大请求，再注册 hwmon、解析 `cooling-levels`，最后注册 `pwm-fan` cooling device。五项表得到 `max_state=4`，任一表值大于 255 都会使解析失败。

[交付内核包](../../debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb) 的 `boot/config-6.1.84-12-rk2410-nocsf` 将 Rockchip thermal/PWM 配为内建，而 `CONFIG_SENSORS_PWM_FAN=m`；对应成员为 `lib/modules/6.1.84-12-rk2410-nocsf/kernel/drivers/hwmon/pwm-fan.ko.xz`。因此传感器可能先就绪，风扇要等匹配模块装载并完成 probe，二者不是按 DTS 行号依次启动。

Radxa 的风扇驱动还有一条独立的 Rockchip system-monitor 通知路径：只有编译可达且节点含 `rockchip,temp-trips` 时才采用，并提前返回，不再注册普通 thermal cooling device。当前节点没有该属性，所以本章追踪 cooling map 路径，不将这两套控制器同时拼进运行链。

## 9.2 温区怎样把控制目标关联到冷却设备

### 9.2.1 trip 是控制点，map 是绑定关系

SoC 公共 DTSI 定义 trips，IO DTS 将 `threshold` 改为 60000，并把 `sustainable-power` 改为 5000。[交付内核包](../../debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb) 的 `usr/lib/linux-image-6.1.84-12-rk2410-nocsf/rockchip/rk3566-radxa-cm3-io.dtb` 保存了以下组合：

| 配置 | 值 | 用途 |
| --- | --- | --- |
| `threshold` | 60000 m°C，passive，hysteresis 2000 m°C | 第一处被动冷却控制点 |
| `target` | 85000 m°C，passive，hysteresis 2000 m°C | 后一处被动控制点；power_allocator 用作目标温度 |
| `soc-crit` | 115000 m°C，critical | 进入严重过热保护路径 |
| `polling-delay` | 1000 ms | 普通状态下的温区轮询周期 |
| `polling-delay-passive` | 20 ms | `tz->passive` 有效时采用的周期 |
| `sustainable-power` | 5000 mW | 策略的可持续耗散功率参数 |

20 ms 不表示风扇 PWM 的周期，5000 mW 也不是风扇额定功率。`passive` 在这里指定一种 trip 类型及其策略处理，不能据名字断定它只用于 CPU，或认为风扇必须绑定 `active` 才会工作。critical 则越过普通 governor 调档：到达 115°C 时框架调用严重过热处理，默认走保护关机。这与 TSADC 的硬件 TSHUT 是不同保护路径。

基础 `map0/map1` 把 CPU、GPU 冷却设备接到 `target`，IO DTS 又增加 `map2/map3`，把同一个 `fan0` 分别接到 `target` 和 `threshold`。CPU/GPU 冷却通过限制工作点减少发热，风扇通过增加散热搬走热量，三个设备的状态值互不通用。

风扇映射中的 `THERMAL_NO_LIMIT` 表示 map 不进一步收紧状态范围，实际仍限于 0～4。`contribution=8192` 是参与策略分配的权重，不是 8192 RPM。框架为每条映射保存一个 `thermal_instance` 请求；最终更新同一个冷却设备时，`__thermal_cdev_update()` 取所有有效请求中的最大状态，避免一个较弱请求覆盖另一个更强的散热需求。

### 9.2.2 默认 power_allocator 与当前风扇存在接口缺口

包内配置选择 `CONFIG_THERMAL_DEFAULT_GOV_POWER_ALLOCATOR=y`。[这一基线的 gov_power_allocator.c](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/thermal/gov_power_allocator.c) 将首个 passive trip 作为开始控制的点，最后一个 passive trip 作为目标温度。因此在这套配置中，60°C 是介入点，85°C 是目标，85°C 不是关闭风扇的温度。

策略根据目标与当前温度之差、累计偏差等计算允许功率，再向各 power actor 分配。power actor 必须提供 `get_requested_power`、`state2power`、`power2state`，让策略在功率与冷却状态之间换算。CPU 限频设备可以利用能量模型承担这一角色；一张 PWM 档位表本身没有表达这样的功率关系。

当前基线的 `pwm_fan_cooling_ops` 仅有三个状态回调：

```c
static const struct thermal_cooling_device_ops pwm_fan_cooling_ops = {
    .get_max_state = pwm_fan_get_max_state, // 提供最大表索引 4
    .get_cur_state = pwm_fan_get_cur_state, // 读取保存的状态
    .set_cur_state = pwm_fan_set_cur_state,// 查表并提交 PWM
    // 没有功率估计、state2power、power2state 回调
};
```

这使它无法参与上述功率分配。governor 已运行后才出现风扇时，分配循环会跳过这个非 power actor；若尝试在已有该绑定的温区上绑定 power_allocator，`check_power_actors()` 会警告并返回 `-EINVAL`。代码没有“发现 pwm-fan 就自动改用 step_wise”的补救。

实际影响是：仅保留当前默认策略和这张 map，无法形成自动风扇调档闭环；风扇可能停留在 probe 请求的最大值，即使 CPU 限频仍在工作。要建立自动调速，策略须能调用状态式冷却设备，或另有适配过的风扇控制实现。运行系统的 `policy` 决定应分析哪条路径，不能只靠两个温度值推导行为。

## 9.3 一次冷却状态请求怎样成为 PWM 波形

### 9.3.1 表索引与输出控制量分两步转换

先追踪已经到达 `pwm_fan_set_cur_state(cdev, 2)` 的请求。2 是 `cooling-levels` 的索引，取出的是 128。该函数检查状态不大于 `max_state`，相同状态直接返回；变化时调用 `set_pwm()`，提交成功后才更新保存的状态。下面是核心摘录：

```c
if (!ctx || state > ctx->pwm_fan_max_state)
    return -EINVAL;                  // 超出本设备支持的状态范围
if (state == ctx->pwm_fan_state)
    return 0;                        // 相同请求不重复配置

ret = set_pwm(ctx, ctx->pwm_fan_cooling_levels[state]);
if (ret) {
    dev_err(&cdev->device, "Cannot set pwm!\n");
    return ret;                      // 失败时不提交新的软件冷却状态
}
ctx->pwm_fan_state = state;
```

`set_pwm()` 在 mutex 内调用 `__set_pwm()`，串行化 thermal 与 hwmon 对 PWM 共享状态的修改。非零请求按下面的实际公式计算 duty，并经 `pwm_apply_state()` 交给 Rockchip PWM 驱动；必要时再使能输出。这个锁协调软件请求，不检查风扇机械状态，也不赋予用户空间写入比温控策略更高的优先级。

```c
/* __set_pwm() 的非零分支中，period 和 duty_cycle 的单位均为 ns。 */
period = state->period;
state->duty_cycle = DIV_ROUND_UP(pwm * (period - 1), MAX_PWM);
ret = pwm_apply_state(ctx->pwm, state);
if (ret)
    return ret;                      // 硬件请求失败，向调用者传播
ret = pwm_fan_power_on(ctx);          // 尚未使能时开启 PWM 及可选电源
```

周期为 10000 ns，即 10 µs，频率为 `1 / 10 µs = 100 kHz`。驱动使用 `period - 1` 并向上取整，而非简单的浮点百分比。代入本项目五档：

| 冷却状态 | 查表值 | 请求的有效时间 | 占请求周期比例 |
| --- | --- | --- | --- |
| 0 | 0 | 走停机分支 | 停机请求 |
| 1 | 64 | 2510 ns | 25.10% |
| 2 | 128 | 5020 ns | 50.20% |
| 3 | 192 | 7529 ns | 75.29% |
| 4 | 255 | 9999 ns | 99.99% |

这些是提交给 PWM 层的计算结果；控制器还要按自身时钟精度量化。GPIO0_C7 通过 pinctrl 进入 PWM0_M1 后，波形由硬件重复产生。20 ms 的温控更新可以改变下一个档位，却不负责每 10 µs 翻转一次 GPIO。

### 9.3.2 启动、停机和恢复属于不同动作

probe 先请求最大 PWM，主要结果是：开机风扇转动可能来自初值，不能据此判断温控已经调过档。这份实现没有“每次从 0 档起转时先全速若干毫秒”的启动增强，也没有读取最低起转占空比属性；从 0 调到 1 就直接请求 64。电机所需的起转力矩可能大于维持旋转所需力矩，所以“能在 1 档持续转”不等于“能从静止以 1 档启动”。

0 值进入 `pwm_fan_power_off()`：把 duty 设为 0、PWM 设为 disabled，再提交硬件。默认 `enable_mode=1` 会保留可选 regulator 供电；本项目没有这个 regulator，所以真正停止仍要由引脚停止状态、MOS 和负载电路共同形成。hwmon 的 `pwm1_enable=0` 还会令非零请求直接返回而不启动，排查时应同时读取使能模式与控制值。

挂起回调关闭输出，恢复回调重新应用保存的 `pwm_value`。shutdown 和设备托管清理会同步删除 RPM 定时器并关闭输出，再由 devm 回收资源。这些动作与 governor 的降档不同：一个由设备生命周期触发，一个由温度控制请求触发。

## 9.4 阈值、迟滞与升降温过程要按策略解释

迟滞通常给进入与退出条件留出温差，减少边界反复切换。本项目配置的 `2000 m°C` 等于 2°C，但属性存在之后，还必须继续读消费者。

在此基线中，`__thermal_zone_set_trips()` 用 `trip_temp - hysteresis` 计算低边界，`handle_thermal_trip()` 用迟滞参与下降通知判断；然而 `rockchip_thermal_set_trips()` 只把高边界写入 TSADC 告警寄存器。更关键的是，[step_wise](https://github.com/radxa/kernel/blob/3bbac32c942f4d98fc87bde3852f185dce56ff56/drivers/thermal/gov_step_wise.c) 的调档判断直接比较 `temperature >= trip_temp`，不读取 hysteresis；power_allocator 的开关判断也直接比较其介入温度。因此这里没有由 `60 − 2 = 58°C` 自动得到的风扇停机条件。

可以用当前阈值和档位做一组 **运行策略为 step_wise 时的计算示例**。它需要运行配置明确选中该策略；此表不把包内默认 power_allocator 偷换成 step_wise。设温度先在 59°C 完成初始化，两个风扇映射均无请求、状态归零，随后温度按表变化；全过程低于 85°C，`target` 映射保持不介入，其他温区也没有对这只风扇的请求。

| 本轮温度 | 与上轮相比 | 60°C 控制点的动作 | 风扇状态 / 控制值 |
| --- | --- | --- | --- |
| 60°C | 升温 | 达到阈值，状态加一级 | 1 / 64 |
| 61°C | 升温 | 继续加强一级 | 2 / 128 |
| 62°C | 升温 | 继续加强一级 | 3 / 192 |
| 61°C | 降温 | 仍不低于 60°C，保留请求 | 3 / 192 |
| 59.5°C | 降温 | 已低于阈值，降低一级 | 2 / 128 |
| 59°C | 降温 | 再降低一级 | 1 / 64 |
| 58.5°C | 降温 | 再降低一级 | 0 / 0 |
| 57.9°C | 降温 | 已在下限，撤销该映射请求 | 0 / 0 |

它说明状态既取决于温度，也取决于上一轮状态和趋势；59.5°C 已开始降档，58.5°C 已到零档，迟滞没有把它锁到 58°C。温度稳定不变时，趋势为 STABLE，这份 step_wise 会保留原请求。若温度升到 85°C，还必须合并第二条风扇映射，并考虑同温区 CPU/GPU 请求，不能继续用这张单控制点表推算。

在 power_allocator 下，60°C 以下允许 power actor 使用最大功率，60°C 起按 85°C 目标计算功率预算，并设置 passive 更新状态；当前 pwm-fan 不具备该接口，因此这组温度不会按上表产生风扇档位。区分策略之后，才能判断要调整阈值、换策略，还是修复设备能力配套。

## 9.5 PWM 之后还要经过功率电路与机械响应

旧底板第 8 页的 CN1 为二线风扇供电接口。PWM0_M1 经 R81 接 U31 栅极，R82 下拉；U31 标为 AO3400，串在 +5 V 与风扇正端之间，风扇负端接地。它调制的是供电支路，和四线风扇的独立逻辑 PWM 控制不同。

这里存在具体的栅极驱动问题。[AO3400 原厂资料](https://www.aosmd.com/res/data_sheets/AO3400.pdf)将它定义为 N 沟道 MOSFET；按图中连接，漏极接 +5 V，源极接风扇正端。若实物按此装配、栅极仅由 SoC 的约 3.3 V 电平驱动，源极升高就会减小 `VGS = VG − VS`；源极要接近 5 V 时，VGS 已为负值，器件无法像理想高侧开关那样保持充分导通。结果可能是风扇端电压不足、起转失败或 MOS 额外发热。调高 cooling state 只延长同样驱动条件的作用时间，无法补出高于源极所需的栅极电压。

因此对这份图纸对应的实物，应把栅极与源极电压一并对照。只量到 PWM 引脚有 100 kHz，不足以解释风扇实际得到的电压；还要结合器件型号、装配连接、风扇对供电调制的适应性及起转条件分析。

当前节点没有测速 IRQ。驱动只有检测到 tachometer IRQ 输入时才建立 `fan*_input`、统计脉冲并换算 RPM；本配置只提供 PWM 控制量与冷却状态。`cur_state=4` 或 `pwm1=255` 描述软件请求，不表示已测得满转速。

风扇加速与温度下降还存在机械、热传导延迟。PWM 改变后，电机先改变转速，散热器与气流再影响芯片温度。判断散热效果应比较相近负载下的持续趋势；一次调档后下一次采样仍升温，可能只是热响应尚未完成，也可能是总散热能力不足。

## 9.6 从标准接口定位最早断开的交接

在目标 Linux 上先按 `type` 找对象，再把温区与冷却设备关联起来，不能假定编号一直为 0：

```sh
# 同时观察温度、实际策略、冷却状态；缺少的可选属性跳过。
for item in /sys/class/thermal/thermal_zone* /sys/class/thermal/cooling_device*; do
    [ -d "$item" ] || continue
    printf '\n%s\n' "$item"
    for key in type temp policy mode cur_state max_state; do
        [ -r "$item/$key" ] || continue
        printf '%s=' "$key"
        cat "$item/$key"
    done
done
```

没有 SoC 温区，先看 TSADC 注册；温度正常但没有风扇 cooling device，查模块、PWM 提供者与 probe。两端都有时，沿该温区的 `cdev*` 链接及 `cdev*_trip_point` 确认映射，再读实际 policy。当前 power_allocator 与状态式风扇不配套时，问题位于策略到设备接口，缩短轮询间隔不会修复它。

档位已变化而 PWM 没变，继续检查 `pwm1_enable`、PWM 申请结果和 pinctrl；波形已到栅极而风扇响应不足，转到源极电压、功率电路与起转条件；转动正常而温度仍持续上升，再评估热负载、散热器接触和气流。这样，每次观察都会把下一步留在真正有因果关系的节点。

## 9.7 核心工程问题与深度理解

### 9.7.1 为什么风扇一直高速转，反而可能说明自动温控没有接通

probe 默认先请求最大 PWM。若随后采用的 power_allocator 跳过非 power actor 风扇，或根本没有有效控制请求，初始化输出就可能一直保持。应把 policy、绑定和温度变化时的状态放在一起看，不能只看开机转动。

### 9.7.2 能否把迟滞从 2°C 改为 5°C，就保证这份实现减少风扇换档

不能直接得到这个效果。此基线 step_wise 的档位判断不读取 hysteresis，TSADC 也只设置高告警边界。先确认正在运行的策略怎样消费该属性，再决定改哪个控制条件；属性名称本身不是行为保证。

### 9.7.3 状态 2、PWM 128 与风扇半速有什么关系

状态 2 先查表得到 128，再按周期生成约 50.2% 的有效时间。电路输出电压、风扇启动与转速特性还在后面；本配置没有测速输入，所以无法从这个数值推出半速。旧图的高侧 N-MOS 驱动条件尤其可能使电压与理想占空比例偏离。

下一章[部署生效检查](10_部署生效检查.md)把这些机制放回启动选择：先确定运行内核与最终设备树，再查绑定、接口和各条外设链路的实际响应。
