# 13 关键资料阅读索引：从学习问题回到原始证据

前面各章建立了项目主线，本章用于回答“这个解释依据在哪里，接下来该读什么”。先确定正在研究的板型、屏幕、驱动和交付包，再沿生产者与消费者查资料；同名文件、同版本包或相同函数符号都不能独立证明对应关系。

本索引路径相对于学习目录。行号按 2026-10-13 本轮读取的文件辅助定位，长期检索优先使用节点、函数、属性或文档标题。源码、包内成员、硬件设计和历史操作记录分别说明各自能证明的范围；板端命令未执行的地方不预填结果。

## 13.1 先明确需要哪一种证据

如果问题是“为什么这样设计”，从正文与相应接线、属性、函数关系开始；如果问题是“当前板到底用了什么”，则从第 10 章的运行身份和最终设备树开始。两种阅读会使用相同资料，但结束条件不同。

| 要回答的问题 | 先读什么 | 再连接什么 | 到这里能形成的判断 |
| --- | --- | --- | --- |
| 为什么这条 GPIO 要这样控制？ | 实际板型对应原理图 | 设备树属性、驱动所用 GPIO API | 设计与软件解释是否一致，物理效果仍需测量 |
| 驱动为什么没有注册接口？ | 最终节点及绑定证据 | 对应分支 probe、资源与错误返回 | 找到初始化中断层级 |
| 一个触点为什么变成这个坐标？ | 芯片记录格式与驱动解码 | CFG 范围、变换、input 能力和桌面映射 | 分辨错误属于哪层 |
| 安装包包含什么？ | 确定哈希的原始包 | control、config、DTB、源码或 hook 成员 | 确定交付内容，不等于已启动 |
| 历史记录为什么与当前文件不同？ | 记录中的对象、环境和时间 | 当前源件或包内值 | 保留版本差异，不把某一方自动当作最终系统 |

[原有全局分析](../../全局架构与技术剖析.md) 保留为历史分析入口。它可以帮助定位问题，但关键结论应回到下列原件；本轮没有覆盖该原文档。

### 13.2.2 6 英寸和 7 英寸资料分别成组

7 英寸显示从 [阿美林规格书](<../../阿美林-1000nit-7inch/调试规格书 7inch 800x1280 MIPI AML070WXM31-1000 Shenzhen  Amelin  Electronic Technology  Co., Ltd..pdf>) 确认对象，再读 [ILI9881C 原始初始化表](../../阿美林-1000nit-7inch/初始化序列/BOE_7WX_ILI9881C_V04_20210507.txt)，最后对照 [转换序列](../../阿美林-1000nit-7inch/初始化序列/panel_init_sequence.txt) 与产品 overlay。三者分别回答“器件要求什么”“怎样发命令”“当前文件描述了什么”。

云奥 [6 英寸规格书](<../../云奥-270nit-6inch/L6.0-1-2-A规格书160728解密 (1).pdf>) 和 [初始化表](<../../云奥-270nit-6inch/6.0-1MIPI CODE (1).txt>) 属于另一面板。两者都可能使用 MIPI 和 Goodix 触摸，但这些共同词不足以支持交换面板时序、初始化序列或 CFG。

触摸源码放在某个屏幕目录下，只能说明资料归属。它是否进入某次内核构建，还须通过 13.3、13.5 的包内和源码关系核对。

遇到缩写相近的材料，先分清配置对象：ILI9881C 初始化表发给面板内的 ILI9881C；GT911 CFG 配置触摸控制器；CW2015 profile 对应电池模型。三者都可能表现为一串十六进制数，但接收器件、传输路径和生效条件完全不同，不能按文件格式相似就互相类比执行过程。

### 13.3.2 内核包：按“编了什么、描述什么、怎样安装”查成员

以下是 [linux-image 包](../../debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb) 内部路径，不是 Windows 主机已经安装的路径，也不是当前板端文件快照。列表工具可能显示或省略前导 `./`。

| 包内成员 | 对应的阅读任务 |
| --- | --- |
| `boot/config-6.1.84-12-rk2410-nocsf` | 查 GT9XX、CW2015、charger、panel、backlight、风扇等编译选择和默认 thermal governor |
| `boot/System.map-6.1.84-12-rk2410-nocsf` | 找 `goodix_ts_probe`、`goodix_ts_work_func`、`gtp_dat_gt9112`、`panel_simple_prepare`、`cw_bat_work` 等链接符号 |
| `usr/lib/linux-image-6.1.84-12-rk2410-nocsf/rockchip/rk3566-radxa-cm3-io.dtb` | 比较平台身份、控制器启用状态、风扇和 thermal 配置 |
| `lib/modules/6.1.84-12-rk2410-nocsf/kernel/drivers/hwmon/pwm-fan.ko.xz` | 与 `CONFIG_SENSORS_PWM_FAN=m` 交叉核对模块交付 |
| 控制档案中的 `control`、`postinst` 及其他维护脚本 | 看包身份、依赖和目标系统 kernel hooks 的调用阶段 |

包配置可确认：`CONFIG_TOUCHSCREEN_GT9XX=y`、`CONFIG_TOUCHSCREEN_GOODIX=m`、`CONFIG_INPUT_EVDEV=y`，未设置 `CONFIG_CHROME_PLATFORMS`；CW2015 和 gpio-charger 配置为内建，风扇为模块。默认 thermal governor 为 `power_allocator`，并提供 `step_wise` 能力。默认值和可用能力不能替代实板当前 zone 的策略。

基础 DTB 大小为 163769 字节。离线解析可见 HDMI、route_hdmi、PCIe2x1、SDMMC0 为 disabled；I2C1、I2C3、PWM5、DSI0 也需要产品配置启用；`__symbols__` 保存相关目标标签。风扇使用 PWM0_M1 / GPIO0_C7，档位为 0、64、128、192、255；相关 passive trip 为 60℃、85℃，均带 2℃ 滞回。

这些属性回答基础包是什么，不能直接回答 overlay 合并后的最终树，更不能从两个温度值推导出简单风扇开关逻辑。第 04、09、10 章分别解释组合、策略和运行验证。

### 13.3.3 overlay 包：把安装脚本和构建回调分开

普通包与 PWM 包的数据档案共同前缀是 `usr/src/radxa-overlays-0.2.4/`。以此前缀阅读：

| 相对包内路径 | 它在交付过程中的作用 |
| --- | --- |
| `dkms.conf` | DKMS 名称、版本、自动构建设置和回调入口 |
| `dkms.post_build` | 按内核版本与架构保存构建的 DTBO |
| `dkms.post_install` | 链接目标内核 overlay 目录，并在可用时调用 rsetup |
| `dkms.post_remove` | 对应移除阶段；本任务仅阅读，不执行 |
| `Makefile` | 顶层构建组织 |
| `arch/arm64/boot/dts/rockchip/overlays/Makefile` | Rockchip 插件目标 |
| `arch/arm64/boot/dts/rockchip/overlays/aircas-compact-GCS.dts` | 普通产品描述，两个包均包含 |
| `arch/arm64/boot/dts/rockchip/overlays/aircas-compact-GCS-pwm.dts` | PWM 包额外成员，含 197 项亮度表 |

控制档案中的 `postinst` 负责进入 DKMS 生命周期；上表数据档案中的 `dkms.post_install` 是构建后的回调，两者名字相近但阶段不同。后者遇到目标内核不支持相应 vendor，或已有实际 overlay 目录等情况会跳过，不能把“执行包安装”直接等同为“所需 DTBO 已进入引导选择”。

### 13.3.4 在已有 Debian/Ubuntu 环境中只读核对

下面是**未在目标板执行的只读示例**。假设 shell 当前目录为项目根，已具备 `dpkg-deb`、`tar`；命令读取包，不安装包，不执行内部维护脚本。参数含义可查 [Debian dpkg-deb 手册](https://manpages.debian.org/bookworm/dpkg/dpkg-deb.1.en.html)。

```sh
# 看内部身份，不能只依据文件名中的 pwm 或版本后缀。
dpkg-deb --field debs/radxa-overlays-dkms_pwm.deb Package Version Architecture Depends

# 查找真实成员名称，随后才按该名称读取。
dpkg-deb --contents debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb | grep -E 'rk3566-radxa-cm3-io.dtb|pwm-fan.ko'

# 将配置成员输出到终端，仅筛选相关编译条件。
dpkg-deb --fsys-tarfile debs/linux-image-6.1.84-12-rk2410-nocsf_6.1.84-12_arm64.deb | tar -xOf - ./boot/config-6.1.84-12-rk2410-nocsf | grep -E 'CONFIG_TOUCHSCREEN_GT9XX|CONFIG_SENSORS_PWM_FAN|CONFIG_CHROME_PLATFORMS|CONFIG_THERMAL_DEFAULT_GOV'
```

三条命令依次回答内部身份、成员存在、编译条件。第三条先把数据档案交给 `tar`，再用 `-xO` 将指定成员写到标准输出，最后由 `grep` 筛选配置行，不会把成员安装到系统。没有匹配输出时先看前级是否报了包路径或成员名错误，再判断配置是否缺失；不要把管道末端没有文字直接当成“未编译驱动”。读取别的成员时先列目录取得准确路径。任何一条都不回答当前板上是否绑定成功。

## 13.4 理解设备树：沿“基础资源到产品消费者”阅读

不要从 overlay 第一行一直背到最后一行。先找基础资源的提供者，再看产品节点怎样引用它，最后到驱动确认属性是否被消费。

| 阅读顺序与入口 | 关键定位 | 应带着的问题 |
| --- | --- | --- |
| [CM3 DTSI](../../src/rk3566-radxa-cm3.dtsi) | 第 10 行附近 include，113 行附近 IO 域，后续存储/网络/UART/VOP | 哪些属于核心板公共资源？哪些 SoC include 仍由完整内核提供？ |
| [CM3 IO DTS](../../src/rk3566-radxa-cm3-io.dts) | `fan0` 约 86 行、`sdmmc0` 约 173 行、PWM0/pinctrl、`soc_thermal` 约 242 行 | 参考 IO 板怎样分配引脚、供电和散热资源？ |
| [AIRCAS overlay](../../设备树包/aircas-compact-GCS_overlay.dts) | metadata 约 11 行，供电 26/40 行，背光 54 行，电池 100 行 | 产品增加哪些消费者，引用哪些提供者？ |
| 同一 overlay | `dsi_panel` 约 120 行，序列 146—339 行，时序约 349 行 | DSI 面板需要哪些独立条件？ |
| 同一 overlay | `i2c1` 约 391 行，`i2c3` 约 412 行，route 约 438 行 | 触摸、电量和显示路由怎样接到基础控制器？ |
| [历史 v1 片段](../../设备树包/rk3566-radxa-cm3-io_v1.dts) | 文件开头与屏幕节点 | 哪些是历史修改线索，而非可独立编译入口？ |

本轮再次计算副本哈希：`src/` 的 CM3 `.dtsi`、对应 `.txt` 与 `设备树包/` 副本分别一致；IO `.dts`、对应 `.txt` 和包目录副本也分别一致。它们可以交叉检查，但不能证明某个副本就是完整构建系统的唯一来源。

普通 overlay 包内产品 DTS 与工作区 overlay 按行归一化后一致，原始字节差异来自 LF/CRLF。PWM 变体的亮度表则是实质配置变化。基础源码与包内 DTB 在 HDMI、PCIe、SDMMC0 和部分供电节点上另有差异，因此必须区分“文本副本相同”和“构建产物等价”。

## 13.5 理解屏幕与触摸：把命令、采集和事件分别对应

### 13.5.1 显示先读原始要求，再看转换结果

沿 13.2.2 的 7 英寸材料，重点对照原表末尾 `0x11 → Delay 120 → 0x29`。产品 overlay 有 194 条初始化记录；转换文本还含额外的显示开启记录，不能只按同一目录认定它们逐条一致。Word 中“屏幕初始化序列”的 `15 78 02 11 00` 示例，也应与当前 overlay 的实际延迟位置分开读。

这一任务最终要回答：等待约束的是哪两个事件，转换格式的延迟字段何时被执行。第 06 章已给出条件解释；当前仓库缺少对应 BSP 的完整 panel 解析器，不能仅借上游代码补齐本项目全部回调顺序。

[7 英寸 GT911 CFG](../../阿美林-1000nit-7inch/GT911_700190_20191129_164215_800_1280_V96.cfg) 则属于触摸参数。文件共 186 字节，首字节配置版本为 `0x60`（十进制 96），范围为 800×1280；除末尾 fresh 标志外，包含校验字节的 185 字节累加模 256 为 0，fresh 为 1。这里“模 256”就是只保留总和低 8 位；校验成立说明数据满足这一内部条件，不证明驱动已经选中并下发这份配置。

### 13.5.2 旧 V2.2：从注册一路读到释放事件

先读 [旧 gt9xx.h](<../../云奥-270nit-6inch/mipi_touch (1)/mipi_touch/gt9xx.h>) 的版本宏和第 60—64 行条件宏，再沿 [旧 gt9xx.c](<../../云奥-270nit-6inch/mipi_touch (1)/mipi_touch/gt9xx.c>) 阅读下表。这样可以避免先看 slot 函数，就把未必启用的代码当作实际路径。

| 问题 | 函数与辅助行号 | 连接到下一处 |
| --- | --- | --- |
| 驱动怎样进入系统？ | `goodix_ts_init()` 3204；匹配表 3182 | 全局 workqueue、I2C 注册，再到 probe |
| 芯片如何取得资源？ | `goodix_ts_probe()` 2630 | 电源、GPIO、配置和 input 注册；对照 overlay 属性 |
| 复位为什么操作 INT？ | `gtp_reset_guitar()` 1104 | 地址选择之后才能解释 I2C 是否应答 |
| 通知由谁采集？ | `gtp_request_irq()` 1905；回调 1066；定时器 1045 | 本地线程化 IRQ 回调和定时器都继续投递 workqueue |
| 读取成功怎样判断？ | `gtp_i2c_read()` 157；工作函数 581 | 两消息返回值，状态 784—801，再到 808 行续读 |
| 坐标和触点怎样上报？ | `gtp_touch_down/up()` 422/470；事件分支 894—1018 | CFG 范围、轴变换、Type A/B、释放和同步 |
| 失败或退出怎样处理？ | probe 尾部 2877；remove 2896 | 资源账本、在途 work 与托管/手工回收 |

[旧 Makefile](<../../云奥-270nit-6inch/mipi_touch (1)/mipi_touch/Makefile>) 用于核对对象组合，不能替代父级构建工程。头文件还引用当前缺失的 `../tp_suspend.h`；本地历史 `.o` 为 ELF32/ARM，不能当作 ARM64 最终驱动交付物。

实际阅读时，可以只追一个量，避免在数千行代码里失去方向。例如先找 probe 中 `max-x` 的读取，再看结果是否真正赋给 `ts->abs_x_max`；此处赋值已注释，就继续找这个字段在 `gtp_init_panel()`、`gtp_get_info()` 等路径中的来源，最后到输入注册处看 `input_set_abs_params()` 使用了什么范围及是否交换两轴。只有把“读取、有效赋值、后续覆盖、最终消费者”连起来，才知道修改属性能否改变上报范围；搜索到属性名还只是第一步。各分支是否执行仍须结合条件宏和返回值，详见第 05、07 章。

## 13.6 电量、温控与历史记录怎样相互校验

电量先读旧底板第 4 页，确定测量、外部在线检测与充电电路；再读 overlay 的 `simple-battery`、`gpio-charger` 和 `cw2015@62`；最后回到 Word 中 profile 来源。温控先读 IO DTS 与包内 DTB 的 zone/trip/cooling map，再结合 PWM 和实际风扇电路，不能从温度记录跳过 governor。

Word 段落编号不是稳定页码。以下短语比临时提取文件中的序号更适合定位：

## 13.7 对通用参考和未闭合关系保持明确边界

各章引用 Linux v6.1 上游文档或源码，用于解释 input、GPIO、devres、power_supply、thermal 等机制。它们帮助理解“某种机制如何工作”，不能自动替代 Rockchip/Radxa BSP 的匹配实现。

后续继续研究时，以下缺口决定应索取或采集什么：

| 尚缺的关系 | 需要的材料 | 得到之后才能回答 |
| --- | --- | --- |
| 源码到内核包的完整对应 | 内核提交、补丁集、配置及构建记录 | 本地函数和参数是否确实进入这个包 |
| panel 描述到具体执行 | 配套 panel 解析器、生命周期和恢复源码 | 命令延迟及 GPIO 操作在本 BSP 中怎样执行 |
| CW2015 属性到读数 | 配套完整驱动和实际电池信息 | 双节换算、profile 应用、缓存和恢复机制 |
| 包产物到一次启动 | 引导配置、启动日志、最终树与运行内核 | 这次启动究竟采用哪套组合 |
| 标准接口到应用消费 | 实际 RootFS 配置与应用源码/日志 | 图像、输入、电量如何进入具体地面站功能 |

相机、WFB-NG、ROS、QGC 和飞控接口仍按现有资料解释集成位置与缺失条件。内核配置中启用相关能力，不能补成已经完成采集、图传、遥测或业务联调。

## 13.8 自查与回答要点

### 13.8.1 自查题

1. 要解释某 GPIO 的高低电平，为什么应先确认原理图版本，再查 DTS 和驱动 API？
2. 两个 overlay 包都显示 0.2.4，怎样证明它们是否相同？同样的哈希又不能证明什么？
3. 找到包内 `goodix_ts_probe` 后，为什么还要继续找对应源码和补丁？
4. 某一源码行号失效后，怎样继续定位而不误换版本？
5. 想查“插电但电池不充电”，怎样用本索引避免只围着 CW2015 驱动排查？

### 13.8.2 回答要点

1. 不同底板可把同一个 GPIO 分给不同电路；DTS 和 API 还可能解释逻辑有效值。只有对象和语义都对应，物理电平推导才成立。
2. 比较原包哈希和内部成员；本项目两包确实内容不同。同哈希识别同一文件，仍不证明当前板已安装或启动其中内容。
3. 符号只提供函数名字，不能证明函数体、宏、配置数组和调用者相同。包内额外的 `gtp_dat_gt9112` 也是继续核查修改版本的线索。
4. 先确认文件身份，再按函数、节点、属性或文档标题检索，最后更新辅助行号；不能为匹配行号改用另一分支。
5. 从第 4 页电源电路区分在线检测、采样与实际充电通道，再对照第 08 章和运行对象。外部在线或电量读数不能代替充电电流证据。
