# 12 项目讲解提纲

这份提纲用于把前面的机制组织成一次约 15～20 分钟的讲解。先用系统地图确定职责，再以触摸走完一条链，随后比较显示、电源与温控的不同数据和控制方式。需要函数、节点或包成员时，使用[资料索引](13_关键资料阅读索引.md)展开。

```text
CM3 与底板分工 -> 硬件资源怎样表达 -> 触摸初始化与一次事件
                                           |
                 +-------------------------+----------------------+
                 v                         v                      v
        显示的像素/命令/背光       电量的采样/缓存/属性       温控的策略/档位/执行器
                 +-------------------------+----------------------+
                                           v
                              构建交付与启动选择 -> 故障推理
```

## 12.1 用硬件职责建立系统地图

开场可以这样说明：

> CM3 提供计算、存储与 SoC 控制器，自定义底板把控制器接到屏幕、触摸、电量计和风扇，并提供电源开关及负载电路。板级适配把这套具体接线写成设备树，让驱动取得资源、初始化器件，再通过 Linux 标准接口交给上层。

随后指向[第 01 章](01_项目总览.md)的三种流程。构建处理源码与文件，初始化处理提供者与消费者的依赖，运行处理事件与请求。它们在产物和接口处衔接，内核、RootFS 和多个外设都有独立支线。

到这里，听者应知道设备树描述“在哪里、依赖谁”，驱动实现“怎样操作”，子系统规定“怎样交付”。将板型与屏幕组合讲清后，才进入具体 GPIO 和函数。

## 12.2 以一次触摸贯通资源、执行与数据

### 12.2.1 从接线到 probe

触摸需要供电、I2C、复位和 INT。产品 overlay 将它接到 I2C1、地址 0x14，INT/RST 为 GPIO0_C5/C6，供电引用 `vcc_lcd_tp`。INT 既在启动时参与地址选择，也在运行时通知读取触点；这就解释了为什么复位错误可能表现成 I2C 无应答。

以[第 05 章](05_驱动匹配与初始化.md)的本地 V2.2 为源码样本：总线控制器建立 adapter，内核根据有效子节点创建 client，驱动注册并匹配后进入 `goodix_ts_probe()`。probe 依次建立状态、解析资源、取得供电和 GPIO、复位选址、检查通信、配置器件并注册输入能力，再建立 IRQ 或轮询路径。

每个阶段都说明交付物：供电和复位给 I2C 建立工作条件，通信给 CFG 和范围读取提供数据，input 注册给上层建立事件解释方式。资源未就绪时，错误必须正确传播；释放状态前，则要先收束仍会使用它的 IRQ、timer 和 work。

两套供应商驱动与交付修改分别有自己的属性和配置选择。本地 V2.2 的 `tp-size` 分支没有 overlay 的 9112，讲解正常机制时应使用它实际处理的配置路径；产品对应关系继续沿构建记录与包内内容辨认。

### 12.2.2 让一份触点记录一直走到 evdev

可以连续口述：

> 手指变化发生在控制器里，INT 只通知 CPU。旧驱动的 IRQ 回调屏蔽本设备中断并投递 work，工作线程用 I2C 读取 0x814E 的状态和触点记录。先检查就绪位和触点数，多点时继续读取，再按每点 8 字节解释 ID、X/Y 和接触量。
>
> 驱动按当前分支变换坐标，提交 input 事件，并用同步边界结束一帧。正常尾部确认器件状态再恢复 IRQ。evdev 把标准事件交给用户空间，桌面随后将输入位置映射到显示和窗口。

用[第 07 章](07_触摸与input.md)的连续例子说明按下、移动和释放。Type A 通过逐点同步与完整帧表达接触，Type B 用 slot 保存触点身份并释放消失 ID；两条分支由实际宏或属性选择。控制器坐标、驱动范围、轴变换和桌面方向属于不同位置，旋转画面不会自动旋转整个输入链。

### 12.2.3 用执行上下文和失败分支讲设计取舍

I2C 可能等待或睡眠，需要线程上下文。旧路径增加一次 workqueue 投递，换取队列内串行执行；V2.8.7 IRQ 线程直接采集，少一次排队，但仍要检查自己的状态与退出同步。函数名带 `work` 不决定上下文，其无 IRQ hrtimer 直接采集就是具体反例。

再选一个数据完整性问题解释可靠性：旧 I2C 读取完整成功返回 2，含义是完成两条消息；续读不检查返回值会让不完整帧继续解析。错误帧、前帧触点状态和释放事件相互关联，所以处理失败不能只看“有没有打印错误”。

## 12.3 比较另外三种运行链

### 12.3.1 显示分别追像素、面板准备与照明

显示缓冲区经 DRM/VOP/VP 组织扫描，通过 DSI Host/PHY 送到 panel；endpoint 与 route 描述这条连接。供电、复位及初始化命令建立面板接收条件；PWM5 和使能电路另行提供背光。

选择两处数值讲清层次即可：854×1314 总周期与 67.3 MHz 对应约 59.974 Hz；默认亮度 200 是索引，197 项表会被配套公开驱动钳到 196，再取表值 255。像素时钟不是 lane 比特率，控制值也不是光学百分比。

面板命令中的延时位置同样属于语义。厂商要求 Sleep Out 后等待再 Display On，而当前 overlay 把 120 ms 放到后一记录；公开基线在发送记录后等待，故两者顺序有实质差异。把这个条件放回“背光亮但无图”的排查，能说明为什么不能只看灯已亮。

### 12.3.2 电量把测量、模型和缓存交给属性接口

`simple-battery` 提供容量等静态参数，CW2015 的 profile 配置芯片模型，周期任务读取电压和 SOC，gpio-charger 则检测外部输入。硬件充电电路独立承担能量流动。

沿同一笔数据讲一次：电池 7.6 V 经等值分压约为 3.8 V，VCELL 码经过三次平均、mV 换算及双节补偿，属性再以 µV 输出。后台每轮完成后延迟 5 秒重排，sysfs 返回缓存；I2C 失败时旧值可以继续存在。由此解释“读接口很快”和“数据足够新”是两个问题。

外部 ONLINE 可立即通知，CW2015 下一轮才组合 SOC 推导 Charging/Full。设计容量改变的是部分派生量，profile 才进入芯片配置，软件 Charging 又没有直接测充电电流。这些对象各自负责一段明确工作。

### 12.3.3 温控增加了策略与执行器能力的匹配

TSADC 把温度交给 zone，governor 根据 trips 与 map 请求冷却，pwm-fan 把状态索引映成控制量，PWM 驱动输出波形，风扇与散热结构改变后续温度。CPU/GPU 降频减少发热，风扇增强散热，是不同冷却设备。

当前包默认 power_allocator，公开基线的普通 pwm-fan 却没有功率模型回调，策略会跳过它。若运行 step_wise，还要按它的趋势与前次状态解释调档，其代码没有直接按 2℃迟滞控制档位。因此“60℃开、58℃关”不是当前配置可直接推出的规则。

状态 2 对应 PWM 128，10 µs 周期得到 5020 ns 有效时间；后面的功率电路、起转和转速仍有各自条件。当前没有测速输入，这个数值描述请求，不能拿来报 RPM。

## 12.4 回到交付，说明修改怎样进入设备

内核工程按配置生成内核、模块和基础 DTB；overlay 工程提供源码包，DKMS 同时构建插件和占位模块，hooks 保存、链接 DTBO；RootFS 提供程序、配置和系统 hooks。占位模块只打印日志，不负责应用 overlay。

接着沿[第 10 章](10_部署生效检查.md)把同一个产物追到底：包内文件 → 安装位置 → 实际启动项 → 运行内核与最终树 → driver → 接口行为。内建 GT9XX 更新需要更换内核，模块 pwm-fan 还包含装载，DTBO 更新则改变驱动读取的描述。

用当前差异说明为何要保存配套关系：两个 overlay 包都叫 0.2.4，却有不同亮度表；本地 DTS 与交付 DTB 的 SDMMC0 状态不同。发布记录要保留硬件、基线、本地补丁、配置、包哈希和插件选择，才能解释下一台设备。

## 12.5 用一个故障展示推理方式

选择“触摸有事件但点击错位”。先固定底板、屏幕、内核和最终配置，按 input 范围确定四角预期，再比较 evtest 与桌面命中位置。

input 正确而桌面错位，下一步查用户态映射和重复旋转；input 已错，返回 CFG、驱动范围和变换。evtest 位于驱动之后，继续区分芯片输出与驱动变换时，需要解析前后的诊断。这里最关键的是每个结果都会改变检查方向。

需要换案例时，黑屏比较照明与像素链，电量停住比较后台采样与缓存，风扇不响应比较策略接口与物理输出。使用[第 11 章](11_故障排查与验证.md)的观察点展开，无需把所有命令再讲一遍。

## 12.6 按追问进入原件

| 追问方向 | 展开位置 | 应拿出的具体对象 |
| --- | --- | --- |
| 某个属性到底生效在哪 | 第 04、05、07 章 | 属性读取、保存、覆盖与最终消费者 |
| 一笔数据怎样改变输出 | 第 06～09 章 | 触点记录、亮度索引、VCELL 码或冷却状态 |
| 失败后为什么残留状态 | 第 05、07、08 章 | 返回值、前帧/缓存、异步任务和回收次序 |
| 换包后为什么行为不同 | 第 02、10 章 | 包成员、kernel release、链接及最终树 |
| 当前结论适用哪个版本 | 第 13 章 | 本地文件、公开固定提交、包哈希和硬件图页 |

讲解时保持同一对象前后连贯：一条实际连接成为一个资源，一次资源申请支撑一次事务，一份数据变成一个标准接口结果。听者追问到哪一层，就沿对应入口继续，而不跳到另一版本的相似函数。
