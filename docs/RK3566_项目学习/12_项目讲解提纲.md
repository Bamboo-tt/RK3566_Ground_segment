# 12 项目讲解提纲：从架构讲到一次完整适配

这份提纲用于把前面各章组织成一段连贯说明。可以按下面顺序讲 15～20 分钟，再沿听者的追问进入源码。重点不是背出所有目录，而是让每一段自然回答上一段留下的问题。

## 开场：先说明成果和边界

可以这样开始：

> 这个项目为 Radxa CM3/RK3566 手持地面端提供板级适配。核心板提供计算与控制器，自定义底板连接高亮屏幕、触摸、背光、电量计和风扇。软件工作是把实际接线和器件需求转换成设备树与驱动行为，再通过 Linux 标准接口交给桌面及应用。
>
> 当前资料覆盖设备树、两套触摸驱动、交付包和硬件调试记录，缺少完整 BSP 工程及地面站应用源码。因此我能讲清外设如何接入系统，也能指出构建和运行证据缺口；图传、遥测与任务管理仅说明未来集成位置。

这里先区分产品目标和材料覆盖范围，再进入架构。不要从“项目用了 C、Linux、I2C”开始罗列名词，因为听者还不知道这些技术在解决什么问题。

## 第一段：用一条主线讲清分层

指向[项目总览的三种流程](01_项目总览.md)，先讲硬件连接与供电，再讲硬件描述，随后是驱动、子系统和消费者。

**关键解释：** 核心板有控制器不代表外设已可用；还需要底板接线、电压与时序。设备树把这些条件描述给内核，驱动按对应属性取得资源并操作器件，子系统则让上层使用统一事件或状态接口。

可以用下面的因果关系衔接：

> 我们不希望桌面知道 GT911 每个寄存器的含义，所以让驱动完成通信和解析，通过 input 上报事件。相同原则也用于背光与电源状态：上层请求亮度或读取供电属性，底层负责映射到具体 PWM、GPIO 或 I2C 操作。

设计收益是分工与复用；代价是各层契约必须一致。属性拼错、驱动分支不配套或坐标系重复变换，都会让分层之间的交接失效。

**可能追问：为什么不用应用直接读写 GPIO/I2C？**

回答要点：直接访问可用于有明确条件的实验，但产品链路还需要设备生命周期、输入事件标准化、电源管理、并发和恢复。现有内核子系统已经组织了这些接口；绕过它们会把资源所有权和同步责任转移到应用。

## 第二段：先把屏幕拆成三条通道

> 屏幕不是一个单一外设调用。图像从 DRM/VOP 经 DSI 到 panel；触点从控制器经 I2C 进入 input，中断线只负责通知；背光通过 PWM 和使能电路控制照明。这三条链最终形成同一个使用体验，但任何一条成功都不能替代另外两条。

接着结合[显示与背光](06_显示与背光.md)说明：route 和 endpoint 决定图像连接；供电和 reset 建立硬件条件；初始化表配置面板并退出睡眠；时序决定每行、每帧怎样扫描；背光用独立映射控制照明。

用一个参数说明理解即可：67.3 MHz 不是“屏幕每秒刷新 6730 万次”，它是像素时钟，计算帧率还要除以含消隐区的总列数与总行数。亮度 200 也不是天然的 200/255 光学亮度，它首先是亮度表索引。

**可能追问：背光亮却黑屏，先怀疑什么？**

回答要点：已有照明不等于面板和像素链正常。先确认当前板型及最终配置，然后依次判断面板供电、复位、命令等待、显示路由与模式。当前命令延迟差异是有条件的静态线索，不能直接替代当前故障证据。

## 第三段：选择一套触摸代码，走完真实调用链

主讲分支选用云奥资料中的本地 V2.2。先声明这是可读源码样本，与包内旧家族符号相近，但未取得打包内核对应的完整修改源码。

### 从接线走到初始化

触摸芯片需要电源、I2C、RST 和 INT。产品 overlay 把它写在 I2C1 下，声明地址 `0x14`、GPIO、`tp-supply` 和产品参数。基础 DTSI/DTS 与 overlay 合并后，内核依据有效节点建立设备，I2C 驱动匹配后执行 `goodix_ts_probe()`。

probe 取得供电和引脚，完成复位、地址选择和通信检查，再准备配置与 input 能力。这里要强调：当前 overlay 的 `tp-size=9112` 不在本地旧分支显式列表里；两套 GT9XX 的属性接口也不同。它们展示真实的适配问题，不能为了讲通流程就假定配套已完成。

讲到这里，可以指出“节点存在 → 节点可用 → 驱动已编译 → 绑定成功 → 事件正确”的五层区别，详见[第 05 章](05_驱动匹配与初始化.md)。

### 从一次通知走到上层事件

本地旧代码使用线程化 IRQ 注册，但 IRQ 回调还会禁用通知并投递单线程 `goodix_wq`。采集在 work 函数中进行：读取 `0x814E` 的状态与首个触点，先检查就绪位和数量，多点时继续读取，解码 ID/X/Y，再做轴交换或反转并报告输入事件。

中断不含坐标；I2C 读取可能等待和重试，所以执行上下文必须允许这些操作。workqueue 的收益是串行化采集，代价是增加排队和调度时间。I2C 重试、复位还会拉长一次处理，不能认为每次 IRQ 都保存了一份独立完整帧。

继续说明 Type A 与 Type B 是编译或配置分支。Type B 用 slot 保持触点身份，缺失触点要释放；Type A 逐点分隔再结束一帧。`input_sync()` 形成同步边界，input/evdev 把标准事件交给用户态。桌面如何映射到界面，是下一层消费者行为。

### 再对比另一套分支，而不把函数接进去

V2.8.7 的 `gtp_irq_handler()` 在线程化 IRQ 中直接调用 `gtp_work_func()` 和 `gtp_get_points()`，省掉旧链路的额外 workqueue 投递。它的 GPIO 名、供电名、状态与配置模型也不同。

还应说明，同名 `work_func` 不保证一定在工作队列运行：V2.8.7 的无 IRQ 定时器也直接调用它，因而出现普通 hrtimer 上下文与可睡眠 I2C 路径不匹配的静态风险。这个例子展示了为什么审阅调用者比只看函数名更重要。

**可能追问：恢复函数走完，为什么还会没有触摸？**

回答要点：代码允许上报只改变软件状态，芯片供电、通信、有效触点和上层消费还要分别成立。V2.8.7 恢复失败后仍可重新允许 work，正是不能以状态位替代硬件证据的例子。

## 第四段：把电源监测和温控放回各自控制关系

电源侧用一句话串起来：`simple-battery` 描述电池对象，CW2015 读取电量相关状态，`gpio-charger` 描述外部输入在线，`power_supply` 将这些对象呈现给上层。实际充电由硬件充电通路完成；外部电源存在既不等于正在充电，也不证明 SOC 模型准确。

随后用一个具体边界加深解释：当前 64 字节 profile 与 Word 的 FEB 6 Ah 数据相同，但仍需确认实物电池与该模型相配。没有匹配 CW2015 源码，就不能编造 `dual-cell` 的实际换算函数和 5000 ms 属性的消费路径。

温控侧按温度采集、zone/trip、governor、cooling map、pwm-fan 和 PWM 输出讲。60℃和85℃是控制描述中的两个 passive trip，不是简单开关点。风扇档位是表索引，PWM是控制波形，电机转速是物理结果。

当前包把 pwm-fan 编为模块，还需要配套加载和绑定；默认 power_allocator 也要与实际 cooling device 能力配套。讲到这里，应指出本项目尚缺真实 policy、波形和风扇响应证据，而不是宣布风扇闭环已完成。

## 第五段：解释这些适配如何进入交付物

现在回到[第 02 章](02_BSP构建与交付.md)，回答听者自然会问的问题：“代码与设备树有了，怎样放到板上？”

内核工程生成内核、模块与基础 DTB，并包装为 Debian 包；overlay 工程制作源码包，借助目标内核环境的 DKMS 生命周期生成并安装 DTBO；镜像工具组织 RootFS、启动内容和指定包。它们在镜像制作或已有目标系统中汇合。

安装脚本会调用 hooks，overlay 安装可能触发 rsetup 重建；但实际启动选择仍需检查。包已安装、DTBO已生成、插件已被选中、最终树已应用、驱动已绑定和接口可用，是一组相互依赖但不同的结果。

用现有材料的差异结束这一段：普通与 PWM overlay 两包同版本但内容不同；基础源码与包内 DTB 的 SDMMC0 等状态不同。可重复交付需要把硬件版本、源码/补丁、配置、包哈希和启用组合关联起来。

## 第六段：用一个故障案例展示分析能力

任选“背光亮但无图像”或“input 正常但点击位置错误”，按下表讲，而不是现场罗列一屏命令。

| 讲解步骤 | 应讲出的内容 |
| --- | --- |
| 描述现象 | 发生条件、范围和可以重复的输入 |
| 固定对象 | 板型、面板、运行内核、最终树和驱动分支 |
| 定位层级 | 哪一层已有证据，哪一层还没有 |
| 提出原因 | 与当前版本和调用链一致的候选解释 |
| 选择检查 | 结果为A时查哪里，为B时查哪里 |
| 给出结论 | 能证明的范围、仍未排除的条件及后续证据 |

例如 input 坐标正确、桌面位置错误，支持向桌面变换继续查；它不能证明所有触摸分支都没问题，但足以阻止本轮无依据地修改 CFG。排查的效率来自这一判断分叉。

## 收束：说明已经理解什么，还需要什么

可以这样结束：

> 我可以从器件接线解释设备树资源，再沿具体驱动分支说明初始化和运行时处理，最后定位标准接口与上层使用位置；也能解释构建产物如何组合，以及版本不一致会怎样影响判断。
>
> 当前掌握的是源码、包和资料层证据。要把它提升为当前整机功能验证，还需要确认实物、运行版本、有效设备树、驱动绑定、真实事件或读数及消费者结果。缺失部分已经整理为可执行的检查步骤，而没有写成已完成结论。

## 自查：脱离提纲后还能否回答

1. **若只允许画三张图，画什么？** 构建交付、上电初始化、运行时外设链；每张保持执行者和时间尺度一致。
2. **哪一条链最适合证明自己读过源码？** 选择明确版本的触摸链，从 IRQ 注册方式到上下文、状态检查、触点解析、Type A/B和同步帧，再解释错误分支。
3. **最值得说明的设计取舍是什么？** 描述与驱动分离提高复用但要求属性契约一致；异步或线程化采集允许等待但引入调度与同步责任；标准子系统减少上层硬件依赖但仍需验证消费者关系。
4. **被问“现在全部外设都正常吗”怎样回答？** 先说证据层和验证范围；列出已读配置及包内能力，再指出没有当前实板结果支撑全面结论。
