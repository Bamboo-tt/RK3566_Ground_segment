# 12 项目讲解提纲

前面各章分别解释构建、接线、驱动和运行机制。本章把它们重新连成一次完整讲解：先建立听者的系统地图，再用触摸这一条有本地源码的链路展示适配过程，随后扩展到显示、电源、温控、交付和故障判断。

可以按这一顺序讲 15～20 分钟，追问时再进入具体文件。讲解重点是让后一段自然回答前一段留下的问题，不能用大量函数名替代原理。以下场景是组织讲解的方法，不是本次整机实测记录。

## 12.1 从使用需要建立项目地图

开场先说明产品需要，再交代当前工程承担的部分：

> 这个项目面向 Radxa CM3/RK3566 手持地面端。CM3 提供计算、存储与片上控制器，自定义底板把这些能力接到屏幕、触摸、电量计、背光和风扇，并提供相应供电与负载电路。板级适配要让 Linux 认识这套具体连接，驱动器件，再向桌面和应用提供标准接口。
>
> 当前仓库包含设备树、两套触摸代码、交付包、硬件资料和构建记录。我可以据此讲清外设适配及其交付关系；完整 BSP、最终 RootFS 和地面站应用源码尚未包含在材料中，图传、遥测和任务管理需要另外的实现证据。

接着使用[第 01 章](01_项目总览.md)的三张图。构建图回答文件从哪里来，初始化图回答工作条件怎样建立，运行图回答事件怎样流动。不要把生成镜像、执行 probe 和读取触点排成一条应用调用链。

此时听者应能理解最基本的分工：硬件描述“有什么、在哪里”，驱动“怎样操作”，子系统“怎样统一表达”，上层“怎样使用”。技术选型的收益是复用，代价是每一层的资源与数据约定必须一致。

## 12.2 用触摸走完一次外设适配

### 12.2.1 从四类硬件条件进入设备树

先拿出实际连线，不立即背属性名。触摸芯片需要供电、I2C、复位和状态通知。电源让芯片能工作，复位建立初始状态，I2C 传寄存器与触点数据，INT 通知 CPU 该读取状态。这四类关系缺一项，后续都可能表现为“触摸不工作”，但原因和检查不同。

本项目产品 overlay 把 GT9XX 描述在 I2C1，地址 `0x14`，INT/RST 使用 GPIO0_C5/C6，供电引用 `vcc_lcd_tp`。这是当前源码表达的关系，必须与所选底板对应；GPIO 的逻辑有效值还要经过驱动 API 和开关电路，不能直接当成物理高低。

基础描述与产品 overlay 合起来表达这套硬件，但驱动必须认得属性。讲解到这里可以解释一个具体取舍：把接线放在设备树，能让同一驱动适应不同板子；代价是属性契约要匹配。两套 GT9XX 使用不同 GPIO、供电和坐标属性，即使 `compatible` 类似，也不能直接互换。

### 12.2.2 用明确分支讲初始化

主讲分支选择云奥资料内的本地 V2.2，先声明它是当前可阅读的源码样本。包内旧家族符号提供相关线索，仍不能证明此文件逐字进入交付内核。产品 `tp-size=9112` 也不在本地旧分支的显式选择列表中，不能为了讲通正常流程就假定这一组合已经配套。

沿[第 05 章](05_驱动匹配与初始化.md)说明：内核依据总线与有效节点建立设备，驱动注册后完成匹配，进入 `goodix_ts_probe()`。probe 检查总线能力、建立状态对象、解析板级参数，再取得供电和 GPIO，完成复位、地址选择、通信检查和芯片配置，最后注册输入能力并建立事件处理条件。

每个阶段都应接一句“这给下一步提供什么”。例如没有可靠供电和复位，I2C 地址配置只是文字；未验证通信，读取芯片范围就没有可靠来源；未建立 input 能力，上层无法正确解释后续坐标。资源提供者未就绪时还需要正确保留错误码，才能让驱动核心安排后续探测。

将资源申请和失败清理放在同一条叙述里：无论接口和异步工作怎样安排，释放状态对象前都必须处理仍可能访问它的回调。设备管理的自动释放能帮助回收资源，却不能自动证明线程、定时器和所有失败分支都已安全收束。这样才能解释为什么“初始化依次申请”还需要配套的失败回退和退出同步。

### 12.2.3 从一次通知讲到一帧事件

初始化之后，转向运行时。这里可以用连续口述展示因果链：

> 手指变化首先发生在触摸芯片里。中断线只提供通知，没有携带坐标；驱动必须再发 I2C 事务读取状态和记录。本地旧代码虽然用线程化 IRQ 注册，回调仍会控制 IRQ 状态，再把采集投递到单线程 `goodix_wq`。真正读芯片的是工作函数。
>
> 工作函数读取 `0x814E` 附近状态与首个记录，先检查就绪位和触点数，多点时继续取数据。随后解析触点 ID、X/Y 和接触量，按所选配置处理坐标，再报告输入事件。一帧末尾的 `input_sync()` 标记这组变化完成，evdev 将标准事件交给用户空间。桌面最后还要把输入映射到实际显示方向与界面。

接着用[第 07 章](07_触摸与input.md)的示例解释为什么按下、移动和释放不是简单的三种 I2C 指令：驱动结合触点 ID 与前后帧状态识别持续存在或消失的接触。Type B 用 slot 保持身份，消失的触点需要释放；Type A 用逐点同步及帧边界组织接触信息。本地旧分支的选择与 `CONFIG_CHROME_PLATFORMS` 条件有关，不能看见 slot 函数就认定当前一定走 Type B。

再解释上下文与时间。I2C 事务、等待和复位可能睡眠，因此需要合适的线程上下文。工作队列便于串行处理，但引入排队时间；重复通知也不自动生成一份独立、永久保留的触点帧。重试提高通信成功机会，却可能拉长处理和暴露错误返回约定不一致的问题。

此处有两个值得讲清的代码细节：本地旧分支使用的 I2C 两消息事务完整成功要返回 2，这个 2 是完成的消息数，不是字节数；多点续读的返回值如果没有检查，首段成功仍不能证明整帧完整。讲清它们的影响与条件即可，不把静态风险宣称成当前已复现的故障。

### 12.2.4 用另一分支说明设计取舍

在听者理解第一条链后，再比较 V2.8.7：其 `gtp_irq_handler()` 运行于 IRQ 线程，直接调用 `gtp_work_func()`、`gtp_get_points()` 完成采集，省去了旧路径的额外 workqueue 投递。它同时更换了属性与状态管理方式，所以比较必须以各自完整链路为单位。

这里可以引出一个底层原则：执行上下文由调用者决定，不由名字决定。V2.8.7 的无 IRQ 路径从普通 hrtimer 回调直接进入采集，其下游又有可睡眠操作，因而形成上下文不匹配的静态风险。`work_func` 这个名称不能证明它一定运行于工作队列。

恢复同样分为软件和硬件两层。代码重新允许上报，并不证明供电、芯片应答和有效数据已恢复；V2.8.7 恢复错误后仍可重新允许 work，正适合用来说明为何要继续检查硬件通信和事件，而不能把标志位当验收结果。

## 12.3 将同一方法用于显示、供电与散热

### 12.3.1 显示与背光共享体验，控制通道不同

从刚讲完的触摸转到另一条并行链：输入告诉桌面“用户点了哪里”，显示负责把界面送到人眼，二者要通过方向和坐标映射配合。DRM/VOP 经 DSI 向 panel 输出像素，route 和 endpoint 描述连接；面板供电、复位和初始化命令建立接收条件，视频时序决定每行每帧的扫描节拍。背光则由独立的 PWM5 和使能电路提供照明。

用一个可复算例子解释“配置值”的层次：67.3 MHz 是像素时钟，需除以包含消隐区的 854×1314 才得到约 60 Hz；默认亮度 200 首先是表索引，普通 256 项表与 PWM 变体 197 项表对它的有效性不同。前者不是屏幕每秒刷新几千万次，后者也不是天然等于某个光学亮度百分比。

再用命令等待说明时间位置也属于语义。原始表要求 `0x11` 后等待再发 `0x29`；当前 overlay 在记录中的延迟位置不同。若实际解析器采用资料描述的命令后延迟语义，两者就不等价。另一阶段的 120 ms 不能仅因数值相同而替代所需间隔。这是条件性解释，仍需匹配 panel 实现和当前运行证据。

### 12.3.2 电源接口统一的是信息对象

界面上的电池图标需要容量、状态和外部供电信息，但这些信息不是同一个器件完成的。`simple-battery` 提供电池参数描述，CW2015 通过采样与模型相关状态提供电量信息，`gpio-charger` 读取外部输入在线，`power_supply` 将它们表达成可查询对象。实际充电由硬件通路承担，ONLINE 不能单独证明正在给电池充电。

当前 64 字节 profile 与 Word 的 FEB 6 Ah 数据匹配，说明资料之间有对应；还需确认实物电池是否符合该模型。缺少匹配 CW2015 实现时，不能编造双节标志的换算函数或 5000 ms 属性的实际调度路径。这里的学习重点是区分元数据、模型、观测和最终状态，而不是记一个容量值。

### 12.3.3 温控由策略把温度变成请求

温度采集得到观测，thermal zone 组织温区，trip 描述控制阈值，governor 根据策略作出冷却请求，cooling map 建立设备关联，pwm-fan 再把档位映射为 PWM。当前包的 60℃、85℃是两个 passive trip，不能据此简化成“到前者开、降到后者关”。

还要继续跨过两个交接：本包 pwm-fan 为模块，须装载并绑定；策略需要的 cooling device 能力必须与驱动提供的能力相容。档位 2 是请求表中的一个位置，不是已测转速。PWM 波形经过实际供电开关和负载才产生风扇响应，完整判断需要软件关系与物理观察同时成立。

## 12.4 回到构建交付，解释改动怎样被采用

此时听者已经认识硬件、描述和驱动，便会自然追问：这些内容怎样放进设备？用[第 02 章](02_BSP构建与交付.md)的产物图回答。

内核工程按配置生成内核、模块及基础 DTB，包装为配套 Debian 包；产品 overlay 工程生成源码包，在目标内核环境的 DKMS 生命周期中形成 DTBO 与安装链接；镜像工具组织 RootFS、启动内容和指定包。它们可以在镜像准备或已有目标系统中汇合。

实际生效还要跨过安装脚本与启动选择。包的 `postinst` 调用系统 hooks，overlay 的安装回调可能调用 rsetup；当前缺少完整目标环境，不能仅凭这些入口宣布启动已采用新配置。应从包身份检查到最终树、绑定驱动，再到接口和物理结果。

用本项目的真实差异结束这一段：同为 0.2.4 的两个 overlay 包内容不同，本地 DTS 与包内 DTB 的 SDMMC0 等状态不同。可重复交付需要保存硬件版本、源码/补丁、配置、包哈希和启用组合；只记录“编译成功”或版本号不足以解释下一台设备。

## 12.5 用故障案例展示推理过程

选择“触摸有事件但点击错位”作为连续案例。先说明观察条件：一台已确定底板、面板和启动版本的设备，在四角触摸时持续出现位置偏差。然后区分 input 事件与桌面行为，避免一次修改多层参数。`evtest` 看到的是驱动已经解析和变换后的事件，本文所谓“原始 input”只是相对桌面映射而言，不能当作芯片寄存器原始数据。

判断四角时，先依据已声明的坐标范围和预期方向，写下物理左上角应该接近哪组最小值或最大值，再与事件比较。不同量程的坐标先按各自范围比较相对位置，不能把触摸数值直接当显示像素。若事件对应已经不正确，沿芯片 CFG、驱动范围与变换继续追踪；仅凭 evtest 还不能区分芯片数据错误与驱动变换错误，需要配套源码及必要的采集诊断。若 input 对应正确而桌面偏差明显，下一步转向输出映射和重复旋转。这项结果缩小了定位范围，并不代表所有多指、恢复路径都通过测试。

讲述中保留完整推理顺序：现象 → 已确定层级 → 候选原因 → 能区分原因的检查 → 不同结果下的下一步。命令是取得证据的手段，关键在于说明输出会怎样改变判断。其他黑屏、电量和风扇案例可沿[第 11 章](11_故障排查与验证.md)展开。

## 12.6 用追问检查是否真正理解

完成主讲后，再用以下问题检查自己是否能脱离提纲回答。遇到需要细节的追问，回到[第 13 章](13_关键资料阅读索引.md)定位函数、节点、原理图页和包内成员。

### 12.6.1 自查问题

1. 为什么不直接在应用里读写 GPIO/I2C 完成触摸和背光控制？采用内核子系统的代价是什么？
2. 为什么“节点存在、节点启用、驱动编译、probe 成功、上层可用”不能只保留一个“已支持”状态？
3. 线程化 IRQ 和 workqueue 都允许等待，为什么换成另一种还要重新检查生命周期？
4. 背光亮但无图，怎样把静态命令延迟差异合理放进故障分析？
5. 被问“现在所有外设都正常吗”，怎样给出清楚且不过度扩张的回答？

### 12.6.2 回答要点

1. 直接访问可用于受控实验，但资源所有权、协议解析、并发、恢复和标准事件都要由应用承担。内核子系统提供复用接口，仍要求驱动遵循它的生命周期和资源约定。
2. 五层分别回答描述、有效性、代码存在、初始化结果和实际消费，前一层成立并不自动保证后一层；分开才能定位最早缺失的条件。
3. 调度入口、屏蔽范围、在途工作和退出同步会改变。允许睡眠不等于自动串行，也不等于取消状态位能等待已经运行的工作完成。
4. 先确认当前板型、基础树、插件与 panel 实现，再核对等待语义和实际命令路径。静态差异可以形成候选原因，需要能排除其他原因的运行证据才能认定根因。
5. 说明已经具备的源码、包内和资料层证据，再明确当前实板需要的启动、绑定、事件/读数、物理测量与上层结果。主机文档核查不等于整机验收。

一次合格的项目讲解，应能把“为什么需要、怎样实现、如何交付、凭什么判断正确”连续讲完。需要展开哪一部分时，回到对应章节和原件，而不是以更长的术语清单结束。
