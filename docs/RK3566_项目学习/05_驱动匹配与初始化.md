# 05 驱动匹配与初始化：从设备描述到输入设备

```text
初始化依赖
最终设备树 ─ I2C 控制器驱动 ─ adapter ─ gt9xx 的 i2c_client ─┐
内建初始化 / 模块加载 ─ 注册 GT9XX 匹配表 ──────────────────┤
                                                         └─ 匹配 → probe
GPIO / pinctrl / regulator 提供者 ───────────── 资源取得 ────────┤
                                                             ↓
                         上电 → 复位选址 → I2C 检查 → 触摸配置
                                                             ↓
                                      注册 input → 建立 IRQ / 轮询
                                                             ↓
                                                  等待运行时触点

生命周期分支
局部失败 → 按已取得资源回退
工作状态 → 挂起 → 唤醒、恢复通信 → 继续采集
设备解绑 → 停止新事件 → 等待在途访问 → 注销接口、关闭资源、释放状态
```

核心依据：[云奥 V2.2 `gt9xx.c`](<../../云奥-270nit-6inch/mipi_touch (1)/mipi_touch/gt9xx.c>) 的 `goodix_ts_init/probe/remove`、`gtp_request_io_port()`、`gtp_init_panel()`、`gtp_request_input_dev()` 及休眠回调；[阿美林 V2.8.7 `gt9xx.c`](../../阿美林-1000nit-7inch/GT9XX通用调试包/gt9xx.c) 的 `gtp_probe()`、回退标签、`gtp_drv_remove()` 与电源管理实现。图中的退出顺序表达资源寿命要求，下文会指出当前代码未满足的环节。

上一章已把 I2C1、地址 `0x14`、INT/RST 和电源连接成设备描述。现在内核需要把描述变成三个协作对象：总线上可寻址的 client、驱动持有的运行状态，以及 input 子系统登记的输入设备。正常初始化先采用云奥 V2.2 的具体代码，再对照 V2.8.7 的实现差异。

## 5.1 总线设备与驱动注册在匹配处汇合

### 5.1.1 描述中的芯片怎样成为 client

I2C 控制器驱动取得自身的寄存器、时钟和 IRQ，注册 I2C adapter，负责后续总线传输。I2C 核心根据可用子节点建立 `i2c_client`，保存器件地址、所属 adapter 和设备树节点。GT9XX 驱动接手的是这个 client，控制器驱动负责实际在 SDA/SCL 上执行传输。

这里 `reg = <0x14>` 是总线器件地址；运行时读取的 `0x814E` 是触摸芯片内部寄存器地址。基于设备树建立 client 不要求先读到芯片 ACK，所以断电器件也可能已有软件对象，通信检查留到 probe。设备树子节点与 client 的关系可对照 [Linux v6.1 I2C 设备实例化说明](https://www.kernel.org/doc/html/v6.1/i2c/instantiating-devices.html)。

| 对象 | 建立者 | 持有内容与交接 |
| --- | --- | --- |
| `i2c_adapter` | I2C 控制器驱动 | 总线传输方法，接受发往具体地址的消息 |
| `i2c_client` | I2C 核心 | 芯片地址、adapter、设备树节点，传给 probe |
| `goodix_ts_data`，简称 `ts` | GT9XX probe | GPIO、电源、采集任务、范围与状态，供回调共同使用 |
| `input_dev` | GT9XX 申请、input 核心接收注册 | 事件能力和输入状态，连接 evdev 等处理器 |

`i2c_set_clientdata(client, ts)` 把 client 与私有状态关联起来。IRQ 注册时将 `ts` 作为回调参数，work 则内嵌在 `ts` 中；以后每次采集继续访问这份对象，其寿命必须覆盖所有异步使用者。

### 5.1.2 注册驱动后，由框架调用 probe

云奥 [Makefile](<../../云奥-270nit-6inch/mipi_touch (1)/mipi_touch/Makefile>)将 `gt9xx.o` 与 `gt9xx_update.o` 组成内建目标。实际进入初始化后，`goodix_ts_init()` 创建单线程 `goodix_wq`，再执行 `i2c_add_driver()`。内建驱动在内核初始化时注册，模块驱动在加载时注册；两种方式最终都要与设备匹配，构建差异见[第 02 章](02_BSP构建与交付.md)。

下面摘录旧驱动描述，省略 `id_table` 等其他字段；函数指针把生命周期交给 I2C 框架管理。

```c
static struct of_device_id goodix_ts_dt_ids[] = {
    { .compatible = "goodix,gt9xx" }, /* 与设备树身份字符串对应 */
    { }
};

static struct i2c_driver goodix_ts_driver = {
    .probe = goodix_ts_probe,          /* 匹配后取得和初始化资源 */
    .remove = goodix_ts_remove,        /* 解绑时停止访问并回收 */
    /* ... 省略 id_table ... */
    .driver = {
        .name = GTP_I2C_NAME,
        .of_match_table = of_match_ptr(goodix_ts_dt_ids),
    },
};
```

设备与驱动注册的先后可以不同，两边都存在且匹配后才具备调用 probe 的条件。`status = "okay"` 使节点可参与枚举，compatible 选择候选驱动，probe 返回值决定本次接管结果；它们分别控制不同阶段。

## 5.2 V2.2 先建立电源、引脚和通信条件

### 5.2.1 probe 中保存资源，运行回调才能继续使用

`goodix_ts_probe()` 先检查 `I2C_FUNC_I2C`，再以 `kzalloc()` 分配 `ts`，读取设备树及 `tp-size`。这里的能力检查询问 adapter 是否支持所需传输，尚未与芯片通信。probe 处在允许睡眠的任务上下文，可以等待电源稳定、执行 I2C 和使用 `GFP_KERNEL` 分配。

随后按名称 `tp` 取得 regulator。以下是该函数的源码摘录，保留获取失败与使能失败的不同处理：

```c
ts->tp_regulator = devm_regulator_get(&client->dev, "tp");
if (IS_ERR(ts->tp_regulator)) {
    dev_err(&client->dev, "failed to get regulator, %ld\n",
            PTR_ERR(ts->tp_regulator));
    return PTR_ERR(ts->tp_regulator); /* 保留原错误，包括依赖未就绪 */
}

ret = regulator_enable(ts->tp_regulator);
if (ret < 0)
    GTP_ERROR("failed to enable tp regulator\n"); /* 本分支只记录，仍继续 */
msleep(20);                          /* 电源请求之后等待 20 ms */
```

资源获取函数可以返回编码了错误的指针，`IS_ERR()` 负责识别，`PTR_ERR()` 取出负错误码。获取成功后，`regulator_enable()` 才发出使能请求，fixed regulator 再控制 GPIO，底板电路接通电源；这几层的对应已在第 03 章说明。使能出错却继续执行，会让本来发生在供电处的问题，稍后表现为 I2C 通信失败。

接着，probe 读取 INT、RST、可选 `power-gpio` 和尺寸等参数，执行 `INIT_WORK(&ts->work, goodix_ts_work_func)`、初始化 `irq_lock`，并把 `ts` 关联到 client。`max-x/max-y` 的直接赋值已注释，范围来源沿下一节的配置链确定；可选 power GPIO 也不能仅凭被读入就当作实际电源开关路径。

### 5.2.2 RST 与 INT 一起决定器件启动地址

`gtp_request_io_port()` 申请 RST 和 INT GPIO，把它们置为输入，再调用 `gtp_reset_guitar(client, 20)`。普通 GT9xx 分支的关键时序如下，摘自该复位函数，省略 GT9xxF 的提前返回和未启用的 ESD 代码：

```c
GTP_GPIO_OUTPUT(ts->rst_pin, 0);              /* 物理拉低 RST，开始复位 */
msleep(ms);                                 /* probe 传入 20 ms */
GTP_GPIO_OUTPUT(ts->irq_pin, client->addr == 0x14);
                                             /* 0x14 对应复位期间 INT 高 */
msleep(2);                                  /* 地址选择电平先稳定 */
GTP_GPIO_OUTPUT(ts->rst_pin, 1);              /* 释放复位 */
msleep(6);
gpio_direction_input(ts->rst_pin);
/* ... GT9xxF 在此提前返回 ... */
gtp_int_sync(50, ts);                        /* INT 拉低 50 ms，再切输入 */
```

`GTP_GPIO_OUTPUT` 在旧头文件中展开为 `gpio_direction_output()`，操作的是物理高低电平。它不会把 DTS 中保存的 `rst_flags` 自动当作 descriptor 逻辑极性执行。注释中的 `0x28/0x29` 是将 7 位地址 `0x14` 左移并加入读写位后的总线字节，和 `client->addr` 的表示方式不同。

INT 在复位时承担地址选择和同步，工作时才作为数据就绪通知。如果 Linux 按 `0x14` 创建了 client，而芯片实际按另一电平启动在 `0x5d`，软件对象照样存在，后续传输会访问错误地址。只观察运行阶段 INT 电平，可能遗漏发生在释放复位之前的选址错误。

## 5.3 通信和触摸配置确定 input 将描述的能力

### 5.3.1 配置组、sensor ID 与芯片现有配置分别起作用

复位后，旧驱动识别 GT9xx/GT9xxF，进行 I2C 测试、读取版本并执行 `gtp_init_panel()`。这里的 `panel` 是触摸配置函数的历史名称，操作 GT9XX 配置寄存器，与 DSI 面板的初始化命令分属不同驱动。

触摸 CFG 保存扫描和坐标参数。旧头文件启用了 `GTP_DRIVER_SEND_CFG`，`gtp_init_panel()` 先根据产品标志选择组 0 的数组，其余组来自头文件。若只有组 0 有内容，直接采用 sensor ID 0；存在其他组时才读取芯片 sensor ID，并用 0～5 的值选择数组、检查组长度。`tp-size` 选择产品方案，sensor ID 选择配置组，两者并非同一编号。

普通 GT9xx 接着读取芯片配置版本。版本小于 90 时，将所选数组的版本临时改成 0，复制到全局 `config` 缓冲区并重新计算校验；版本达到 90 时，代码将其视为固定配置，调用 `gtp_get_info()` 读取芯片现有范围和触发设置后返回，不发送所选组。因而“配置数组已经选中”还不能确定芯片最后采用哪份配置。

该缓冲区前两个字节保存寄存器地址 `0x8047`，配置正文从索引 2 开始。下面是同一函数中尺寸与校验相关的源码摘录；校验循环不包括末尾校验字节和 fresh 标志。

```c
check_sum = 0;
for (i = GTP_ADDR_LENGTH; i < ts->gtp_cfg_len; i++)
    check_sum += config[i];            /* u8 累加，以 256 为模 */
config[ts->gtp_cfg_len] = (~check_sum) + 1;
                                       /* 加上校验字节后，累加和模 256 为 0 */

if ((ts->abs_x_max == 0) && (ts->abs_y_max == 0)) {
    /* RESOLUTION_LOC=3；config[2] 是配置版本，其后是小端 X/Y。 */
    ts->abs_x_max = (config[RESOLUTION_LOC + 1] << 8)
                   + config[RESOLUTION_LOC];
    ts->abs_y_max = (config[RESOLUTION_LOC + 3] << 8)
                   + config[RESOLUTION_LOC + 2];
    ts->int_trigger_type = config[TRIGGER_LOC] & 0x03;
}
```

可写配置路径随后发送配置，恢复缓冲区原版本并重算校验，留给恢复路径再次使用。校验解决传输内容的完整性，配置组还必须匹配触摸矩阵；正确校验无法修复选错面板的问题。第 04 章指出的 `tp-size=9112` 分支缺失与尺寸赋值被注释，就发生在这条参数来源链中。

### 5.3.2 input 注册能力，IRQ 或轮询提供后续采集入口

`gtp_request_input_dev()` 用 `devm_input_allocate_device()` 申请输入对象，声明 `EV_SYN/EV_KEY/EV_ABS`、坐标和接触量范围，选择多点报告分支，并在 `gtp_change_x2y` 为真时交换 X/Y 上限，再调用 `input_register_device()`。注册完成后，input 核心可以连接 evdev，用户空间经 `/dev/input/event*` 读取标准事件。设备编号由系统分配，驱动没有写死 `event0`。

能力注册还没有产生真实触点。驱动继续用 `gpio_to_irq(ts->irq_pin)` 找到 Linux IRQ 编号，实际申请式是：

```c
ret = devm_request_threaded_irq(&ts->client->dev, ts->irq, NULL,
          goodix_ts_irq_handler,
          ts->irq_flags | IRQF_ONESHOT, /* 使用 touch-gpio 取得的触发标志 */
          ts->client->name, ts);        /* 回调继续访问同一个 ts */
```

原来的 `request_irq()` 已注释。此处是线程化 IRQ，回调又将采集投递到 `goodix_wq`；线程与 work 如何衔接见第 07 章。注意实际申请使用 `irq_flags`，并没有使用刚才从 CFG 读出的 `int_trigger_type` 查表，芯片的通知方式与主机 IRQ 类型要另外保持一致。

申请 IRQ 失败时，旧代码释放 INT GPIO，启动 hrtimer 轮询；首次等待 1 s，随后名义间隔为 `(GTP_POLL_TIME + 6) ms = 16 ms`。定时器只排队 work，I2C 仍在工作线程中执行。轮询让设备在没有 IRQ 时仍有采集机会，也会增加周期访问和调度延迟。释放 INT 所有权后，复位函数仍可能再次操作该引脚，这是这条后备路径的资源管理缺口。

## 5.4 失败、挂起和解绑要遵守同一份资源寿命

### 5.4.1 延迟探测保留依赖，回退必须撤销已取得状态

供电等提供者可能稍后才就绪。probe 返回 `-EPROBE_DEFER` 时，框架知道应在后续重新尝试；旧代码从 regulator 获取处原样返回错误，保留了这一语义。重试不会自动清理普通分配，也不会撤销已成功发出的所有硬件请求。

`devm_*` 管理的是与设备绑定的资源释放；普通 `kzalloc/gpio_request` 仍要显式回收。regulator 句柄与使能计数也不同：释放句柄不等于自动平衡 `regulator_enable()`，更不代替等待在途访问结束。[Linux v6.1 Devres 文档](https://www.kernel.org/doc/html/v6.1/driver-api/driver-model/devres.html)明确区分资源管理与调用者承担的并发同步。

旧 probe 的几个失败点说明了这种区别：

| 触发位置 | 当前代码处理 | 对后续的影响 |
| --- | --- | --- |
| `kzalloc(ts)` 后缺少节点、`tp-size` 或 regulator 获取失败 | 直接返回，没有 `kfree(ts)` | 普通内存遗留，反复延迟探测可重复分配 |
| 电源开启后缺少 `max-x/max-y` | 直接返回 | 普通内存与使能请求没有完整回退 |
| RST 申请成功、INT 申请失败 | 辅助函数释放失败的 INT，却未释放已取得的 RST | 后续重新申请可能受遗留占用影响 |
| I2C 测试失败 | 释放 GPIO、`ts`，路径上调用两次 `tp_unregister_fb()` | 此时 input 路径尚未注册该回调；缺失的 `tp_suspend` 实现决定对未注册对象的处理 |
| 配置、input 申请或注册失败 | 部分分支仅记日志，继续申请采集入口并返回 0 | 绑定可成立，但输入能力可能缺失；分配失败后继续采集还可能访问空对象 |

通信成功也要按辅助函数的返回语义判断。旧读函数完整成功返回 2 个消息；`gtp_i2c_test()` 只判断 `ret > 0`，probe 又只判断 `<0`。这会放过非负短传输，不能把该路径的一条“测试通过”日志作为完整数据传输的唯一判断。运行时对应缺口在第 07 章继续分析。

### 5.4.2 挂起保留对象，恢复重建芯片工作条件

旧驱动在 input 注册后，将 `goodix_ts_early_suspend/resume` 填入 `ts->tp`，交给 `tp_register_fb()`。其依赖的 `../tp_suspend.h` 和实现未随本目录提供，所以这里从已经登记的两个回调解释器件动作。

当前关闭了手势唤醒宏。挂起回调先设置 `gtp_is_suspend`，禁用 IRQ 或取消轮询定时器，然后让 INT 拉低、等待 5 ms，向睡眠寄存器发送命令 5；等待 58 ms 后关闭 `tp` 电源，再等 20 ms。`ts` 和 input 设备继续存在，挂起没有做解绑。

恢复先使能电源并等 10 ms，调用 `gtp_wakeup_sleep()`。普通 GT9xx 分支拉高 INT、等待、进行 I2C 测试，失败时复位并重试；成功后 INT 同步 25 ms。回调对普通 GT9xx 再发送配置，恢复 IRQ 或轮询并清除挂起标志。但供电或唤醒失败只记录日志，后续仍放行采集。

这条路径还有并发约束：`gtp_irq_disable()` 用的是 `disable_irq_nosync()`，取消 timer 也不会排空已提交的 work；挂起回调没有 `cancel_work_sync()`，采集函数又没有按 `gtp_is_suspend` 阻止普通读取。因此已排队采集可能与睡眠、关电交错。`irq_lock` 只保护 IRQ 开关状态，未覆盖整个“采集—复位—供电”过程。

### 5.4.3 remove 必须先终止所有使用者，再释放 ts

若 IRQ 已经把 `ts->work` 放进队列，解除 IRQ 只能停止以后进入的通知，队列里原有的 work 仍会访问 `ts`。正确的寿命依赖是停止生产新工作、等待已有工作退出，再注销 input、关闭供电并释放状态；`cancel_work_sync()` 体现的就是“等待在途 work”这一职责。

当前 `goodix_ts_remove()` 注销电源管理回调后，IRQ 模式下释放 INT GPIO 并 `free_irq()`，轮询模式下取消 timer，随后注销 input、释放 `ts`。它没有等待 `ts->work`，也没有对应地关闭 `tp` 电源、释放 RST 或移除配置 proc 入口；IRQ 还是通过 devm 申请，却在这里手工 `free_irq()`，托管记录未被一起移除。解绑与异步采集交错时，存在释放后仍访问设备状态的条件。

模块退出末尾的 `destroy_workqueue(goodix_wq)` 发生在 `i2c_del_driver()` 之后，无法代替每个设备在释放 `ts` 之前完成的等待。资源释放的正确性取决于相对顺序，不能只看某个取消函数最终是否出现。

## 5.5 V2.8.7 调整了初始化结构，也保留了具体缺口

### 5.5.1 独立追踪资源与配置路径

阿美林分支用 `devm_kzalloc()` 分别分配 `ts` 与 `pdata`，`gtp_parse_dt()` 将板级参数放入后者。按[第 04 章](04_设备树与overlay.md)对照，GPIO、电源、范围和配置属性都与旧分支不同。正常路径依次取得两路电源句柄、上电、申请 GPIO、复位、严格检查 I2C、读取固件信息、初始化触摸配置，注册 input 并申请 IRQ，然后接入电源管理、属性接口和 ESD；最后设置 `init_done` 与允许上报标志。

这份代码虽然调用 `gtp_pinctrl_init()`，函数开头却直接 `return 0`，后续获取 `default/int-output-high/int-output-low/int-input` 的专用代码不可达。INT 操作因此不会走这里保存的 pinctrl state；有效 GPIO 路径直接操作 GPIO。设备模型对默认 pinctrl 的处理与这个被提前跳过的函数，应分别理解。

复位函数先将 INT、RST 拉低，等待 50 ms；再通过 `gtp_int_output()` 根据 `client->addr` 选择 INT 电平，等待 1 ms 后释放 RST，等待约 5 ms，再将 INT 拉低 50 ms 并切回输入。`gtp_int_output()` 受 `goodix,int-sync` 控制：该值为 0 时不执行地址选择输出，因而移植 `0x14` 节点时必须一并考虑这个条件。若 RST GPIO 无效，函数在设置 `PANEL_RESETTING` 后直接返回，未清除此位，后续采集入口会一直退出。

配置路径也有差别：开启 `goodix,driver-send-cfg` 时按 sensor ID 读取 `goodix,cfg-groupN`；关闭时读取芯片现有 CFG。input 范围则来自 `touchscreen-size-x/y` 或默认值，轴交换后注册，不自动从这次 CFG 读取中更新。因此芯片扫描范围与 input 声明范围需要成对配置。

### 5.5.2 结构化回退仍要覆盖已经启动的异步入口

V2.8.7 对 input 注册失败等情况使用回退标签，正常 remove 也有 `free_irq()` 或 timer 取消、GPIO 释放、关电和句柄释放。不过每个入口仍要单独检查。

例如 `gtp_power_init()` 的两路电源获取都采用了下面的处理。摘录第一路，省略第二路的重复代码：

```c
ts->vdd_ana = regulator_get(&ts->client->dev, "vdd_ana");
if (IS_ERR(ts->vdd_ana)) {
    ts->vdd_ana = NULL;               /* 原错误指针已丢失 */
    ret = PTR_ERR(ts->vdd_ana);       /* 此时得到 0，无法保留延迟探测信息 */
    dev_info(&ts->client->dev,
             "Regulator get failed vdd ret=%d\n", ret);
}
/* ... 第二路电源采用同样处理 ... */
return 0;                            /* 调用者始终看到初始化成功 */
```

如果该电源实际依赖尚未就绪，错误被吞掉，`gtp_power_on()` 又跳过 NULL 句柄，初始化会继续到复位和通信。需要由外部硬件常供电的方案和需要软件管理电源的方案，不能依靠相同的成功返回来区分。

另一个发生在更晚的阶段：`gtp_request_irq()` 已成功后，`gtp_create_file()` 失败会跳到 `exit_powermanager`，继而注销 input、释放 GPIO 和 `ts`，这条回退没有释放 IRQ 或取消 timer。此时异步入口仍保存旧 `ts`，后续通知存在访问已释放对象的条件。正常 remove 中的清理不会自动补到一次失败的 probe 上。

### 5.5.3 工作标志、PM 回调和真正的同步各有职责

新分支的 `gtp_work_control_enable()` 只设置或清除 `WORK_THREAD_ENABLED`。清零可挡住以后进入的采集，已越过检查的 IRQ 线程仍可能继续 I2C；`ts->lock` 虽被初始化，普通采集并未用它保护完整事务。

挂起先避开固件更新，设置 `SLEEP_MODE`，关闭 ESD 和普通上报，再按配置选择手势待机、断电或发送睡眠命令。手势模式会重新允许工作，以便读取唤醒事件。恢复按相同选择执行唤醒、上电或复位并测试通信；失败时打印警告，成功时重开 ESD，但两条出口都清除睡眠位并允许上报。硬件仍不响应时，软件状态已经回到允许采集。

`CONFIG_FB` 分支使用显示 blank 通知，`goodix,resume-in-workqueue` 可把恢复排进 `fb_notify_work`；未用 FB 且启用 PM 时接入设备 PM 回调。正常 remove 会注销 notifier，但未取消已排队的恢复 work，和“禁止以后收到通知”仍是两个动作。新分支的无 IRQ timer 直接执行采集所带来的上下文问题，以及错误后旧触点是否释放，统一在下一条触摸运行链中解释。

## 5.6 将源码分支与交付内核对应起来

## 5.7 核心工程问题与深度理解

### 5.7.1 有 I2C client，却没有 input 设备，应怎样缩小范围

先看设备是否已经绑定，以及 probe 停在哪一步。client 来自描述，不能代替芯片 ACK；绑定后还要经过供电、复位选址、通信、配置和 input 注册。对旧分支，还需检查它是否只记录 input 注册错误后继续返回 0。此时调整桌面坐标不会补出缺失的输入设备。

### 5.7.2 把全部资源改成 devm，能否解决解绑中的在途访问

不能。devm 可以减少释放遗漏，但不会自动让普通 work、恢复 work 和维护线程停止访问资源。首先停止新事件并等待在途执行，再释放其访问的 input、GPIO 和私有状态；regulator 使能也要按实际取得的次数关闭。新分支 probe 的回退缺少 IRQ 取消，正说明托管内存并不自动保证回调寿命。

### 5.7.3 唤醒日志结束后仍没有触摸，为什么要先确认通信再查看坐标

两套本地分支都存在唤醒失败后仍恢复采集的出口。允许上报只是软件开关，只有电源、复位和完整 I2C 访问重新成立，才可能产生有效触点；没有有效数据时先改坐标变换会掩盖真正断点。通信恢复后，还要检查旧接触是否释放、新接触是否形成完整帧。
